# 组合优于继承

“组合优于继承”是一条选择复用机制的经验法则：独立变化的能力通常通过对象组合连接，稳定且真实可替换的类型关系可以使用继承。入口位于[原则目录](/principles)。它不否定继承或多态，而是要求把共享实现、状态耦合与替换成本一起评审。

## 学习问题

- 继承表达稳定类型关系和共享实现时有什么差异？
- 受保护状态与初始化顺序如何增加状态耦合？
- 组合为何更易替换，又会增加哪些装配成本？
- 哪些场景中继承比委托链更清楚？

## 要保护的性质

**来源事实：** Design Patterns 提出优先对象组合而非类继承的设计指导；Oracle 的 Java 教程说明子类继承超类成员并形成类型层次。**推断：** 选择依据不应是语法偏好，而是父类契约是否稳定、子类是否真正可替换，以及复用的能力是否需要独立变化。

要保护的是局部替换能力：改变一个策略、存储或通知能力时，不迫使整个类型层次理解新的状态和生命周期。继承能提供语言级多态与统一契约，组合则把变化放进明确协作者；二者都会产生耦合，只是传播路径不同。

## 冲突与适用上下文

继承可减少转发代码并让同一类型契约自然参与多态，但子类会受构造顺序、可覆写方法、受保护状态和基类演化约束。组合让能力独立替换，却增加接口、装配、委托和对象数量；过细组合会让一次简单行为跨越难以导航的委托链。

当领域中存在稳定的“是一个”关系、替换契约可验证、基类状态很小且扩展点明确时，继承可以是直接答案。若只是为了复用几行实现，或能力有不同生命周期和变化原因，组合通常更能限制传播。

## 机制

下表为本站原创选择矩阵，把继承树和组合对象图背后的成本显式化。

| 判断 | 继承 | 组合 |
| --- | --- | --- |
| 多态契约 | 子类型天然进入父类型位置，但必须满足替换语义 | 消费方依赖能力接口，运行时选择实现 |
| 共享实现 | 直接复用父类代码，容易连带继承不需要的行为 | 通过协作者复用，需编写装配和委托 |
| 状态耦合 | 子类可能依赖 protected 状态与初始化顺序 | 状态由各对象拥有，交互通过显式接口 |
| 替换成本 | 基类变化可能传播到整个层次 | 可替换单一协作者，但接口变化仍会传播 |
| 适合关系 | 稳定、真实、可验证的类型层次 | 独立变化的策略、能力和资源 |

**本站分析：** 先写替换契约，再问复用目标。若 `CachedRepository` 必须知道父类连接池字段才能工作，它共享的不只是实现，还有状态与生命周期；把缓存策略作为协作者后，替换边界更明确。反之，语言标准库中稳定的异常或抽象集合层次，用继承表达类型关系往往比多层转发更清楚。

## 误用与反原则

误用一是把继承当复制代码工具：子类为了一个辅助方法接受父类全部状态和钩子，随后基类修复会意外改变子类。误用二是把组合绝对化：为一个稳定、无状态操作创建五层策略与装饰器，调用路径和装配成本超过未来替换收益。

另一个反例是只有签名替换而没有语义替换。子类覆写方法后收紧前置条件或破坏父类不变量，即使编译器接受也不能安全多态。选择继承前应以契约和测试验证替换，而不是只验证 `extends` 可编译。

## 适用尺度

类尺度关注状态、覆写和构造；模块尺度可用组合连接策略与端口；服务尺度的“组合”表现为能力编排而非类继承；平台尺度则通过插件协议组合扩展。跨进程时还必须计入网络和故障语义，不能把对象组合经验直接等同于服务拆分。

对封闭且稳定的框架层次，继承可保持一致扩展协议；对业务策略、供应商适配器和运行资源，组合通常更适应替换。决定应随变化历史复核，而不是在编码规范中永久禁止某种语言机制。

## 相邻原则

[高内聚与低耦合](/principles/pr-02)用于比较两种复用机制的变化与状态耦合；[单一职责与关注点分离](/principles/pr-03)检查被组合的能力是否真的独立变化；[依赖倒置、控制反转与依赖注入](/principles/pr-04)约束组合时策略、抽象和具体实现的依赖方向。[KISS、YAGNI 与 DRY 的张力](/principles/pr-06)要求等变化边界稳定后再提取抽象；[演进式设计](/principles/pr-08)则在迁移期间使用可替换的组合接缝。

## 说明性场景

说明性场景：任务执行器需要重试、审计和速率限制。方案 A 建立 `AuditedRetryingRateLimitedExecutor` 继承链，每层覆写执行钩子并访问父类状态；方案 B 让执行器组合三个明确策略。

因为三项能力由不同团队和配置节奏驱动，选择 B，并在组合根固定顺序和失败语义。若所有执行器只共享一个稳定、无状态的 `execute` 模板且子类满足同一契约，则受控继承也可接受。[Kubernetes reconciliation 案例](/cases/kubernetes-reconciliation-loop)可继续观察控制循环如何通过组合具体资源适配器而保持核心机制稳定。
