# Secure by Design

安全设计不是在发布前追加一次扫描，而是让风险、控制、验证和运行反馈在同一生命周期中互相约束。它要求产品、架构、工程、运营与安全专长共同对结果负责；安全团队提供方法与复核，不能独自拥有安全。

这个原则提供把安全判断放回工程流的透镜。组件级的默认拒绝、最小权限和纵深防御由[最小权限、安全默认值与纵深防御](/principles/pr-09)提供；PR-16 把这些控制接入从需求到恢复的生命周期。可从[原则目录](/principles)继续浏览。

## 学习问题

- 如何把资产、信任边界和滥用路径变成可实现的安全需求？
- 默认拒绝与最小权限怎样在生命周期内被验证而非仅被声明？
- 为什么设计、静态、动态、依赖、配置和运行验证需要不同证据？
- 安全例外由谁接受、何时到期、何种条件下撤销？
- 发现控制失效后，谁有权停止、恢复和重新评估风险？

## 一页摘要

**来源事实：** [CISA 的 Secure by Design 指导](https://www.cisa.gov/sites/default/files/2023-10/Shifting-the-Balance-of-Cybersecurity-Risk-Principles-and-Approaches-for-Secure-by-Design-Software.pdf)面向软件制造商，强调把可预见风险从使用者转回能够改变设计的制造者。**推断：** 安全工作必须把需求、设计、实现、部署与运营连成可复核的工程链，而非把责任留给最后一道测试。

生命周期的每一步都要留下下一步可用的输入：资产和边界决定威胁问题，威胁问题决定控制与安全需求，验证产生有限的证据，运行检测揭示例外和新风险。证据只支持已检查的范围，不能把一次通过扩展成“系统已安全”。

下表回答“哪类判断由谁推进”，不是把安全交给一个单独角色。

| 生命周期判断 | 主要协作方 | 必须留下的结果 | 不能据此推出什么 |
| --- | --- | --- | --- |
| 资产与边界 | 产品、架构、工程、安全专长 | 资产、主体、信任边界与假设 | 已枚举全部攻击路径 |
| 控制与需求 | 架构、工程、运营 | 可测试的拒绝、授权、隔离与恢复条件 | 控制已在运行中有效 |
| 验证与发布 | 工程、测试、运营、安全专长 | 覆盖范围、失败记录与残余风险 | 测试关闭了设计风险 |
| 例外与恢复 | 风险所有者、运营、产品与安全专长 | 所有者、期限、撤销和恢复条件 | 例外会永久有效 |

## 事实边界

**本站分析：** Secure by Design 是工程与责任分配的方法，不是认证、产品功能或风险归零的同义词。加密可以保护某些数据与链路，却只是一个控制；它不定义安全设计，也不补足授权、隔离、检测和恢复缺口。

[NIST SP 800-160 Vol. 1 Rev. 1](https://csrc.nist.gov/pubs/sp/800/160/v1/r1/final)提供可信安全系统工程的生命周期语境；本文据此讨论工程活动，不把 NIST 文档当成合规结论或某个部署的安全证明。

## 架构图

要检查的不是线性“交付完成”，而是运行发现怎样回到资产和信任边界，迫使先前假设重新接受审视。

```mermaid
flowchart LR
  A["资产与信任边界"] --> T["威胁与滥用路径"]
  T --> C["控制与安全需求"]
  C --> V["实现与验证证据"]
  V --> O["运行检测与例外"]
  O --> R["风险再评估"]
  R --> A
```

这条回路要求将检测到的例外、失效和新依赖重新关联到资产与边界；只有补齐控制或明确接受残余风险后，才可继续发布或恢复。它不是“所有风险都能被发现”的保证。

下表把验证证据与其未覆盖部分分开，避免把一种工具替代另一种判断。

| 验证层 | 要回答的问题 | 证据不能证明 |
| --- | --- | --- |
| 设计评审 | 边界、滥用路径与控制是否可解释 | 实现没有偏离设计 |
| 静态与依赖检查 | 已知代码与组件问题是否被发现 | 运行配置和业务授权正确 |
| 动态与配置验证 | 已测攻击路径、部署配置是否按预期拒绝 | 未测路径不存在风险 |
| 运行检测 | 例外、漂移和异常是否可观察 | 过去和未来的设计风险已关闭 |

## 控制权与任务流

**来源事实：** [OWASP Threat Modeling Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)将威胁建模作为识别、沟通和处理威胁的工作流。一个可审查的输入序列是：资产、攻击者目标、信任边界和滥用路径；少一项就可能把控制选择变成无根据的清单。

**说明性场景：** 一个服务准备新增“导出审计记录”能力。产品说明受保护资产和合法用途；架构与工程标出管理员、导出服务和对象存储之间的信任边界；团队再列出越权导出、过期下载链接和日志泄露等滥用路径。默认拒绝没有匹配授权的导出，最小权限把临时凭据限制为单一租户、对象前缀和短期限；运行告警发现异常下载时，运营先撤销凭据并保留核查记录，再由风险所有者决定恢复条件。

这不是某个真实事件或产品承诺；它说明控制权随状态移动：产品与架构定义可接受用途，工程实现控制，运营执行撤销和恢复，风险所有者接受残余风险。对租户范围凭据和路由治理的具体实现，可对照[LiteLLM Virtual Keys 治理案例](/cases/litellm-virtual-keys-governance)，但该案例不因此被宣称实现本文全部生命周期控制。

## 关键源码导读

这个原则没有单一源码入口。先从资产清单、数据流与接口契约读取信任边界，再检查授权策略、基础设施配置、依赖清单、测试报告和运行告警是否能指向同一控制要求。

这些材料可以证明某次评审或验证覆盖了什么，不能证明产品整体没有设计风险。渗透测试是部分攻击路径的证据，不是关闭设计风险的开关；当策略或边界改变，应回到威胁模型与验证范围。

## 架构决策与权衡

**推断：** 默认拒绝与最小权限应先决定“无明确授权时发生什么”，再决定授权成功后能做什么；这使策略缺失、身份不明或上下文不完整时的结果保持保守。

[Fail Fast、Fail Safe 与 Graceful Degradation](/principles/pr-07)补充控制不可用时的停止或诚实降级边界。

[幂等与最小协调](/principles/pr-10)约束撤销、补偿和恢复期间可能被重放的副作用。

纵深防御需要不同失效模式的独立防线：例如授权拒绝、网络或服务隔离、密钥限制、审计与运行检测分别限制不同路径。重复部署同一错误策略并不构成独立防御层；独立也不等于永不共同失效，仍须在设计中说明依赖与失效相关性。

下表回答控制为何不能由一个检查点承担全部负担。

| 控制选择 | 获得什么 | 代价与适用边界 |
| --- | --- | --- |
| 默认拒绝 | 未匹配政策不扩大权限 | 需提供可诊断的拒绝和受控恢复路径 |
| 最小权限 | 缩小每次操作的可达范围 | 需要维护角色、资源、期限和变更流程 |
| 独立防线 | 单一控制失效不必直接变成完全失守 | 增加配置、监控与故障排查复杂度 |
| 多层验证 | 让设计与运行假设分别受检 | 覆盖范围有限，不能承诺风险清零 |

## 生产化分析

**本站分析：** 生产化的关键不是“上线后再修”，而是把发布门、告警、变更、例外和恢复连接到风险判断。风险接受必须有例外期限、责任所有者和撤销条件；到期、条件触发或范围变化时，例外应被撤销、续审或以新的控制替代，而不是静默保留。

发现配置漂移、依赖漏洞或异常访问时，运营者需要有权停止受影响能力、撤销凭据或隔离路径；恢复前要核对影响范围、控制状态和未完成副作用。风险所有者可以接受明确的残余风险，但不能用接受决定消除受影响用户、工程或运营的共同责任。

下表把例外视为可终止的状态，而不是永久豁免。

| 状态 | 所有者动作 | 退出条件 |
| --- | --- | --- |
| 申请 | 说明资产、范围、替代控制与风险 | 有授权的风险所有者作出决定 |
| 生效 | 记录期限、检测信号和撤销条件 | 到期、条件触发或范围变化 |
| 撤销或恢复 | 停止豁免，补齐控制并核查影响 | 风险重新评估后才允许恢复 |

## 可迁移经验

### 可直接复用的机制

把威胁建模输入、可测试控制、验证范围、运行信号和例外状态串成同一评审回路。每个控制都要有实现所有者、运行观察者和恢复条件，才能在变化后判断下一步。

### 只能有限类比的部分

默认拒绝、最小权限和纵深防御可跨系统复用，但具体资产、攻击者能力、信任边界、法规和可恢复性不同。加密、扫描或渗透测试各自提供有限证据，不能替代本地的威胁模型与风险决策。

### 不应照搬的部分

不要把通用清单直接当作发布许可，也不要把例外固定为永久配置。安全团队不应代替产品、架构、工程与运营作出其授权范围内的决定；没有明确所有者、期限、撤销和恢复条件的例外不应启用。
