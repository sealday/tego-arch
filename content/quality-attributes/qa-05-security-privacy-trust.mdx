# 安全、隐私与信任边界

系统启用了加密和服务身份，仍可能让一个租户导出另一个租户的数据；用户点了“同意”，也不代表后续派生数据、日志和备份都符合原处理目的。Security 关心资产面对威胁时的保护，privacy 关心数据处理给主体带来的影响；两者重叠，却不能相互代替。

本文位于[质量属性目录](/quality-attributes)，承接[质量属性总览](/quality-attributes/qa-00)与[质量属性场景写法](/quality-attributes/qa-01)，把资产、主体、数据流、目的和授权上下文放进同一张可验证场景。

## 学习问题

- 资产、数据主体、数据类别与处理目的应如何共同盘点？
- 信任边界为何是安全假设或授权上下文变化，而不只是网络分段？
- 威胁与隐私伤害如何分别分析，又在哪里交叉？
- 跨租户导出要用什么证据证明边界有效？

## 定义与业务目标

**来源事实：** [NIST SP 800-160 Vol. 1 Rev. 1](https://csrc.nist.gov/pubs/sp/800/160/v1/r1/final)提供面向可信系统的工程视角；[NIST Privacy Framework 1.0](https://doi.org/10.6028/NIST.CSWP.01162020)提供识别和管理隐私风险的自愿框架。它们不是本站合规结论，也不把草案版本当作正式版本。

**本站分析：** 最小盘点要同时记录资产、数据主体、数据类别、处理目的、控制者和生命周期。威胁问题是“谁能利用什么条件破坏机密性、完整性或可用性”；隐私伤害问题是“即使系统按设计运行，这种收集、关联、推断或披露会怎样影响主体”。同一数据流可能同时进入两类分析，但威胁清单不等于隐私影响清单。

| 对象 | 必须记录 | 决策边界 |
| --- | --- | --- |
| 资产 | 业务事实、凭据、模型输出、审计记录 | 谁能读、改、删或触发副作用 |
| 数据主体 | 用户、员工、第三方联系人 | 主体如何知情、访问、更正或退出 |
| 数据与目的 | 原始字段、派生数据、用途、最小字段 | 新目的必须重新授权和评估 |
| 生命周期 | 在线数据、日志、备份、保留与删除 | 删除请求如何传播并留下受限证据 |

目的限制要求数据只用于声明且批准的目的；最小化要求只收集、传输和保留完成该目的所需的数据。派生数据不会因为由模型或统计过程生成就脱离治理，日志与备份也不会因为“只供运维”就自动豁免保留和删除策略。

## 质量属性场景

下面六字段场景是本站原创说明，验证的是一个有界的跨租户导出控制，不是完整 Security 或 privacy 认证。

| 字段 | 场景 |
| --- | --- |
| Source | 已登录的租户 A 管理员 |
| Stimulus | 提交包含租户 B 对象标识的批量导出请求 |
| Environment | 正常流量，缓存、异步队列和对象存储均启用 |
| Artifact | 导出 API、授权策略、任务消息、文件、日志与备份索引 |
| Response | 在每次上下文转换处重建租户和目的约束，拒绝越权对象并审计 |
| Response measure | 跨租户对象为零；拒绝原因、策略版本、请求 ID 和删除传播结果可核对 |

### Source

已登录的租户 A 管理员。

### Stimulus

提交包含租户 B 对象标识的批量导出请求。

### Environment

正常流量，缓存、异步队列和对象存储均启用。

### Artifact

导出 API、授权策略、任务消息、文件、日志与备份索引。

### Response

系统在每次上下文转换处重建租户和目的约束，拒绝越权对象并审计。

### Response measure

跨租户对象为零；拒绝原因、策略版本、请求 ID 和删除传播结果可核对。

证据必须覆盖直接请求、缓存命中、队列重放、对象存储下载和备份恢复后的读取路径。一次 API 拒绝测试不能证明所有派生路径都守住边界。

## 架构策略

信任边界是安全假设或授权上下文发生变化的地方，不是网络段的同义词。进程内插件、队列消费者、缓存键、租户切换和数据目的变化都可能跨越边界；反之，同一套授权上下文即使跨网络，也不必被误画成新的权限模型。

以下本站原创 DFD 风格表先问“什么随数据一起越界”，再决定控制点：

| 流 | 数据与目的 | 边界前假设 | 边界后必须重建 | 失败动作 |
| --- | --- | --- | --- | --- |
| 用户 → API | 导出条件；履行用户请求 | 外部声明身份 | 主体、租户、权限、目的、完整性 | 拒绝且不创建任务 |
| API → 队列 | 最小对象引用；异步执行 | 在线请求上下文 | 签名、租户、策略版本、过期时间 | 隔离消息 |
| Worker → 存储 | 导出文件；限时交付 | 任务已授权 | 对象级租户、下载者、保留期 | 删除未发布文件 |
| 系统 → 日志/备份 | 最小审计字段；恢复 | 生产处理目的 | 访问者、二次用途、删除例外 | 限制查询并登记残留 |

实现上把身份认证、租户授权、对象过滤、目的标签和完整性校验分开记录。加密只保护特定传输或存储边界，服务身份只说明调用方是谁；两者都不能证明对象级授权或处理目的正确。consent 也不是无限期、无限用途的授权。

## 测量信号与阈值

至少记录拒绝与允许决策、主体与租户、策略版本、数据类别、处理目的、字段最小化差异、派生数据去向、保留到期、删除传播、异常导出量和审计访问。阈值来自资产价值、伤害分析、合同与适用规则，不能把一个扫描器默认分数外推成通用安全线。

验证通过意味着声明的路径和对象集合中没有跨租户泄露，且日志、备份与派生数据符合已批准的保留或受限例外。它不意味着所有威胁已穷尽，也不证明任何法律合规。

## 权衡与失败模式

更细的对象级授权降低越权风险，却增加策略复杂度、延迟和审计量；更少日志改善数据最小化，却可能削弱取证；更短保留期减少暴露窗口，却提高恢复和争议处理成本。控制必须说明保护目标、失败方式和不可用时的降级边界。

失败模式是把网络隔离或 mTLS 当作租户授权，因为可信服务仍可能携带错误租户上下文，导致合法连接执行越权导出。另一个反例是把 consent 或合规清单当作 privacy 证明，因为新用途、派生数据和长期备份会超出原语境。

STRIDE 可帮助提出威胁问题，但不能证明威胁完整；加密、服务身份、同意和审计也都不证明 Security/privacy。对于完全不处理敏感数据且没有跨主体影响的本地演示，可简化流程，但仍需声明资产和边界。

## 说明性场景

**说明性场景：** 租户 A 管理员请求导出，其过滤器中混入租户 B 的对象 ID。API 的对象级检查拒绝直接路径；测试随后重放旧队列消息并尝试复用已生成文件，确认策略版本、租户标签和下载授权仍阻止 B 的数据出现。日志只保留核对所需标识，删除任务继续覆盖导出文件、派生索引和备份例外清单。

**基于证据的推断：** 这组有界测试能支持“所列路径在所测策略版本下拒绝跨租户导出”，不能外推为系统已安全、隐私风险已清零或满足全部合规要求。
