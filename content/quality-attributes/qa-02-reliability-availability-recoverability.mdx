# 可靠性、可用性与可恢复性

服务返回成功不代表业务结果正确，服务短暂不可达也不等于数据已经丢失。可靠性分析要拆开 fault、failure、可用性、恢复时间和数据边界，否则一个“99.9%”会掩盖完全不同的损失。

本文承接[质量属性目录](/quality-attributes)中的[质量属性总览](/quality-attributes/qa-00)与[质量属性场景写法](/quality-attributes/qa-01)，把可靠性词汇放回触发条件、状态所有权和恢复证据中。

## 学习问题

- fault 与 failure 的边界为何会改变隔离和恢复策略？
- 可用性比例为什么不能代替 RTO、RPO 与业务正确性？
- 网络超时造成结果未知时，谁有权重试、核对或终止？
- 如何证明恢复完成，而不是只证明进程重新启动？

## 定义与业务目标

**来源事实：** [Google SRE Availability Table](https://sre.google/sre-book/availability-table/)说明时间型可用性比例与允许不可用时间之间的换算假设。它不替团队设定 SLO，也不证明请求成功、数据正确或恢复过程安全。

本文把 fault 作为可能导致异常的内部缺陷或外部条件，把 failure 作为系统对外未能提供所需服务的可观察偏差。一个 fault 可以被冗余或隔离吸收而不形成 failure；同一 failure 也可能由不同 fault 引起。可靠性关注在规定条件和时间内维持正确服务，可用性关注所需时刻能否提供服务，可恢复性关注 failure 后恢复服务与业务状态的能力。

业务目标必须进一步声明允许中断、允许丢失和允许不确定各是多少。RTO 表示需要在多长时间内恢复目标能力，RPO 表示恢复点允许落后多少数据；两者是业务边界，不是备份工具的默认参数。

## 质量属性场景

以下六字段是本站原创的订单恢复场景。数值仅用于说明结构，实际阈值必须由业务承诺、损失与演练证据批准。

### Source

主区域数据库健康检查与订单核对器共同产生信号；前者报告连接 fault，后者识别业务结果缺口。

### Stimulus

主区域写入连续失败，且部分请求在提交后未收到确认，因此客户端看到 failure 或结果未知。

### Environment

促销峰值期间，订单入口仍接收请求，备用区域最近一次可验证恢复点落后 30 秒。

### Artifact

订单写入路径、提交日志、幂等键、未确认订单集合和备用区域恢复流程。

### Response

停止向故障路径发送新写入，保存未知结果的核对责任，切换到已验证恢复点，并在恢复后对账而不是盲目重试副作用。

### Response measure

说明性目标为 5 分钟内恢复受控接单（RTO），已确认数据丢失窗口不超过 30 秒（RPO），所有结果未知订单均进入核对，且未经核对不重复扣款。

先看本站原创插图中的两条分支：fault 可能被隔离，也可能传播；无论走哪条恢复路径，恢复验证与结果未知核对都不能被省略。

![区分故障隔离、传播与可验证恢复路径](/img/illustrations/qa-02-failure-recovery-boundaries.png)

*图：RTO 约束恢复能力所需时间，短的回看 RPO 括号约束恢复点；恢复完成仍需验证业务结果。*

图不表示每个 fault 都会成为 failure，也不承诺未知结果都能自动解决。本站原创边界表进一步精确回答各信号证明什么：

| 信号 | 可以证明 | 不能证明 |
| --- | --- | --- |
| 健康检查失败 | 探测路径观察到异常 | 业务已经 failure |
| 可用性比例 | 时间窗口内探测成功占比 | 数据正确或副作用唯一 |
| RTO 达成 | 目标能力在时限内恢复 | 所有积压和错误状态已清理 |
| RPO 达成 | 恢复点落后未超过边界 | 结果未知请求已经核对 |

## 架构策略

故障隔离、冗余、健康探测、故障转移、持久日志、幂等、核对与降级分别处理不同边界。[Google SRE 关于级联故障的章节](https://sre.google/sre-book/addressing-cascading-failures/)解释资源耗尽、正反馈与恢复困难的机制；它是有语境的运行指导，不是通用恢复配方或当前 Google 政策。

**基于证据的推断：** 自动故障转移只有在状态复制、写入所有权与回切条件清楚时才改善场景。否则它可能把局部 fault 扩散成双写冲突，或在依赖仍过载时制造级联 failure。

## 测量信号与阈值

最小信号包括探测开始时间、failure 影响范围、成功与错误请求、复制落后、恢复点、切换完成时间、积压、结果未知集合和核对结论。服务进程“up”只是一个信号，不能单独证明业务恢复。

阈值应同时覆盖时间和状态：可用性窗口、RTO、RPO、未知结果核对完成率、重复副作用与永久失败数量。恢复完成需要验证关键业务不变量，而不是在路由切换后立即停止观察。

## 权衡与失败模式

更敏感的探测可以缩短发现时间，却会增加误切换；更多副本可以吸收局部 fault，却增加复制延迟、成本和状态冲突；自动重试可以恢复瞬时 failure，却可能放大过载并重复不可逆副作用。每个策略都必须绑定预算、停止条件和核对责任。

失败模式是把可用性比例当作可靠性的全部，因为探测成功会隐藏错误数据、结果未知和不可恢复副作用，导致团队在仪表盘绿色时仍无法解释业务事实。另一个反例是故障后无限重试：它会争抢恢复所需资源，使级联故障持续。不要在副作用不幂等、结果无法核对或状态所有权不明时自动重放；不应把 RTO 与 RPO 写成同一个“恢复快”，也不可用备份存在代替恢复演练。对于可立即回退、无持久状态且失败后果很低的内部工具，不适用完整灾难恢复工程，但仍需定义停止与人工接管边界。

## 说明性场景

**说明性场景：** 上述订单系统在写入超时后先冻结未知请求的自动重试，再依据提交日志与支付查询核对结果。若备用区域达到说明性的 30 秒 RPO，但支付状态仍无法确认，恢复流程可以接收新订单，却不能宣告旧订单全部恢复；未知集合必须保留到自动或人工终态。

**本站分析：** 这一演练的判断点不是“是否切换成功”，而是服务能力、数据恢复点与副作用事实是否分别得到证据。数值和订单背景均为原创说明，不代表来源规定的通用目标或真实生产事件。
