# 架构模式

模式页按“谁掌握下一步控制权”组织概念。名称相同的实现可能采用不同状态、权限和恢复策略，因此模式只提供比较框架，不能替代案例证据。

外部学习起点：[LangChain 多智能体模式](https://docs.langchain.com/oss/python/langchain/multi-agent)。

## Agentic Architecture 模式入口

下面八篇把既有控制与协作概览映射到可独立使用的设计判断；顺序按基础模式到能力扩展排列：

1. [Deterministic Workflow vs Autonomous Agent](/patterns/agt-p-01)：先决定任务需要显式步骤还是自主选择下一步。
2. [Agentic RAG](/patterns/agt-p-02)：把检索、证据选择和引用核验组织为有停止条件的循环。
3. [Planner–Executor](/patterns/agt-p-03)：分离动态规划与执行，并明确重规划责任。
4. [Evaluator–Optimizer](/patterns/agt-p-04)：用可判定标准、预算和终止条件约束反馈迭代。
5. [Router 与模型驱动分发](/patterns/agt-p-05)：以集中路由选择有限专家、模型或流程。
6. [Supervisor、Handoff 与 Agents-as-Tools](/patterns/agt-p-06)：比较监督、移交与专家调用如何分配控制权和最终回答责任。
7. [Orchestrator–Workers 与 Fan-out/Fan-in](/patterns/agt-p-07)：明确子任务拆分、并发执行、结果收敛与冲突处理。
8. [Durable Agent 与 Human-in-the-loop](/patterns/agt-p-08)：为跨进程任务加入持久恢复、人工审批和取消边界。

A2A 连接独立 Agent 运行时之间的任务协作，MCP 连接宿主与工具、资源或数据上下文；它们解决的是互操作接口，不自动保证控制权归属、治理、失败恢复或生产安全。协议是否可用，不能替代对下面控制模式及运行边界的逐项设计。

## 智能体（Agent）控制与协作模式

### 路由器（Router）

控制模型：一个路由器根据输入选择单个专家或流程，决策集中，执行通常不回到路由器循环。相关案例：[智能体框架软件开发工具包（Software Development Kit，SDK）](/cases/openai-agents-sdk)。

### 监督者（Supervisor）

控制模型：多智能体管理者（Manager）反复分派任务、接收结果并决定下一步，工作智能体不拥有全局流程。相关案例：[图式智能体编排框架监督者](/cases/langgraph-supervisor)。

### 智能体作为工具（Agents as Tools）

控制模型：主智能体把专业智能体当作工具调用；调用结束后控制权和最终回答责任仍在主智能体。相关案例：[智能体框架 SDK](/cases/openai-agents-sdk)。

### 移交（Handoff）

控制模型：当前智能体把会话和后续决策权移交给另一个智能体，控制中心随任务阶段变化。相关案例：[智能体框架 SDK](/cases/openai-agents-sdk)。

### 扇出与扇入（Fan-out/Fan-in）

控制模型：编排者并行发出独立子任务，再汇总、去重或解决冲突；分发和收敛点仍由编排层控制。相关案例：[微软多智能体参考架构](/cases/microsoft-multi-agent-reference-architecture)。

### 评估者—优化者（Evaluator-Optimizer）

控制模型：生成者产出候选，评估者按明确标准反馈，循环由终止条件或预算约束控制。相关案例：[图式智能体编排框架监督者](/cases/langgraph-supervisor)。

### 分层团队（Hierarchical Teams）

控制模型：顶层协调者把目标交给子团队管理者，子团队再控制本地工作智能体；控制权分层而非完全扁平。相关案例：[谷歌智能体开发套件智能体协作案例](/cases/google-adk-a2a)。

### 智能体间协议（Agent2Agent Protocol，A2A）

控制模型：一个智能体通过可发现的能力和任务协议与另一个独立智能体协作，双方保留各自运行时与内部实现。相关案例：[谷歌智能体开发套件与 A2A](/cases/google-adk-a2a)。

### 模型上下文协议（Model Context Protocol，MCP）

控制模型：智能体或宿主通过标准接口访问工具、资源和数据上下文，工具端不因此成为对等智能体。相关案例：[智能体框架 SDK](/cases/openai-agents-sdk)。

A2A 处理的是智能体之间的任务协作与互操作；MCP 处理的是智能体到工具或数据的能力和上下文接入。两者可以组合，但不能因为都使用协议就视为同一种控制关系。
