# 持久智能体与人工介入：恢复控制状态，不臆测外部真相

长时智能体会跨进程、跨部署、跨凭证有效期，也可能停下来等人决定。真正困难的不是把一段对话保存下来，而是恢复后知道：哪一步已经提交、哪项授权仍有效、外部动作是否发生、谁有权继续，以及什么条件必须安全停止。

本文把**持久控制状态**与**外部业务真相**严格分开。前者由运行框架持久化，描述智能体应从哪里继续；后者只能由权威业务系统回答，描述钱、工单、部署、账号或设备究竟处于什么状态。检查点不是业务数据库的副本，重放也不能把未知副作用变成已知成功。

## 学习问题

- 哪些状态属于持久控制状态，哪些事实必须从外部权威系统回读？
- 检查点应在何时提交，确定性重放的边界在哪里？
- 等待人工批准时要冻结哪些上下文，怎样处理拒绝、超时、取消和凭证过期？
- 恢复时如何使用稳定 `operation_id`、检查点模式与版本避免重复副作用？
- 代码或模型版本漂移、未知外部效果和无法自动收敛时，谁负责终止与人工接管？

## 问题与适用上下文

本模式适合执行时间超过单进程寿命、会等待外部事件或人工决定、并且需要在崩溃后继续的任务，例如长时编码、变更审批、生产事件响应和跨系统业务处理。它也适合短任务中的高风险动作：即使模型推理只需数秒，批准等待和外部结果确认仍可能跨数小时。

持久化目标是**恢复控制决定**，不是恢复模型的主观记忆。控制存储保存运行身份、当前状态、检查点引用、预算、等待条件、批准记录和终止原因；外部业务系统保存真正的对象状态。控制器恢复时先读取两者，再决定继续、对账、失败或进入人工终态。若流程可由已知步骤和规则表达，确定性工作流（Workflow）仍是首选；模型只负责不能预先编码的有界判断。

## 约束与驱动力

采用持久执行前固定以下合同：

1. **稳定运行与操作身份：** `run_id` 标识一次业务运行；每个可能产生副作用的意图在第一次尝试前获得稳定 `operation_id`。重试（Retry）、恢复和人工批准沿用同一操作标识，不能通过改写提示生成新身份绕过去重或预算。
2. **版本化检查点：** 每个检查点记录 `checkpoint_schema`、`checkpoint_version`、代码版本、模型与提示版本、输入摘要、已消费事件位置、预算、下一状态和外部操作引用。模式版本回答如何解码，检查点版本回答它在同一运行中的提交顺序。
3. **明确提交时机：** 在产生外部副作用之前提交意图与 `operation_id`；在收到工具结果后提交原始回执引用；在权威回读后才提交已确认结果。不能只在“步骤完成”时保存一张混合快照。
4. **确定性重放边界：** 重放只重建纯控制决定、事件消费和可重复计算。模型采样、当前时间、随机数、网络读取、凭证获取和工具调用都在边界之外，必须记录结果或通过受控活动重新执行；外部写入绝不因重放隐式发生。
5. **冻结批准上下文：** 批准请求包含主体、租户、目标资源、规范化动作、参数摘要、风险、理由、证据、`operation_id`、策略版本、截止时间与可见差异。批准的是这份不可变上下文，不是“继续”两个字。
6. **批准不是永久凭证：** 恢复执行前重新检查身份、权限、租户、资源版本、凭证有效期和策略。批准仍有效但凭证已经过期时，运行进入 `paused`，重新获取最小权限凭证；不能把旧令牌写进检查点，也不能把审批决定等同于当前授权。
7. **有界等待：** 每个 `waiting` 或 `approval required` 状态都有截止时间、提醒策略和超时去向。超时默认不批准；它进入失败、取消或 `manual terminal`，不能静默恢复到执行。
8. **幂等恢复：** `resuming` 先取得运行租约，按检查点版本做比较并交换，验证尚未取消，再查询 `operation_id` 的权威结果。只有确认未发生且动作可安全重试时才再次调用工具。
9. **取消优先：** 取消是耐久控制事件。控制器停止新动作、撤销可撤销的等待和沙箱任务、记录取消意图，并对已经发出的不可撤销动作继续对账；取消完成不能掩盖一个仍未知的外部效果。
10. **人工可收敛：** 拒绝、高风险版本漂移、持续失败、授权冲突或未知副作用必须能进入 `manual terminal`。该终态不可由自动重试重新打开，只能由新运行或带新授权和新操作身份的显式补救流程处理。

驱动力是降低长时运行中的丢失进度、重复副作用和无人负责风险。代价是更多持久存储、迁移、租约、对账、审批运营与隐私（Privacy）治理责任。

## 结构与协作关系

| 架构平面 | 责任所有者 | 显式合同 |
| --- | --- | --- |
| 控制 | 确定性运行控制器 | 解释事件、执行状态转换、检查预算与取消、选择继续/失败/人工终止；模型只能提出下一步 |
| 状态 | 耐久控制存储与检查点存储 | 保存状态机、运行租约、版本、等待条件、批准记录和外部操作引用；不宣称保存外部业务真相 |
| 上下文 | 上下文装配器 | 从版本化输入、检查点和权威回读重建最小上下文；不把完整对话当作提交日志 |
| 批准 | 批准服务、策略引擎与具名批准者 | 冻结批准上下文，验证批准者权限，记录同意、拒绝、过期与撤销 |
| 动作 | 沙箱、工具适配器与副作用所有者 | 以最小权限和稳定 `operation_id` 执行动作，返回结构化回执，不自行宣告业务完成 |
| 真相 | 外部权威系统 | 对资源版本、操作结果和业务终态给出权威读取；其状态不能由检查点覆盖 |
| 恢复 | 结果对账器与操作员 | 查询未知效果、处理冲突与补偿；无法自动确定时把运行送入人工终态 |
| 治理与评测 | 安全、合规与质量所有者 | 审查权限、保留期、重放漂移、批准质量、恢复时延、重复动作和错误终止 |

控制所有者负责唯一状态转换，状态所有者负责提交可恢复记录，副作用所有者负责外部动作及其幂等/补偿语义，终止责任属于确定性控制器与具名人工责任人。模型、批准服务和工具都不能各自写一个相互矛盾的终态。

颜色只帮助分组；实线/虚线、箭头方向、节点名称和两个有边框的责任区域共同表达语义。正常路径先把 `running` 的下一意图和 `operation_id` 提交到控制存储，再写入检查点。需要人决定时先进入 `approval required`，持久化冻结的批准上下文，然后进入 `waiting`；运行进程可以释放资源。

收到同意事件后，控制器不直接调用工具。批准记录先从 `approval required` 进入 `waiting`；有效决定到达后，控制器可以进入 `paused` 完成凭证或迁移准备，再进入 `resuming`，也可以在无需额外准备时从 `waiting` 直接进入 `resuming`。它校验事件只消费一次，检查批准未撤销、截止时间未过、输入和资源版本仍匹配，重新取得短期凭证，再以同一 `operation_id` 调用受限沙箱或工具。取消进入 `cancelled` 控制终态；拒绝、等待超时或未知效果沿虚线分支进入 `manual terminal`，不会走自动恢复分支。

工具返回成功并不立即产生 `completed`。结果对账器用 `operation_id`、资源标识和回执查询权威系统；确认外部业务真相后才提交完成。若崩溃发生在调用与回执提交之间，恢复路径先对账：已发生就记录结果，明确未发生且可重试才重发，不确定就进入人工终态。虚线恢复分支只恢复控制，不倒带外部世界。

## 失败模式与误用

**把聊天记录当检查点。** 对话没有稳定模式、提交边界或外部操作身份。应把它作为可裁剪的上下文证据，控制状态另存为可验证结构。

**检查点与业务真相混在一起。** 控制记录写着“部署完成”，权威部署系统却仍在执行。恢复时先从权威系统读取，不允许检查点覆盖业务对象。

**跨副作用重放。** 恢复器重跑包含模型采样、当前时间或工具写入的节点，造成不同决定或重复动作。把非确定性结果记录为事件，把副作用隔离为带 `operation_id` 的活动。

**盲目升级代码或模型。** 新提示、新模型或新代码从旧检查点继续，状态解释和工具选择发生版本漂移。对兼容变更运行回放测试，对不兼容变更做迁移、版本固定或人工接管；不能把更强模型当兼容性证明。

**批准上下文漂移。** 人批准了测试环境的小范围命令，恢复后却对生产资源或新参数执行。批准绑定规范化意图、资源版本和截止时间；任何实质变化都需要新批准。

**持久化凭证。** 长期令牌随检查点保存，恢复时绕过轮换和撤销。检查点只保存凭证引用与所需权限，执行前重新颁发短期凭证并重新授权。

**等待没有超时。** 运行永久占用运营注意力，责任人已离职仍可迟到批准。等待合同必须有截止、升级和安全终止；过期决定只进审计。

**恢复即重试。** 崩溃点位于外部写入之后、回执提交之前，直接重试会重复扣款或部署。先做未知副作用对账；没有查询、去重或补偿能力时转人工。

**取消只改控制状态。** 沙箱和外部动作继续运行，控制台却显示已取消。取消要传播到活动工作，且继续追踪不可撤销动作直至权威结果确定。

**人工终态被自动重开。** 定时恢复扫描把拒绝或未知效果重新送回运行。`manual terminal` 没有自动出边；补救使用新运行和清晰授权，保留原审计链。

## 质量属性（Quality Attribute）权衡

持久控制状态提高可恢复性、可审计性与长时可操作性；批准和最小权限降低高风险副作用，但增加等待时延与人工负担。细粒度检查点减少重做，却增加存储、写放大、模式迁移和敏感上下文保留面；粗粒度检查点成本低，却扩大恢复后需要对账的窗口。

确定性重放增强可测试性，但会限制可在重放区内使用的应用程序编程接口（Application Programming Interface，API）。模型版本固定降低漂移，却推迟质量或安全修复；快速升级提高能力，却需要影子回放、兼容迁移和更严格人工门。沙箱降低直接损害，但不能证明外部授权、业务幂等或最终结果正确。

至少度量检查点提交延迟与失败率、恢复时延、旧租约拒绝、事件重复抑制、批准等待分布、拒绝/超时/撤销、凭证重新颁发失败、版本迁移结果、未知效果比例、对账时延、重复外部动作、人工终态积压和错误完成。只报告“崩溃后继续了”不能证明业务正确性。

## 实现与迁移提示

从没有副作用的长时任务开始。第一阶段只建立 `run_id`、状态机、租约、事件收件箱、`checkpoint_schema`、`checkpoint_version` 和恢复演练；故障注入验证任意检查点后重启都不会跳步或重复消费事件。第二阶段给只读工具加结构化回执和超时，再加入人工批准，先演练同意、拒绝、撤销、迟到决定与批准者权限变化。

第三阶段才接入写操作：在动作前持久化 `operation_id`，要求适配器支持幂等查询或权威回读，注入“外部成功但本地超时”“凭证过期”“取消与回执竞态”等故障。上线代码或模型新版本前，用脱敏历史做影子重放，对比状态转换、工具意图与终止；不兼容检查点必须有显式迁移或保持旧工作者处理。

图编排框架（LangGraph）的持久化文档描述检查点器（Checkpointer）保存线程图状态快照；其中断文档描述保存状态、用相同线程标识恢复，并提示恢复会从含中断的节点开头重新运行，因此中断前副作用应具备幂等性。这些是所记录版本的框架行为，不证明外部写入恰好一次、状态迁移正确或授权持续有效。

Temporal 工作流平台的工作流与事件历史文档描述以历史重建工作流状态和重放工作流代码的机制，可帮助理解确定性边界；它不把模型调用变成确定函数，也不替智能体解决批准语义、凭证轮换或业务对账。OpenAI 公司智能体开发工具包在固定提交的人机协作文档展示工具批准、中断状态和恢复接口的实现形态；这个协议/工具示例不能证明授权、可靠性或治理，更不能证明外部副作用安全。

确定性回退分三档：关闭模型选步但保留耐久工作流；把高风险工具改为生成候选、由人手动执行；若对账和迁移合同尚不可靠，则停止自动恢复，输出检查点、未决操作和权威查询清单给操作员。回退保留同一运行身份和审计链，不靠清空状态“重新开始”。

## 说明性场景

生产事件响应智能体准备回滚服务。控制器创建 `operation_id=rollback:incident-483:service-a:v7`，在 `running` 中保存目标版本、证据摘要和回滚意图，然后进入 `approval required`。值班负责人看到当前生产版本、目标版本、影响范围、验证查询和 20 分钟截止时间后批准。十分钟后工作者重启，旧凭证已经过期；系统进入 `paused`，重新颁发只允许该服务回滚的短期凭证，再进入 `resuming`。

沙箱向部署系统提交回滚后连接中断，本地没有回执。控制器没有重发，而是进入结果对账：部署系统按 `operation_id` 返回“已接受，仍在进行”。运行回到 `waiting`，收到完成事件后再次权威回读，确认服务版本与健康检查，再写 `completed`。若部署系统既不能按操作标识查询、也无法从资源版本判断是否发生，运行进入 `manual terminal`；操作员获得检查点、批准记录、请求摘要和查询清单，自动路径不再重开。

同一场景中的拒绝沿独立分支立即进入人工终态；超时也不等同于批准。若批准后目标版本改变，原批准上下文失效，系统创建新意图并重新批准，而不是把旧决定套在新动作上。
