# 架构图审阅清单

一张图可以整齐、完整，却仍让评审者对系统内外、数据权威和故障传播作出错误判断。本文提供四道顺序执行的审阅门，把“看懂图”转成九项可记录、可分派、可复查的发现；[建模目录](/modeling)提供其他模型入口。

本文以 [MOD-02 C4 Context 与 Container](/modeling/mod-02)的费用申报系统为权威输入，使用故意含缺陷的问题图做说明性演练。图、表和中文方法是教学综合，不是生产盘点，也不把外部资料扩张为对本站方法的背书。

## 学习问题

- 如何判断标题、范围、图例和版本足以让未参与绘图的人独立理解？
- 如何发现抽象层级混用、系统内外错置以及数据关系缺少权威依据？
- 如何区分已有协议证据与猜测，并把信任边界、失败边界保留为候选？
- 如何用发现台账、修正图和独立复述完成逐项复查？

## 审阅目标与输入

审阅目标不是把图改得更漂亮，而是判断它能否支撑当前评审问题，并让未知项继续可见。开始前收集原始文件、目标受众、待作决策、图类型、抽象层级、场景、环境，以及代码、接口、数据、部署、运行、安全、故障和决策证据；证据不足时形成“待澄清”，不能自行补全。

元素名称和系统边界沿用 MOD-02：员工在边界外，Web 应用、申报 API、申报数据库和支付任务执行器位于费用申报系统内，银行支付服务是外部系统。[MOD-01 建模总览](/modeling/mod-01)帮助先选问题与视图，[MOD-03](/modeling/mod-03)区分 Component、Dynamic 和 Deployment，[MOD-04](/modeling/mod-04)承接文档事实分类与版本记录。

## 四道审阅门

四道门按身份与范围、表示与边界、运行与交换、风险与隔离依次执行。每个检查项都必须回答问题、指出所需证据、识别失败信号，并明确它不能证明什么。

| 表示与边界 | 边界 | 系统内外、外部参与者和当前抽象层级如何分开 | MOD-02 权威系统边界与元素类型 | 银行支付服务位于费用申报系统内部 | 系统边界不等于信任、部署、网络或组织边界 |
| 运行与交换 | 数据 | 交换什么业务事实，方向、权威和消费责任是什么 | 接口、数据、业务权威或可核验案例 | 只有“使用”或无标签箭头 | 数据关系不等于所有权、一致性、事务或顺序 |
| 运行与交换 | 协议 | 哪些协议、通道或同步异步语义已有证据 | 接口契约、配置、运行或部署事实 | “同步/事件？”既暗示实现又没有依据 | 协议标签不证明实现、兼容性或运行健康 |

| 风险与隔离 | 失败域 | 外部依赖、故障传播和候选失败边界在哪里 | 部署、依赖、故障、恢复与演练记录 | 本地执行器和银行被画成一个已隔离失败域 | 外部系统不自动证明故障隔离或切换 |

</div>

矩阵是一组提问顺序，不是合规打勾表。前一道门发现范围或边界错误时，应先修复观察单位，再继续判断关系和风险；后一道门不能抵消前一道门的阻断发现。

## 完成判断

九项检查都有明确结论，每条发现都有图中证据、风险、修复建议、责任类型和复查状态，才可以进入关闭判断。所有阻断项必须关闭，否则明确拒绝发布；待澄清项必须保持未知，不能被改写成具体协议、安全机制或可靠性事实。

阻断的错误表示在被删除，或改为明确标注的候选/未知时即可关闭；这只关闭错误表示。认证、授权、部署、故障隔离、故障切换和恢复证据仍然未知，不得自行补全。

未参与修图的人应能复述图类型、范围、系统内外、数据关系和非证明项，并能从修正图回到每条发现。两组 Draw.io 与 SVG 还需保持可见语义同步，并在桌面和移动端验证局部滚动与可读性；资产验证由后续发布任务完成。

## 常见失败

标题完整不等于图中事实正确。

图例完整不等于所有抽象层级可以混用。

系统边界不等于信任边界、网络边界、部署边界或组织边界。

数据关系不等于数据所有权、一致性、事务或运行顺序。

协议标签不证明实现、配置、兼容性或运行健康。

Container、Context、数据库或团队不存在自动一一映射。

外部系统不自动构成独立失败域或完成故障隔离。

版本块不证明图与当前代码、部署或运行状态一致。

审阅清单不替代威胁建模、可靠性演练、代码检查、部署盘点或生产观测。

另一种常见失败是把发现合并成一个总 PASS。九项中的任何一项都可能拥有不同证据、责任类型和复查状态，因此必须逐项关闭、保留或退回。

## 与其他模型的衔接

[MOD-11 Context Map](/modeling/mod-11)可以提供候选业务边界和交换事实，但候选 Context 不能直接重命名为 Container，也不能推出协议或调用顺序。[QA-02 可靠性、可用性与可恢复性](/quality-attributes/qa-02)要求用运行、部署、故障和恢复证据验证失败边界；图上的隔离形状本身不证明故障隔离。

[QA-05 安全、隐私与信任](/quality-attributes/qa-05)要求补充数据分类、身份、权限、威胁与控制证据；系统边界不能代替信任边界判断。同一方法也可用于 [Microsoft multi-agent reference architecture 案例](/cases/microsoft-multi-agent-reference-architecture)，但必须采用该案例自己的权威名称和边界。

MOD-13 是下一步模型同步、版本与漂移治理方向。在它发布前，本文只保留普通文字交接，不建立可操作链接或邻接关系。

## 完整演练

说明性演练从含缺陷图开始，不能先看修正答案。审阅者把观察写入台账，再由另一位未参与修图的人做独立复述，防止作者用口头背景填补图中缺口。

1. 只看问题图，用一句话复述它声称回答的问题，并记录无法复述的部分。
2. 执行身份与范围门，检查标题、范围和版本。
3. 执行表示与边界门，检查图例和系统内外边界。
4. 执行运行与交换门，检查数据事实、方向、权威和协议依据。
5. 执行风险与隔离门，检查信任域、失败域和未知项。
6. 将九条发现写入台账，分配严重度、责任类型和复查状态，再制作修正图。
7. 由未参与修图的人重新复述，逐项关闭、保留或退回发现，并确认没有引入新事实。

这套练习的终点不是“图已美化”，而是每一项判断都有可追溯证据，剩余未知没有被伪装成事实。四道门、九项矩阵、严重度、问题图、修正图、两张表、七步演练和中文表述均为本站原创综合。
