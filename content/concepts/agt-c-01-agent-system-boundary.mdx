# AI Agent 系统边界

一个应用调用了大语言模型、接上检索和工具，还不足以说明它是 Agent。架构判断的关键不是界面是否像聊天，而是谁选择下一步、谁约束它、任务事实放在哪里，以及失败后谁停止和恢复。

## 学习问题

- Model、Augmented LLM、Workflow 与 Agent 的控制权如何划分？
- Agent Harness 与 Agent Loop 分别拥有什么，为什么 Harness 必须包住并约束 Loop？
- 什么信号表明应继续增加自治，什么信号要求退回确定性 Workflow？

## 定义与尺度边界

本文在“一次用户目标如何被推进”的系统尺度上区分四类边界。同一个产品可以在不同路径上落在不同位置，因此这是控制权的分析框架，不是产品命名法。

| 边界 | 候选能力 | 下一步由谁决定 | 不自动证明 |
| --- | --- | --- | --- |
| Model | 根据输入生成文本、结构或工具调用候选 | 调用者代码 | 拥有任务状态、终止权或业务真相 |
| Augmented LLM | 在模型调用上增加检索、工具或记忆 | 可以是代码，也可以让模型选一次能力 | 存在多步循环或自主恢复 |
| Workflow | 组合多步模型与工具调用 | 代码预定步骤、分支和大部分终止条件 | 模型拥有整条任务的控制权 |
| Agent | 在环境反馈中计划、行动、观察、评估并停止 | 模型在 Harness 设定的边界内选择下一步 | 无限权限、无限预算或无需人工责任人 |

因而：**Model 生成候选输出，不拥有任务控制权**；**Augmented LLM 增加检索、工具或记忆能力，但不必拥有循环**；**Workflow 的步骤和分支主要由代码预先定义**；**Agent 让模型在受约束边界内选择下一步动作**。**自治程度是连续谱，不是四个互斥产品类别**。

图中 Agent Harness 持有运行时和约束责任：它接收 User / Event，执行 Policy & Routing、预算与终止、人工批准，装配上下文，暴露经权限限定的工具，并为恢复与评测留下挂钩。Agent Loop 是被包住的任务推进机制：Plan → Act → Observe → Evaluate → Terminate。Loop 可以调用 Knowledge / Retrieval、Tools / Sandbox 或 Human / Other Agents，但不能越过 Harness 获得更多权限、预算或时间。

State、Memory、Checkpoint 与 Trace / Evaluation / Guardrail 是跨切底座，不是模型隐藏“记住”的一团数据。模型输出不能在未经外部验证时成为权威业务状态。State 保存当前任务事实，Memory 保存允许跨任务复用的偏好或摘要，Checkpoint 保存可恢复执行位置，Trace 记录发生了什么，Evaluation 判断质量，Guardrail 执行约束。

| 架构平面 | 主要所有者 | 必须显式化的合同 |
| --- | --- | --- |
| 交互 | Harness 与人类责任人 | 目标、追问、人工批准和最终接受者 |
| 控制 | Harness 设边界，Loop 选边界内动作 | 步数、时间、费用、成功、失败、人工中止和预算耗尽条件 |
| 知识与上下文 | Harness 装配，Loop 申请 | 来源、时效、证据充分性与上下文限额 |
| 状态与记忆 | 显式状态底座 | 任务真相、跨轮偏好、恢复点和写入权限分离 |
| 动作与工具 | Harness 的工具网关与沙箱 | 只读/写入分类、参数校验、幂等身份、结果验证和补偿 |
| 治理与评测 | Harness 与人类责任人 | 追踪、评测、护栏、审批、升级和停止自动化 |

正常路径是：Harness 验证目标与策略，创建任务 State 和预算；Loop 选择一次可允许动作；Harness 执行、记录并返回环境结果；Loop 重新评估，直到成功、明确失败、预算耗尽或人工中止。长时执行在可重放边界写入 Checkpoint，恢复时先核对已发生副作用，不盲目重试。

确定性降级是必要的运行合同：当任务步骤可稳定枚举、分支可由规则表达、副作用风险超过当前护栏，或评测无法证明模型选步带来净收益时，停止 Loop，保留只读建议，把执行切换为预定步骤、显式分支和人工批准的 Workflow。

## 常见混淆

有工具不等于有 Agent。代码可以根据固定规则选择工具，模型也可以只做一次工具选择；它们都可以是 Augmented LLM 或 Workflow。有循环也不等于自治：固定次数的重试、轮询或 evaluator–optimizer 可以完全由代码控制。

Harness 不是“调用模型的一个 SDK 包装”。如果它不拥有上下文限额、工具协议、权限、沙箱、预算、终止、恢复和评测挂钩，它就没有形成可审查的 Agent 系统边界。Loop 也不拥有这些责任；它只在被允许的选项中推进任务。

Agentic RAG 不是与 Harness 和 Loop 并列的底层构件。它是 Agent Loop 的一种具象：Loop 围绕“证据是否充分”选择检索、阅读、反思、改写查询、再次检索、回答或拒答；Harness 仍然约束来源、预算、权限、状态和追踪。

## 说明性场景

考虑一个希望“找出部署失败原因，必要时回滚”的请求。Model 可以根据已给日志生成候选假设；Augmented LLM 可以额外查询指标或运行手册；Workflow 可以按“收集—比较—报告”的固定顺序执行。只有当模型在多轮环境反馈中选择下一个假设、查询或验证动作时，这条路径才具有 Agent Loop。

Harness 先将诊断限定为只读，设置查询时间窗、最大步数和费用，并持久化每次工具结果。当 Loop 提议回滚时，写操作必须经过人工批准、幂等身份和执行后验证。若无法确定安全回滚目标、评测未达阈值、超出预算或违反只读策略，Harness 终止自动化，保留 Checkpoint 与 Trace，将责任交还人类值班者。

这个场景只说明责任分配，不证明任何框架、模型或部署已实现上述安全性。用实现证据检查类似边界时，可对照 [OpenAI Agents SDK 案例](/cases/openai-agents-sdk)的运行与工具机制，以及 [Kubernetes 调和循环案例](/cases/kubernetes-reconciliation-loop)中的期望状态、观察、重试与停止边界；二者都不能被外推为所有 Agent 系统的通用保证。
