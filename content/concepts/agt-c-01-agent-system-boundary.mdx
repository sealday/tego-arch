# AI 智能体系统边界

一个应用调用了大语言模型、接上检索和工具，还不足以说明它是智能体。架构判断的关键不是界面是否像聊天，而是谁选择下一步、谁约束它、任务事实放在哪里，以及失败后谁停止和恢复。

## 学习问题

- 模型、增强型大语言模型、工作流与智能体的控制权如何划分？
- 智能体运行框架与智能体循环分别拥有什么，为什么前者必须包住并约束后者？
- 什么信号表明应继续增加自治，什么信号要求退回确定性工作流？

## 定义与尺度边界

本文在“一次用户目标如何被推进”的系统尺度上区分四类边界。同一个产品可以在不同路径上落在不同位置，因此这是控制权的分析框架，不是产品命名法。

| 边界 | 候选能力 | 下一步由谁决定 | 不自动证明 |
| --- | --- | --- | --- |
| 模型 | 根据输入生成文本、结构或工具调用候选 | 调用者代码 | 拥有任务状态、终止权或业务真相 |
| 增强型大语言模型 | 在模型调用上增加检索、工具或记忆 | 可以是代码，也可以让模型选一次能力 | 存在多步循环或自主恢复 |
| 工作流 | 组合多步模型与工具调用 | 代码预定步骤、分支和大部分终止条件 | 模型拥有整条任务的控制权 |
| 智能体 | 在环境反馈中计划、行动、观察、评估并停止 | 模型在智能体运行框架设定的边界内选择下一步 | 无限权限、无限预算或无需人工责任人 |

因而：**模型生成候选输出，不拥有任务控制权**；**增强型大语言模型增加检索、工具或记忆能力，但不必拥有循环**；**工作流的步骤和分支主要由代码预先定义**；**智能体让模型在受约束边界内选择下一步动作**。**自治程度是连续谱，不是四个互斥产品类别**。

图中智能体运行框架持有运行时和约束责任：它接收用户或事件，执行策略与路由、预算与终止、人工批准，装配上下文，暴露经权限限定的工具，并为恢复与评测留下挂钩。智能体循环是被包住的任务推进机制：计划 → 行动 → 观察 → 评估 → 终止。它可以调用知识与检索、工具与隔离沙箱（Sandbox），或人类与其他智能体，但不能越过智能体运行框架获得更多权限、预算或时间。

状态、记忆、执行检查点（Checkpoint）与追踪、评测、护栏（guardrail）是跨切底座，不是模型隐藏“记住”的一团数据。模型输出不能在未经外部验证时成为权威业务状态。状态保存当前任务事实，记忆保存允许跨任务复用的偏好或摘要，检查点保存可恢复执行位置，追踪记录发生了什么，评测判断质量，护栏执行约束。

| 架构平面 | 主要所有者 | 必须显式化的合同 |
| --- | --- | --- |
| 交互 | 智能体运行框架与人类责任人 | 目标、追问、人工批准和最终接受者 |
| 控制 | 智能体运行框架设边界，智能体循环选边界内动作 | 步数、时间、费用、成功、失败、人工中止和预算耗尽条件 |
| 知识与上下文 | 智能体运行框架装配，智能体循环申请 | 来源、时效、证据充分性与上下文限额 |
| 状态与记忆 | 显式状态底座 | 任务真相、跨轮偏好、恢复点和写入权限分离 |
| 动作与工具 | 智能体运行框架的工具网关与沙箱 | 只读/写入分类、参数校验、幂等身份、结果验证和补偿 |
| 治理与评测 | 智能体运行框架与人类责任人 | 追踪、评测、护栏、审批、升级和停止自动化 |

正常路径是：智能体运行框架验证目标与策略，创建任务状态和预算；智能体循环选择一次可允许动作；智能体运行框架执行、记录并返回环境结果；智能体循环重新评估，直到成功、明确失败、预算耗尽或人工中止。长时执行在可重放边界写入检查点，恢复时先核对已发生副作用，不盲目重试（Retry）。

确定性降级是必要的运行合同：当任务步骤可稳定枚举、分支可由规则表达、副作用风险超过当前护栏，或评测无法证明模型选步带来净收益时，停止智能体循环，保留只读建议，把执行切换为预定步骤、显式分支和人工批准的工作流。

## 常见混淆

有工具不等于有智能体。代码可以根据固定规则选择工具，模型也可以只做一次工具选择；它们都可以是增强型大语言模型或工作流。有循环也不等于自治：固定次数的重试、轮询或“评测者—优化者”流程可以完全由代码控制。

智能体运行框架不是“调用模型的一个软件开发工具包（Software Development Kit，SDK）包装”。如果它不拥有上下文限额、工具协议、权限、沙箱、预算、终止、恢复和评测挂钩，它就没有形成可审查的智能体系统边界。智能体循环也不拥有这些责任；它只在被允许的选项中推进任务。

智能体检索增强生成（Agentic RAG）不是与智能体运行框架和智能体循环并列的底层构件。它是智能体循环的一种具象：循环围绕“证据是否充分”选择检索、阅读、反思、改写查询、再次检索、回答或拒答；智能体运行框架仍然约束来源、预算、权限、状态和追踪。

## 说明性场景

考虑一个希望“找出部署失败原因，必要时回滚”的请求。模型可以根据已给日志生成候选假设；增强型大语言模型可以额外查询指标或运行手册；工作流可以按“收集—比较—报告”的固定顺序执行。只有当模型在多轮环境反馈中选择下一个假设、查询或验证动作时，这条路径才具有智能体循环。

智能体运行框架先将诊断限定为只读，设置查询时间窗、最大步数和费用，并持久化每次工具结果。当智能体循环提议回滚时，写操作必须经过人工批准、幂等身份和执行后验证。若无法确定安全回滚目标、评测未达阈值、超出预算或违反只读策略，智能体运行框架终止自动化，保留检查点与追踪，将责任交还人类值班者。

这个场景只说明责任分配，不证明任何框架、模型或部署已实现上述安全性（Security）。用实现证据检查类似边界时，可对照 [OpenAI Agents SDK 智能体开发工具包案例](/cases/openai-agents-sdk)的运行与工具机制，以及 [Kubernetes 容器编排系统调和循环案例](/cases/kubernetes-reconciliation-loop)中的期望状态、观察、重试与停止边界；二者都不能被外推为所有智能体系统的通用保证。
