# Microkernel / Plug-in Architecture：让扩展能力可替换，也让风险止步于边界

从[架构风格目录](/styles)可以返回同类主题入口。

稳定宿主与受控扩展之间的冲突，决定了 Microkernel / Plug-in Architecture 是否成立。插件可以替换能力，但不能顺势取得订单状态、提交或补偿的所有权。扩展性来自宿主拥有的窄扩展点，不来自把内部函数全部开放。

进程外执行只提供进程故障边界，不自动形成安全沙箱。身份、来源、网络、文件、凭证和资源仍要分别约束；插件声明需求不决定授权，声明也不能绕过控制面的门禁。

本文用本站原创的订单平台场景解释这条边界：稳定订单宿主通过受控网关调用税费、支付、库存和通知插件，控制面治理身份、兼容、权限与激活。外部来源只支持插件关系、生命周期、版本范围、子进程远程过程调用和扩展宿主机制，不证明本场景的生产效果。

## 学习问题

- 宿主、控制面、调用网关和插件分别拥有哪部分控制权？
- 插件清单怎样经过身份、兼容、能力、权限和资源门禁？
- 一次订单调用经过哪些状态与交接，业务真相留在哪里？
- 超时、签名异常、崩溃风暴和结果未知分别由谁停止？
- 何时从模块内策略升级为进程外插件，何时应停止？

## 一页摘要

Microkernel（微内核）保留稳定业务政策和权威状态，Plug-in Architecture（插件架构）把已证实的变化放进宿主拥有的扩展点。控制面决定哪个制品可激活，执行面限制一次调用；插件只实现被批准的能力，不能自行扩大范围。

这不是“核心越小越好”。核心必须保留订单流程、不变量、提交、结果查询和补偿决定；扩展面则承担版本、发现、供应链、隔离和运营成本。

| 判断面 | 宿主必须保留 | 插件可以变化 | 不可外推 |
| --- | --- | --- | --- |
| 业务 | 订单状态机、提交、补偿策略 | 税费、支付适配、库存适配、通知通道 | 插件不拥有业务终态 |
| 治理 | 身份、兼容、权限、激活绑定 | 清单中声明能力与需求 | 声明只是待审需求 |
| 运行 | 期限、幂等、结果校验、停止条件 | 一个批准能力的实现 | 进程边界不等于沙箱 |

因此，先判断扩展点是否稳定且值得独立交付，再判断隔离与治理成本是否可承担；顺序反过来，平台会先拥有复杂性，后寻找用途。

## 事实边界

**已证实事实：** `Eclipse` 的历史文章说明核心插件、宿主插件、扩展者、清单、注册表和扩展点之间的声明关系。它支持“宿主提供槽位并控制回调”的机制，不支持本文的进程外、安全或订单业务结论。

`OSGi Core 7` 的生命周期层覆盖安装、启动、停止、更新、卸载、状态事件和细粒度权限；`OSGi` 版本方法区分导出方版本与使用方范围。两项证据帮助描述门禁与兼容承诺，但不要求采用 `OSGi`，也不证明业务语义兼容。

`HashiCorp` 的 `go-plugin` 固定提交支持子进程远程过程调用、协议版本、校验和或传输层安全协议（Transport Layer Security，TLS）选项。插件崩溃不会直接令宿主进程崩溃。它明确面向本地可靠网络；本文不会把该假设外推为远程网络保证，也不会把进程隔离写成完整安全边界。

`VS Code` 的固定文档源码说明扩展宿主可位于本地、网页或远端，装载位置受运行时、能力、安装位置与偏好影响，并支持惰性激活。它不证明每个扩展都有独立进程，也不支持本文订单平台的隔离保证。

税费插件只实现一个被批准的扩展能力；支付插件只实现一个被批准的扩展能力；库存插件只实现一个被批准的扩展能力；通知插件只实现一个被批准的扩展能力。它们不直连订单数据库，也不互相调用或组成隐藏业务流程。

**说明性场景（订单平台的一次调用）：**

{/* terminology-exempt: unknown-english-term | match: ID | record: 宿主生成最小数据投影，例如订单 ID、地区、应税项目和合同版本。 | reason: STY-10 已批准八步调用流固定使用订单 ID 字段文本 */}

{/* terminology-exempt: unknown-english-term | match: ID | record: 网关加入操作 ID、幂等键、期限、短期凭证和 ，再发起本地进程间 gRPC 调用。 | reason: STY-10 已批准八步调用流固定使用操作 ID 字段文本 */}

1. 订单宿主到达扩展点，宿主仍持有订单状态与业务期限。
2. 调用网关向控制面解析能力、批准绑定和兼容协议。
3. 宿主生成最小数据投影，例如订单 ID、地区、应税项目和合同版本。
4. 网关加入操作 ID、幂等键、期限、短期凭证和 `deadline`，再发起本地进程间 gRPC 调用。
5. 插件返回版本化结果或标准错误，不返回宿主内部对象引用。
6. 网关校验响应结构、大小、能力版本和错误分类。
7. 宿主根据业务失败策略决定提交、拒绝、查询权威结果或安排通知补偿。
8. 控制面只接收健康与策略信号，不接管订单状态机。

受控发布按验证 → 预热 → 灰度 → 排空 → 卸载推进。任何阶段失败都停止推进并恢复上一批准绑定；回滚不会撤销已发生的外部效果，结果未知先查询权威结果，不能盲目重放。

## 架构决策与权衡

第一项决策是把控制面与执行面分开。好处是身份、兼容、权限和发布可以在流量进入前完成；代价是注册表、签名、策略、合同测试和绑定状态都要持续运营。控制面故障时，既有批准绑定可按明确策略继续，新的绑定与权限扩张必须停止。

第二项决策是让宿主保留业务权威。插件崩溃或回滚时，订单仍能根据权威记录判断真实结果；代价是宿主要维护最小投影、结果映射与补偿政策。若插件必须共享宿主事务、任意内部对象或订单表写权限，这个扩展点就没有形成。

第三项决策是选择进程外远程过程调用，而不是把每个策略直接拆成服务。与[模块化单体](/styles/sty-04)相比，它新增序列化、进程、兼容与隔离成本；与[微服务](/styles/sty-05)相比，插件仍受宿主扩展点和业务流程控制，不拥有独立业务能力与私有权威数据。

[最小权限、安全默认值与纵深防御](/principles/pr-09)约束插件的身份、短期凭证、网络和资源范围；[开闭原则（Open/Closed Principle）与接口隔离原则（Interface Segregation Principle）](/principles/pr-12)要求扩展点来自真实变化。扩展点还要围绕消费者任务保持内聚。两项原则都不替代运行时失败治理。

税费、支付和库存决定订单能否继续，失败时保持关闭；通知可在订单提交后降级为有界异步工作。补偿队列不改变这一区别，发布回滚也不能假装外部效果从未发生。

隔离实例前要保存制品摘要、签名、绑定、错误和异常访问证据，并撤销短期凭证。进程重启不能替代来源复核；多次崩溃命中停止条件后，人工所有者必须决定隔离、回退或退役。

## 可迁移经验

### 可直接复用的机制

迁移应按以下顺序推进：

1. 收集真实变化和实现差异，不为假想需求预建扩展点；
2. 在宿主内提取一个业务含义明确、输入/输出有限的策略接口；
3. 固定业务所有权、错误语义、权限和消费者合同测试；
4. 引入清单、注册表和版本/能力解析，但仍保持同一制品；
{/* terminology-exempt: unknown-english-term | reason: 六步迁移内容契约要求保留进程外 RPC 插件的精确短语 */}
5. 独立交付或第三方风险成立时，再迁移为进程外 RPC 插件；
6. 建立签名、最小权限、配额、灰度、排空、回滚和人工处置后，才开放动态激活。

每一步都要保留回退点。若模块内接口尚不能稳定表达输入、输出和失败，进程边界只会把变化放大成协议与运营问题。

### 只能有限类比的部分

`OSGi` 的生命周期和版本范围可用于设计问题清单，不要求复制其模块系统。`go-plugin` 证明一种本地子进程远程过程调用实现，`VS Code` 证明一种扩展宿主选择；二者都不是通用插件市场、安全沙箱或远程服务治理模板。

进程外插件与微服务都面对序列化、超时、兼容、观测和发布成本，但控制权不同。微服务通常拥有业务能力与权威数据，本文插件仍由订单宿主决定何时调用、如何解释结果和何时停止。

[生产中的微前端案例](/cases/micro-frontends-single-spa)只能有限类比独立交付的扩展边界，不等同于进程隔离的后端插件。浏览器切片共享进程与文档对象模型，本文插件则通过宿主控制的进程间协议执行；两者都要治理版本与生命周期，但不能互换安全、状态或故障结论。

### 不应照搬的部分

只有一个稳定实现、没有独立交付需求，或扩展点语义仍频繁变化时，应保持直接实现。插件若需要共享宿主事务、写入任意内部表、与其他插件形成隐藏依赖，或每次升级仍锁步发布，也应停止拆分。

团队若不能维护签名与撤销、兼容矩阵、最小权限、资源配额、灰度、排空、结果查询和人工处置，就不能开放动态激活。低延迟预算无法承担进程间调用成本时，应退回进程内策略，而不是削弱失败与权限边界。

**个人分析：** 微内核的价值不在“可插拔”三个字，而在宿主能明确拒绝一个不可信、不兼容或不可运营的扩展，同时不丢失业务真相。拒绝条件说不清时，扩展面尚未准备好。
