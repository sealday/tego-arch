# Micro-Frontend：用独立交付证明运行时拆分

Micro-Frontend（微前端）首先是一项组织与发布决策：多个长期稳定的业务团队是否真的需要在同一产品中独立交付。把页面拆成多个仓库、混用框架或增加挂载点，都不能单独证明运行时拆分有价值。

本文从[架构风格目录](/styles)进入电商前台场景，用商品、购物车、结算和账户四个切片说明控制权、状态、发布和失败边界。它是框架中立的决策指南；single-spa 微前端框架只提供可核对的运行时组合与浏览器边界证据，不是本文的实施模板。

证据截至 2026-08-26。外部来源只支持微前端定义、single-spa 已记录的组合建议，以及浏览器标准中的模块解析、响应完整性、执行策略和长任务观测；完整清单、原子提升、后端权威状态与恢复流程均明确标为本站推断或原创分析。

## 学习问题

- 微前端解决的是哪一种跨团队发布压力，什么情况下模块化前端单体更合适？
- 共享应用外壳、业务切片、公共运行时、发布控制面和权威后端分别拥有什么？
- 购物车到结算怎样只传稳定标识，不把可变业务对象变成跨切片数据库？
- 不可变制品、版本化清单和兼容门禁怎样形成可审计的提升与回滚单位？
- 同页错误边界能限制哪些影响，哪些浏览器资源仍会跨切片传播故障？

## 一页摘要

微前端的采用门槛不是前端规模，而是至少两个稳定业务团队已经拥有清晰业务边界，并被统一发布列车持续阻塞。独立交付必须覆盖制品、流水线、观测、值班与回滚责任；若每次发布仍等待中央共享应用外壳修改，系统只是把前端单体改造成分布式前端单体。

若只有一个小团队、一个优先级和一个发布节奏，模块化前端单体通常拥有更低的组合、测试、安全和治理成本。

## 事实边界

**已证实事实：** 主要工程文章把微前端描述为可独立交付的前端应用组合，并强调围绕业务能力形成跨职能团队。它是独立分析，只支持定义、历史背景与比较，不证明本文电商场景、团队效率或生产结果。

**已证实事实：** single-spa 的概念页与推荐设置页支持浏览器运行时组合、应用公开入口、受控模块解析和选择性共享依赖等记录范围。它们说明一种可实现机制，不支持整份清单原子提升、组织自治、安全隔离、后端授权或应用兼容保证。

**已证实事实：** 网页标准只支持导入映射（Import Map）如何参与模块说明符解析，以及导入、作用域和完整性元数据的结构与处理。

**已证实事实：** 子资源完整性（Subresource Integrity，SRI）规范只支持用摘要元数据验证响应内容及失败处理。内容安全策略（Content Security Policy，CSP）只作为浏览器资源与执行策略的纵深防御。

**已证实事实：** 长任务接口只暴露超过规定阈值的任务和受限归因。四项标准均不证明微前端发布、团队责任或业务正确性。

**基于证据的推断：** 受控模块解析、内容身份验证和已记录的运行时组合能力，可以成为可审计发布链的一部分，但不能自动形成一个原子发布单位。完整版本化清单、候选组合门禁和整份回滚是本站在这些窄机制之上作出的架构推断。

**本站原创分析：** 商品、购物车、结算和账户的数据流，以及逐请求后端授权，都是说明性设计。订单不确定结果查询、人工终态与退出演练同样不代表任何来源的开箱能力或生产效果。

## 运行时组合与发布流

**说明性场景（本站原创分析）：** 用户进入结算路由时，共享应用外壳读取当前已批准的完整清单，解析结算制品并准备其槽位。共享应用外壳只传最小只读会话上下文和购物车稳定标识；结算切片随后从购物车后端重新读取带版本的权威状态。

购物车和订单真相留在权威后端；切片之间只交换稳定标识、预期版本和幂等键。

提交订单时，结算切片发送购物车稳定标识、预期版本与幂等键。订单后端逐请求验证会话、租户、资源权限和业务不变量，成功后返回权威订单标识；界面再用订单标识查询结果，而不以按钮状态或本地提示推断业务终态。

**本站原创发布设计：** 每个业务团队先产出不可变制品与内容身份。发布控制面检查公开入口、共享应用外壳最低版本、公共运行时兼容范围和健康探针，再在预发布环境验证候选组合。

回退前端清单只改变后续加载的制品组合，不能撤销已经发生的订单、支付或库存效果。外部效果必须由权威业务系统按自己的状态、幂等与补偿合同处理，发布系统无权伪造业务回滚。

## 关键机制导读

机制阅读的目的不是选择框架，而是确认每一层到底证明什么。导入映射把模块说明符解析到受控地址，并允许在范围内表达不同解析和完整性元数据；它不决定候选组合是否经过审批，也不证明组合兼容。

子资源完整性可以根据摘要验证取回的响应是否匹配预期内容，并在不匹配时阻止相应使用。它验证内容，不认证发布批准者，也不会让多项制品更新自动成为一份原子清单。

内容安全策略限制浏览器可加载或执行的资源，是输入校验之外的纵深防御。它不能替代后端对每次业务请求的认证、授权和不变量校验，也不能把同源切片变成互相隔离的来源。

长任务接口以 50 毫秒阈值暴露长任务，并提供受同源与隐私（Privacy）约束的归因信息。它可以触发性能信号，不能隔离主线程，也不能证明每次延迟都由某一个业务切片独自造成。

## 架构决策与权衡

采用决策按停止优先的顺序进行：

1. 是否至少有两个长期稳定、能端到端负责用户价值且确需独立发布的团队？若否，保持模块化前端单体。
2. 业务边界是否已在单体中形成明确公开接口和局部状态？若否，先用[垂直切片架构](/styles/sty-03)收拢真实变化。
3. 需求是独立代码边界还是独立运行时上线？前者使用构建时包组合即可，不必支付同页组合成本。
4. 共享应用外壳能否保持薄，权威业务状态能否留在后端？若否，先修复状态和权限所有权。
5. 团队是否具备不可变制品、完整清单、兼容门禁、观测、回滚和跨团队事故响应？若否，不进入运行时组合。
6. 每项共享依赖是否有可测量收益、明确维护者、支持范围、升级窗口和回退策略？若否，允许局部重复。
7. 同页降级是否满足隔离目标？安全或资源隔离是硬要求时，评估跨源内嵌页面或独立来源。

[Microkernel / Plug-in Architecture](/styles/sty-10)也治理稳定宿主、版本和生命周期，但其进程外插件结论不能搬到共享浏览器资源的业务切片。两种风格都要求宿主保持窄合同；不同之处在于扩展控制权、业务所有权和真实故障边界。

需要持续量化的不是“微前端数量”，而是发布等待时间、共享应用外壳变更比例、未知组合拒绝数和共享依赖锁步升级次数。还要测量切片级恢复时间、主线程与内存预算，以及跨团队事故能否定位最终责任人。指标用于验证架构假设，不预设任何收益数值。

退出信号包括：每次切片发布仍修改共享应用外壳；共享全局状态或公共领域模型频繁破坏兼容；公共运行时升级要求所有团队锁步；独立流水线数量超过真实团队边界；同页资源争用让局部恢复失效。触发后应合并切片、收窄公共层或退回模块化单体，而不是继续增加组合层。

网络超时不等于订单失败；结算切片用订单 ID 或幂等键查询权威结果，无法判定时进入待确认或人工终态。

**说明性演练（本站原创分析）：** 清单校验失败时保留上一已知可用清单，不猜测地址；关键结算切片加载失败时禁止提交；挂载重试必须有上限；合同未知时回退整份组合。回退只保护后续前端加载，已经产生的业务效果仍由订单、支付或库存所有者对账。

**本站原创安全边界：** 共享应用外壳可提供最小会话身份上下文，但资源服务仍按用户、租户、资源和动作逐请求授权。内容安全策略、响应完整性与受控来源降低供应链风险，不能把浏览器挂载状态变成权限证明。

## 可迁移经验

### 可直接复用的机制

- **先证明独立交付压力：** 用真实发布等待和团队责任验证物理拆分，而不是从仓库数量或框架偏好出发。
- **稳定标识跨边界：** 跨切片只传资源标识、预期版本和幂等键，接收方从权威后端重新读取状态。
- **最小公共运行时：** 只共享收益可测、维护者清晰且兼容策略成熟的依赖；小型或高变依赖允许重复打包。
- **所有者随制品到值班：** 业务切片同时拥有公开入口、流水线、告警、回滚与故障响应，避免把运行责任留给中央共享应用外壳团队。
- **本站推断的完整清单：** 用不可变制品、候选兼容门禁和整份原子提升形成可审计组合；该机制需要站点自己的控制面设计，不能归因于某个框架或浏览器标准。

### 只能有限类比的部分

[single-spa 微前端案例](/cases/micro-frontends-single-spa)可用于核对应用生命周期、运行时组合和共享浏览器边界，但不能证明本文电商所有权、完整清单、后端权威状态或恢复设计。框架状态机回答“何时加载、挂载和卸载”，架构决策还必须回答“为何拆分、谁批准组合、谁拥有业务终态”。

微内核的稳定宿主与微前端的薄共享应用外壳都要治理版本和生命周期，但插件可以处在进程外执行边界，同页切片则共享主线程、文档对象模型、样式与同源能力。两者的安全和故障结论不能互换。

服务端组合可以改善首屏与边缘装配，跨源内嵌页面可以提供更强浏览器隔离；二者都会改变缓存、通信、可访问性和体验成本。比较表给出评估入口，不把任一种方式写成普遍替代品。

### 不应照搬的部分

不要按页面区块或框架数量拆团队，不要广播完整可变购物车对象，不要让所有切片写入一个无版本全局状态库，也不要把私有文档对象模型或内部模块变成跨团队合同。这些做法会把本地耦合扩大成难以审计的运行时协调。

不要让生产解析 `latest`，不要逐项拼接未经验证的版本，也不要假设前端回滚会撤销订单、支付或库存。未知组合必须在提升前被拒绝，结果未知必须回到权威业务系统查询。

不要把错误边界、子资源完整性或内容安全策略写成安全沙箱。若真实目标是进程、来源、权限或资源隔离，应选能表达该边界的部署方式，并接受额外通信与运营成本。

最终采用条件很具体：稳定团队边界、可测独立发布压力、薄共享应用外壳、最小共享、后端权威状态、完整清单和可演练恢复必须同时成立。任何一项尚未闭合时，先修复该边界；若自治收益仍小于组合成本，就回到模块化前端单体。

## 来源

- [Cam Jackson, Micro Frontends](https://martinfowler.com/articles/micro-frontends.html)：只支持可独立交付前端应用、垂直业务团队及组织与组合权衡的独立分析；不证明生产收益或本文电商设计。
- [Microfrontends Overview](https://single-spa.js.org/docs/microfrontends-concept/)：唯一清单主来源，只支持 single-spa 记录的微前端概念、运行时组合和共享浏览器边界；不支持原子发布或安全隔离。
- [The Recommended Setup](https://single-spa.js.org/docs/recommended-setup/)：只支持导入映射、独立流水线、公开入口与选择性共享依赖的记录范围；不支持应用兼容或团队自治保证。
- [HTML Standard — Import maps](https://html.spec.whatwg.org/multipage/webappapis.html#import-maps)：只支持模块说明符解析、作用域与完整性元数据；不支持发布审批、原子提升、回滚或团队边界。
- [Subresource Integrity](https://www.w3.org/TR/SRI/)：只支持基于摘要的响应验证和失败处理；不认证发布批准者，也不使清单原子化。
- [Content Security Policy Level 3](https://www.w3.org/TR/CSP3/)：只支持浏览器资源与执行策略的纵深防御；不替代输入校验、后端授权或来源隔离。
- [Long Tasks API](https://www.w3.org/TR/longtasks-1/)：只支持规定阈值以上的长任务观测和受限归因；不隔离主线程，也不证明全部延迟归属。
- “Micro-Frontend 电商运行时、发布与权威状态边界图”由 Tego Arch 架构知识项目维护者原创，用于解释本站设计，不是生产效果证据。
