# Hexagonal、Onion 与 Clean Architecture：用依赖方向判断边界所有权

[风格目录](/styles)提供主题入口；本文沿用[架构风格比较框架](/styles/sty-00)的判断维度，并以[Layered Architecture](/styles/sty-01)作为依赖边界的比较起点。三者共享依赖向内的共同内核，但观察视角不同，不能仅凭目录名称判定采用了哪一种。

## 学习问题

- 三种架构共享哪些依赖和边界不变量，又在哪些命名与推理起点上不同？
- 同一次提交订单控制流如何在三套术语中保持同一行为？
- 当运行时调用外部机制时，源码依赖为什么仍能指向内部？
- 什么情况下迁移成本超过边界隔离带来的价值？

## 组件、连接器与约束

共同内核是：业务策略位于内部，技术机制位于外部；源码依赖指向内部；跨边界使用显式接口和简单数据。业务规则不依赖 HTTP、ORM、数据库驱动、供应商 SDK 或消息中间件，外部机制反而依赖应用核心拥有的抽象。接口的位置表达所有权，而不只是调用语法；自动化测试或内存实现可以替代外部适配器，但测试替身本身不是架构。

| 关注点 | 共同语义 | Hexagonal | Onion | Clean |
| --- | --- | --- | --- | --- |
| 内部核心 | 业务策略位于内部，技术机制位于外部 | Application | Domain Model / Application Core | Entities + Use Cases |
| 输入边界 | 外部驱动方以显式接口发起用例 | Driving Port | Application Interface | Input Boundary |
| 输出边界 | 核心声明所需的外部能力 | Driven Port | Core Interface | Output Boundary / Gateway |
| 外部实现 | 技术机制实现内侧合同 | Adapter | Infrastructure | Interface Adapter / Frameworks and Drivers |
| 依赖规则 | 源码依赖指向内部或内侧抽象 | Adapter 依赖 Port | Outer Layer 依赖 Inner Interface | Source Dependency points inward |
| 主要观察重点 | 边界所有权可被检查 | 有目的的对话与可替换适配器 | 独立对象模型和核心接口 | 策略层级、用例和边界数据 |

</div>

这张表是有条件的术语映射，不是逐格等同。Hexagonal 从应用与外界有哪些有目的的对话出发，六边形的边数没有架构语义。Onion 从独立对象模型和应用核心拥有哪些接口出发，把基础设施推向外圈；其原始表述具有面向对象偏向，但这不是所有语言都必须采用的实现方式。Clean 区分企业级规则与应用级用例，更细地约束策略层级和边界数据；常见四圈图只是示意，不规定固定圈数或目录层数。

## 边界与控制流

同一个提交订单结构包含外部驱动方、输入适配器、提交订单用例、订单领域规则、库存端口、订单仓储端口、库存服务适配器和数据库适配器。实线表示运行时控制流，虚线表示源码依赖指向内侧接口，两种方向不能混为一谈。接口由需要它的内侧策略拥有，外侧适配器实现并依赖该接口。

调用可以从用例向库存或数据库机制执行，但源码合同仍由内侧持有。HTTP request、ORM entity、database row 与 SDK response 必须在边界转换，不得进入应用核心。边界只传递用例需要的简单输入输出数据，并把外部失败转换为应用可理解的稳定结果；领域实体不直接充当协议响应或数据库记录。

## 数据所有权与一致性

订单领域规则拥有合法状态变化，数据库适配器只实现持久化能力。采用这些架构不自动决定事务边界、数据库所有权或分布式一致性；本例也不承诺事务范围、性能或生产事故收益。这些决策需要独立的业务不变量和运行证据。

## 部署单元与故障域

代码依赖边界与部署、扩缩和故障边界正交，必须用单独证据决定运行拓扑。代码边界不自动形成独立部署、独立扩缩或故障隔离。单进程中的端口、同心层或外圈命名仍共享进程资源与失败传播路径。

## 团队拓扑

业务能力所有者同时维护内侧策略及其所需接口，不按 Controller、Repository、Database 技术角色机械拆队。外围机制可以由专业人员协作维护，但接口语义和业务判断仍由能力所有者负责。

## 质量属性收益与成本

收益是测试接缝、机制可替换性和可检查依赖；成本是接口、映射、组合根、边界错误转换和认知负担。可替换不等于替换必然便宜：数据迁移、外部协议差异和运行风险仍可能主导成本。依赖测试能检查方向，行为测试才能证明用例语义没有改变。

## 迁移路径

迁移修复具体依赖违规，不是三个标签之间的迁移。依次识别被机制类型污染的策略、在现有调用点建立稳定边界、把接口所有权移入核心、逐个替换外部实现、加入依赖与行为测试，并保持每一步可发布和可回退。目录重命名不构成迁移证据。

## 禁用条件

小型、短生命周期、变化压力低的 CRUD 应用可能不值得承担接口、映射和组合成本。若只有目录改名、没有依赖约束，或团队无法维护接口与映射，不得宣称采用成功。若新增边界只有转发、没有隔离真实变化压力，应停止继续拆分并保留更直接的结构。

## 对比案例

以下三套复述保持同一订单行为和拓扑，不把名称差异伪装成实现差异：

- **Hexagonal：** HTTP、CLI 或自动化测试通过 driving adapter 和 driving port 调用提交订单；用例通过 driven port 使用库存和持久化能力，外侧 adapter 实现这些 port。
- **Onion：** 应用服务编排订单领域模型；库存和仓储接口属于 application core，基础设施在外圈实现并依赖这些接口。
- **Clean：** Controller 调用 Input Boundary；Use Case 调用 Entity，并通过 Output Boundary 或 Gateway 使用库存和持久化机制。

| 判断信号 | Hexagonal 视角 | Onion 视角 | Clean 视角 | 不采用或停止条件 |
| --- | --- | --- | --- | --- |
| 端口对话 | 按驱动方和被驱动方识别有目的的对话 | 只在核心需要能力时定义接口 | 用输入与输出边界保护用例 | 只有单一稳定入口且替换价值很低 |
| 核心所有权 | Application 不知道适配器技术 | 内层定义接口，外层实现 | 高层策略不提及外层名称 | 接口仍由数据库或框架模块拥有 |
| 策略层级 | 不强制固定圈数 | Domain Model 位于中心 | 区分 Entities 与 Use Cases | 分层只增加转发而没有独立策略 |
| 测试 | 用测试适配器驱动端口 | 核心可脱离基础设施运行 | 用例和实体可独立测试 | 测试仍必须启动真实 UI 或数据库 |
| 部署 | 不从端口推导部署拓扑 | 不从同心层推导故障域 | Frameworks 位于外圈不等于独立服务 | 目标是独立扩缩或网络隔离却没有额外设计 |
| 迁移成本 | 先包围有变化压力的对话 | 把接口所有权移回核心 | 在边界转换外部数据 | 小型、短生命周期、变化压力低的 CRUD 应用 |

</div>

## 来源

[Alistair Cockburn 的 Hexagonal architecture 原始文章](https://alistair.cockburn.us/hexagonal-architecture/)用于核对端口、适配器、有目的的交互与隔离测试意图。[Jeffrey Palermo 的 Onion Architecture part 1](https://jeffreypalermo.com/2008/07/the-onion-architecture-part-1/)用于核对独立领域模型、应用核心和外置基础设施的范围。[Jeffrey Palermo 的 Onion Architecture part 3](https://jeffreypalermo.com/2008/08/the-onion-architecture-part-3/)用于核对向心依赖原则及其与传统分层的差异。[Robert C. Martin 的 The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)用于核对 Dependency Rule、策略层级、边界穿越和简单边界数据。[AWS Hexagonal Architecture Overview](https://docs.aws.amazon.com/prescriptive-guidance/latest/hexagonal-architectures/overview.html)只补充工程实现边界与成本，不覆盖原作者定义。
