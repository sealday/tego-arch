# Pipes and Filters：用明确合同拆分批处理与流处理

五个处理框连成一条线，不代表恢复和容量问题已经解决。同一组订单转换在有限批次中可以等齐后发布，放到持续数据流中却必须回答窗口何时完成、压力怎样返回、失败从哪里重放。

Pipes and Filters 的可迁移价值，是把转换责任与步骤间传递合同分开。可组合性来自稳定的输入、输出和运行边界，而不是方框数量；批处理与流处理可以共享业务转换，却不能共享一套未声明的保证。

本文以原创订单场景和原创图表解释机制，并把判断落到质量属性（Quality Attribute）。外部来源分别只支持模式定义及其问题、有限与无限输入和窗口、非阻塞背压、进程管道退出状态；版本与许可接缝放在文末证据卡，不把产品实现外推成普遍保证。

## 学习问题

- Filter 与 Pipe 分别拥有哪部分控制权，Pipeline 又组合什么？
- 相同订单转换为何需要两套输入、状态、顺序和输出合同？
- 慢消费者如何逐边界反馈容量，背压在哪里中断？
- 失败从什么最小单位恢复，何时必须查询、对账或转人工？
- 怎样渐进迁移，哪些共享事务或运维条件要求停止？

## 一页摘要

Filter 处理一个明确的转换或判定；Pipe 把结果和运行信号交给下一步；Pipeline 只在输入、输出合同兼容且业务语义允许时组合这些步骤。拆分带来替换、复用、独立扩缩和局部恢复的机会，也增加序列化、状态持久化、积压和跨所有权运营成本。

先用三个问题判断这条链是否真的成立：数据怎样变化，压力怎样传播，失败由谁收束。

| 检查面 | 必须声明 | 未声明时的风险 |
| --- | --- | --- |
| 数据 | 输入身份、输出、过滤原因与版本 | 步骤可连接但语义不兼容 |
| 容量 | 有界缓冲、反馈动作与中断点 | 慢端把积压推成资源失效 |
| 恢复 | 最小重放单位、外部效果与人工所有者 | 重跑重复业务效果或永久循环 |

结论不是“拆得越细越好”，而是每个边界都要有可验证的合同和具名所有者。

## 事实边界

**已证实事实：** Filter 接受已声明输入，执行转换或判定，并产生已声明输出、过滤原因或错误分类。Filter 不证明无状态、纯函数、幂等或可任意并行；它可以持有批次局部状态、窗口状态，或访问外部权威状态。

Pipe 传递一个步骤的输出，并承载序列化、容量、缓冲、确认、顺序和错误传递合同。Pipe 不自动形成可靠消息队列、共享内存或事务边界，也不能偷偷修正业务数据。

Pipeline 组合 Filter，并要求输入与输出都满足相邻合同。Pipeline 不保证交换律或事务；定价与风险判断的顺序变化，可能改变舍入、调用和最终可见结果。

本文不宣称某个产品已实现这些边界，也不从软件仓库许可推导文档的广泛复用权。外部证据只回答模式机制、批流边界、非阻塞背压和进程管道状态；订单场景、图表、质量属性和业务终态判断是本站的原创分析。

**批处理轨的有限输入**

批处理从有限且可枚举的输入清单开始，固定批次身份，可按分区并行。阶段屏障核对输入与输出集合，只有完整批次版本或明确标记的部分版本才能发布；失败可以按记录、分区、阶段或整批重跑。

**流处理轨的持续输入**

流处理面对当下不可完整枚举的输入，必须声明事件时间或处理时间、窗口、迟到数据、完成判断和检查点。持续结果可能追加、更新或撤回；消费者必须知道自己读到的是哪个窗口和哪种可见性语义。

## 控制权与任务流

**说明性场景（Tego Arch 架构知识项目分析）**：输入是一组订单记录。批处理轨：校验、标准化、定价、风险标记、汇总/输出。流处理轨：校验、标准化、定价、风险标记、汇总/输出。风险标记不是支付授权，场景也不代表客户数据、事故或基准测试。

每个 Filter 的评审必须绑定六项字段：

| 合同字段 | 必须回答的问题 |
| --- | --- |
| 输入结构及身份 | 哪种记录、哪个版本和哪个稳定身份可以进入？ |
| 成功输出与过滤原因 | 下游收到什么，未输出时如何区分过滤与失败？ |
| 状态位置 | 状态属于批次、窗口、键、检查点还是外部权威？ |
| 容量和缓冲上限 | 允许积压多少，超限时谁暂停、削减或拒绝？ |
| 重放与幂等边界 | 哪个最小单位可重放，哪些外部效果必须先查询？ |
| 所有者 | 谁拥有代码、数据、容量与人工终态？ |

这六项把可组合的接口与可运营的运行合同连在一起。缺少任一项时，局部步骤即使能运行，也不能据此推导整条链可靠。

## 架构决策与权衡

下表回答同一转换链在哪八个运行维度上必须分轨设计。它不是成熟度阶梯；有限数据可以由持续引擎处理，无界数据也可以切成微批，选择仍取决于输入边界和运行合同。

<div className="table-wrapper table-wrapper--mapping diagram-wrapper--scroll-owner" role="region" aria-label="批处理轨与流处理轨八维机制对照表，可横向滚动" tabIndex={0} onKeyDown={handleHorizontalArrowKey}>

| 维度 | 批处理轨 | 流处理轨 | 决策问题 |
| --- | --- | --- | --- |
| 输入边界 | 有限且可枚举的批次 | 持续、当下不可完整枚举的数据 | 何时知道输入已经结束？ |
| 触发方式 | 计划、文件到达或人工启动 | 订阅、持续读取或事件到达 | 谁负责启动、暂停和恢复？ |
| 状态位置 | 批次、分区或阶段局部状态 | 窗口、键控或检查点状态 | 状态由谁持久化和版本化？ |
| 顺序 | 批内、分区内或显式排序 | 来源/分区/键内的有限顺序 | 哪个范围外不能推导顺序？ |
| 容量控制 | 并行度、分片、调度和批次准入 | 有界缓冲、请求量、暂停读取或负载削减 | 压力能否逐边界传回？ |
| 错误传播 | 失败记录、分区、阶段或批次 | 单记录、算子、分区或持续任务 | 最小恢复单位是什么？ |
| 恢复单位 | 重跑记录/分区/阶段/批次 | 从检查点恢复并受控重放 | 重放会不会重复外部效果？ |
| 输出可见性 | 完整批次版本或明确部分版本 | 追加、更新、撤回或窗口结果 | 消费者何时可以信任结果？ |

</div>

矩阵要求设计者回答所有权，而不是给“批”或“流”贴上性能标签。触发更频繁不证明延迟目标成立，显式排序也只在声明范围内生效。

状态必须有唯一权威位置和版本规则。批次状态通常围绕输入清单、分区进度和发布版本，流状态通常围绕键、窗口和检查点；把两者都叫“处理进度”会隐藏不同的完成条件。

顺序只在批内、分区内、来源内或键内等声明范围成立。该模式不保证全局顺序，也不允许仅凭步骤相连就推导任意重排安全。

输出合同要说明完整批次、部分版本、追加、更新、撤回或窗口结果何时可见。Pipes and Filters 不保证端到端 exactly-once 业务效果，不替代跨步骤业务事务，不保证可靠投递，不保证幂等；这些能力需要逐边界协议和目标系统共同证明。

稳定合同可以改善可修改性、独立扩缩和局部恢复，但序列化、持久状态、排队、观测与人工处置会增加延迟、容量和运营成本。收益与成本必须落到批流矩阵和故障所有权中验证，不能只凭步骤可复用就宣称性能或可靠性改善。

## 生产化分析

背压是逐边界的容量协议。每个 Pipe 和 Filter 的缓冲或队列都必须有界；当下游变慢时，可暂停读取、降低并发、延迟确认、缩小准入、执行负载削减或明确拒绝，动作由数据价值、期限和上游协议决定。

容量信号只说明下游当前能接受多少工作，不撤销已完成转换，也不证明最终成功。背压遇到只有无界写入、固定速率轮询或不支持反馈的不兼容边界时中断；上游必须补上有界队列、准入、溢出或降级方案。

Filter 可以在同一进程、不同进程或不同部署单元中运行；每跨一个进程、队列或网络边界，就新增序列化、超时、容量和独立失效面。拆成独立部署只有在故障隔离、扩缩或发布收益可验证时才成立，不能从 Pipeline 的逻辑分步直接推导物理故障域已经隔离。

**基于证据的推断：** 扩容并非唯一响应。热点键、串行步骤、共享数据库、外部配额或顺序约束仍会限制吞吐；运行者要同时观察缓冲深度、最老记录年龄、处理速率、拒绝或削减计数、重试（Retry）占比与下游时延。

下表把六类失败绑定到检测、自动动作、停止条件和人工所有者。自动化一旦命中停止条件就不得继续；“再试一次”不能替代业务事实判断。

| 故障 | 检测 | 自动响应 | 停止条件 | 人工所有者 |
| --- | --- | --- | --- | --- |
| 坏记录 | 合同/语义校验失败及同类比例 | 隔离并保留诊断上下文 | 隔离率或同类错误超预算 | 数据合同所有者 |
| 临时依赖失败 | 超时、限流或短时不可用 | 有界重试并施加背压 | 重试预算耗尽 | 依赖与管道运行所有者 |
| Filter 崩溃 | 进程/任务退出和健康信号 | 从阶段或检查点恢复 | 恢复循环或状态不一致 | Filter 代码所有者 |
| 部分输出 | 输入清单、输出清单或版本不完整 | 阻止发布或标记部分版本 | 无法证明输出集合完整 | 批次/输出所有者 |
| 外部效果未知 | 超时后缺少权威结果 | 查询、对账或目标侧幂等恢复 | 无法自动判定真实结果 | 业务边界所有者 |
| 毒数据持续失败 | 相同记录跨恢复仍失败 | 隔离→修复→受控重放 | 再次失败后人工终止 | 数据与业务联合所有者 |

</div>

错误可以沿 Pipe 传播，也可以进入隔离路径，但必须留下原始身份、阶段、错误分类和处置状态。支付、通知等不可逆效果超时后是结果未知；恢复前要查询目标权威状态、使用目标侧幂等合同，或进入对账与人工终态。

## 可迁移经验

### 可直接复用的机制

适合候选包括稳定中间数据合同、步骤可独立转换、扩缩需求不同、需要组合复用或分阶段恢复的处理链。订单导入、文件加工、日志处理和特征生成只是说明性候选，不构成性能、成本或可靠性保证。

迁移从一个单体处理函数开始：先观测阶段和失败点，再提取一个无需共享事务状态的 Filter；固定中间合同和幂等键；建立有界 Pipe、隔离与重放边界；最后才选择分片批处理、持续流处理或独立部署。

### 只能有限类比的部分

[微服务](/styles/sty-05)决定独立部署、私有数据与团队边界；跨服务部署 Filter 会增加网络、版本和运行所有权成本。[事件驱动架构](/styles/sty-06)决定事件载荷、业务事实和权威状态；事件不会替 Pipeline 决定步骤组合或输出可见性。

[Apache Kafka 事件流平台消费者组案例](/cases/apache-kafka-consumer-groups)解释分区、消费位置、再均衡和取数所有权；本文只解释步骤组合、容量传播和阶段恢复。[性能、延迟、吞吐与容量](/quality-attributes/qa-03)负责容量包络、排队和负载削减判断，[可靠性与状态管理路径](/paths/reliability-state)继续展开重试预算、恢复验证与人工终态。返回[架构风格目录](/styles)可按统一维度比较其他风格。

消息队列可以实现某个 Pipe，工作流（Workflow）引擎可以协调某条 Pipeline，事件或 Saga 也能参与恢复，但这些概念各自有独立责任。GNU Bash 的进程管道只说明退出状态会如何隐藏上游失败；它不是分布式处理合同的替代品。

### 不应照搬的部分

Pipes and Filters 不等于上述队列、协调、事件与命令行机制；具体机制只能在它们各自的数据、容量、故障和所有权合同内类比。

以下任一条件成立时，应保持现状、收紧范围或停止采用：

- 步骤必须共享一个可变事务状态；
- 业务要求同步交互反馈而无法接受阶段结果；
- 中间数据合同无法稳定；
- 序列化和持久化成本超过复用收益；
- 恢复需要整条链全局协调却无可证明边界；
- 背压无法跨关键依赖传播且无准入/溢出方案；
- 团队无法运营积压、检查点、隔离、重放和人工终态。

**个人分析：** 渐进提取的价值在于让每次拆分都能被回退和观测。若第一个边界尚不能说明状态、容量与恢复所有者，就不应先把后续步骤变成网络服务。
