# G008 Batch 5：UML 选图指南设计

## 1. 目标

本批次只发布并关闭 `MOD-07`：帮助有经验的开发者从评审问题出发，在 use case、sequence、state、class 和 deployment 五类 UML 图之间选择最小而充分的视图，并明确每类图能支持什么判断、不能证明什么，以及仍需补充哪些事实证据。

页面沿用费用申报系统作为贯穿演练，继承 `MOD-02` 的系统边界和权威命名、`MOD-06` 的核心业务概念。所有选择矩阵、问题、图和演练均为本站原创教学决定，不是现有系统已验证的生产事实。

## 3. 已批准的方法

采用“评审问题决策矩阵”方法：

```text
写出需要判断的问题
  → 识别观察对象和时间尺度
  → 选择最小而充分的 UML 图
  → 写出该图能够支持的判断
  → 写出该图明确不能证明的内容
  → 补充代码、运行、部署或业务证据
```

不采用“五类 UML 小教程”，因为它容易变成符号手册并侵入 `MOD-08`。不采用“完整多视图评审包”，因为它会制造每次评审都要维护五张图的错误暗示，并与后续架构图审阅主题重叠。

当问题本身不清楚时，流程返回“先澄清问题”，而不是默认绘制 class diagram。当一个图不足时，页面要求明确第二个互补模型解决的剩余问题，而不是把不同证据边界挤进一张图。

## 4. 五类图的证据边界

| 图 | 主要回答 | 能支持的判断 | 明确不能证明 |
| --- | --- | --- | --- |
| use case | 谁为了什么目标使用系统 | 参与者、目标、系统边界和外部交互范围 | 操作顺序、内部组件、授权已经正确 |
| sequence | 一个场景中谁先后与谁交互 | 消息顺序、参与者、同步点、分支与异常路径 | 性能时限、并发安全、所有状态都被覆盖 |
| state | 一个对象允许怎样变化 | 状态、事件、守卫、转换和终态 | 跨对象原子性、组件所有权、分布式一致性 |
| class | 领域概念如何形成静态类型关系 | 类型、职责、关联、多重性和泛化 | 运行时顺序、数据库 schema、对象数量和生命周期事实 |
| deployment | 软件实例运行在哪里 | 节点、执行环境、部署单元和通信路径 | 实际库存、容量、故障切换和安全控制已经验证 |

### 4.1 Use case

费用申报示例固定员工、审批人、财务人员与费用申报系统边界，表达参与者为了完成业务目标与系统发生的交互。它不展开内部容器、消息顺序或授权实现。

### 4.2 Sequence

只展开“一份已提交申报进入审批并形成付款意图”的单个场景，允许表达一个必要异常分支。消息排列说明场景内的相对顺序，不等于性能时限、全局并发顺序或事务保证。

### 4.3 State

只展示足以支持选图判断的最小申报状态片段，说明事件、守卫、转换和终态的观察单位。完整终态、超时、取消、补偿与人工终态设计留给 `MOD-08`。

### 4.4 Class

复用 `MOD-06` 的 `ExpenseClaim`、`Approval` 和 `PaymentInstruction` 等核心概念，关注类型职责和静态关系。页面必须明确 UML class 不等于 ER 实体、逻辑数据模型或物理数据库表。

### 4.5 Deployment

使用 `MOD-02` 的权威名称、系统边界和外部“银行支付服务”，并与 `MOD-03` 的 C4 Deployment 教学边界比较。图上节点和通信路径不能冒充实际资产清单、容量、容灾或安全验证。

## 5. 内容结构

页面使用固定九段 H2：

1. 学习问题
2. 建模目标与输入
3. 参与者与步骤
4. 模型产物
5. 完成判断
6. 常见失败
7. 与其他模型的衔接
8. 完整演练
9. 来源

### 5.1 学习问题

提出 4–5 个问题，覆盖：

- 如何从评审问题选择最小 UML 图；
- 五类图分别观察什么；
- 图上的元素能支持哪些判断；
- 哪些事实必须由代码、运行、部署或业务证据补足；
- 何时需要第二个互补模型。

### 5.2 建模目标与输入

输入包括评审问题、受众、事实截止时间、系统边界、场景、业务概念、部署环境和现有证据。未知的授权规则、并发行为、实际部署库存、容量、容灾、运行时延和状态覆盖继续标为验证缺口。

### 5.3 参与者与步骤

参与者至少包括问题提出者、业务或领域负责人、应用开发者、平台或运维负责人、模型维护者和未参与绘图的评审者。

步骤：

1. 把“画一张 UML 图”改写成一句可判断的评审问题。
2. 确定观察对象是参与者目标、单场景交互、对象生命周期、静态类型还是运行节点。
3. 选择最小而充分的图。
4. 写出图中每个关键元素的事实来源或假设状态。
5. 写出该图明确不能证明的内容。
6. 由独立评审者复述判断和证据缺口。
7. 只有剩余问题需要不同观察对象时，才增加第二个模型。

### 5.4 模型产物

产物包括一张 Mermaid 选图流、一张证据边界对照表，以及完整演练中的五条评审记录。每条评审记录包含问题、选图、输入事实、预期判断和未解决证据缺口。

### 5.5 完成判断

页面完成时，读者能够从评审问题选择一类图、说明选择理由、指出该图不能证明的内容，并为关键元素给出事实或显式假设。没有问题、证据边界或截止时间的图不算完成。

### 5.6 常见失败

- 默认画 class diagram，把熟悉工具误当成问题分类。
- 用 sequence 表示静态所有权或全局并发保证。
- 用 state 图暗示跨对象原子性或分布式一致性。
- 用 class 图冒充数据库 schema 或运行时对象事实。
- 用 deployment 图声称实际库存、容量或故障切换已验证。
- 把五类视图混进一张无法评审的万能图。

### 5.7 与其他模型的衔接

`MOD-01` 提供模型选择总览；`MOD-03` 提供 C4 Dynamic 和 Deployment 的近邻比较；`MOD-06` 提供 class 与 ER/数据模型边界；Temporal Saga 案例用于说明行为、状态和运行证据必须分层。`MOD-08` 只以“下一主题尚未发布”出现，不建立无效链接。

### 5.8 完整演练

费用申报系统使用五个独立评审问题：

1. 员工、审批人和财务人员分别为了什么目标使用系统？选择 use case。
2. 已提交申报如何经过审批并形成付款意图？选择 sequence。
3. 一份申报允许经历哪些状态变化？选择 state。
4. 申报、审批和付款意图的静态职责如何关联？选择 class。
5. 前端、服务、任务执行单元、数据库和银行支付服务在特定环境中如何部署？选择 deployment。

实际评审只选择当前问题需要的最小子集。五条记录共同出现是为了比较，不是规定必须维护五张图。

## 6. 视觉格式决策

格式决策为 `Mermaid`。

选择流约 6 个主节点，主要表达从评审问题到五类图的简单分支，短标签、文本 diff 和低维护成本比精确布局更重要。它符合 Mermaid 的使用条件，不需要不可见节点或布局技巧。

五类图的多字段比较使用 Markdown 表格，不制作复杂对照图。页面不新增 Draw.io、SVG 或位图，因为静态资产只会重复表格信息并增加维护成本。

Mermaid 与表格都必须处于局部横向滚动边界，支持键盘聚焦和 ArrowLeft/ArrowRight 滚动，并在文章宽度、desktop `1440x1000` 和 mobile `390x844` 下保持可读。颜色不能成为唯一含义载体。

## 7. 来源与版权边界

### 7.1 新增来源

新增 OMG Unified Modeling Language 2.5.1 官方规范来源：

- source ID 固定为 `src-omg-uml-2-5-1-2017`；
- canonical identity 固定为 `https://www.omg.org/spec/UML/2.5.1`；
- 规范 PDF transport 使用 OMG 官方 `UML/2.5.1/PDF`；
- version 固定为 `2.5.1, December 2017`；
- 来源只支持规范名称、正式版本和五类 UML 模型的标准语义；
- 版权策略固定为 `LicenseRef-All-Rights-Reserved`，只保留链接、版本事实、归因和本站原创摘要，不复制规范图、长段文字或表格；
- link policy 使用 `stable`，review policy 使用 `quarterly-version-sensitive`，因为 OMG 的无版本入口可能指向后续正式版本，但本文的 canonical identity 和事实声明固定在 2.5.1。

### 7.2 复用来源

- C4 Dynamic 官方页面只用于比较单场景运行时协作边界。
- C4 Deployment 官方页面只用于比较实例、节点和环境视图边界。
- `Applying UML and Patterns, 3rd edition` 的 Pearson 书目来源只支持 UML 与对象设计的历史语境，不支持复制图表、案例或章节结构。

页面必须至少显示 OMG、C4 和 Pearson 三个独立来源标签。OMG 规范是 manifest-primary 来源；C4 和 Pearson 只在各自登记范围内提供比较或历史语境。

## 9. 错误与缺口处理

- 评审问题不明确时返回“先澄清问题”。
- 一个图无法覆盖剩余问题时，记录第二个模型的独立职责。
- 缺少事实来源时标记显式假设或验证缺口。
- Mermaid、表格、来源或可见关系缺失时，内容测试和生成检查失败关闭。
- 来源 transport 不可用时，不用未经审查的替代页面静默改变 canonical identity。
- 生产渲染或交互检查失败时保持 MOD-07 pending，不进入 Stage B。
