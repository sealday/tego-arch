# G008 Batch 4：ER 模型与关系边界设计

## 1. 目标

本批次只发布并关闭 `MOD-06`：沿用费用申报系统，讲清实体身份、关系边界、基数、约束和关系历史。

页面必须帮助读者回答：

- 什么是实体，如何选择稳定身份；
- 什么应建模为属性，什么应提升为实体或关联实体；
- 一对一、一对多、多对多及可选性分别表达什么；
- ER 图能够表达哪些结构约束，哪些规则必须留在约束表、数据库机制或运行验证中；

## 3. 已批准的方法

采用“平衡型 ER 教学主线”：

```text
业务词义
  → 识别实体与稳定身份
  → 判断属性、实体与关联实体的边界
  → 标注基数和可选性
  → 把图外约束移入约束表
  → 用有效期关联实体保留关系历史
  → 保留数据库与运行验证缺口
```

不采用图示优先方案，因为一张 ER 图不能证明时间重叠、条件唯一性、状态前置条件或并发安全。也不采用时间建模优先方案，因为完整双时态、事件溯源和迁移实现会侵入后续主题并削弱本页的 ER 入门职责。

## 4. 教学边界与术语

### 4.1 实体身份

每个实体使用稳定技术身份。员工号、组织代码、审批步骤和付款幂等键属于业务唯一性，不与实体身份混为一谈。

页面必须明确：

- 身份用于在属性变化后继续指向同一业务对象；
- 显示名称、状态和组织归属不是稳定身份；
- 业务唯一键可能变化、复用或具有作用域；
- 技术身份本身不证明业务唯一性，仍需单独约束。

### 4.2 关系与基数

基数同时表达两端的最大数量和可选性。正文不得只写“一对多”而省略零或一的下界。

基数是教学假设，不是从现有表或样例数据反推的事实。必须通过业务规则、反例和生命周期问题验证。

### 4.3 关系历史

本文只讨论业务关系的有效期历史：

- 当前状态回答“现在是什么”；
- 有效期关系回答“某个业务时间段内是什么”；
- 审计记录回答“谁在何时修改了记录”；
- 事件日志记录发生过的事件，不能自动替代业务关系历史。

不引入完整双时态模型。`recordedAt`、系统时间修正和追溯查询只作为明确的后续边界。

## 5. 逻辑模型

### 5.1 实体

| 实体 | 稳定身份 | 主要职责 |
| --- | --- | --- |
| `Employee` | `employeeId` | 表示员工业务身份 |
| `OrganizationalUnit` | `orgUnitId` | 表示组织单元业务身份 |
| `EmployeeOrgAssignment` | `assignmentId` | 表示员工主要组织归属的一段有效期 |
| `ExpenseClaim` | `claimId` | 表示一次费用申报 |
| `Approval` | `approvalId` | 表示某审批步骤作出的业务决定 |
| `PaymentInstruction` | `paymentInstructionId` | 表示对外付款的唯一业务意图 |

### 5.2 关系

- `Employee` 1 — 0..N `ExpenseClaim`：员工可以没有或提交多份申报；每份申报属于一名员工。
- `ExpenseClaim` 1 — 0..N `Approval`：申报可能尚无审批决定，也可能产生多个步骤的决定；每个决定针对一份申报。
- `Employee` 1 — 0..N `Approval`：员工可以不作或作出多个审批决定；每个已记录的决定有一名决定者。
- `ExpenseClaim` 1 — 0..1 `PaymentInstruction`：申报可能尚未形成付款意图；每个付款意图只对应一份申报。
- `Employee` 1 — 0..N `EmployeeOrgAssignment`：员工在不同有效期内拥有主要组织归属。
- `OrganizationalUnit` 1 — 0..N `EmployeeOrgAssignment`：组织单元可以承载多个员工归属。
- `EmployeeOrgAssignment` 1 — 0..N `ExpenseClaim`：每份申报引用提交时适用的一条归属；同一归属可承载多份申报。

最后一条关系用于避免按员工“当前组织”重算旧申报的历史归属。它不表示组织拥有申报，也不表示审批运行顺序。

### 5.3 有效期与图外约束

`EmployeeOrgAssignment` 使用 `[validFrom, validTo)`：

- `validTo` 可以为空，表示仍有效；
- 非空 `validTo` 必须晚于 `validFrom`；
- 同一员工的“主要组织归属”有效期不得重叠；
- 费用申报的提交时间必须落在引用归属的有效期内；
- 申报员工必须与引用归属中的员工一致；
- 历史变更通过关闭旧区间并增加新记录表达，不静默覆盖旧关系。

其他图外约束：

- 同一申报的审批步骤不得重复；
- 每份申报最多对应一个付款业务意图；
- 只有满足批准条件的申报才能产生付款指令；
- 金额必须与币种共同解释；
- 付款幂等业务键必须唯一。

ER 图只能表达其中部分结构和基数，不能证明时间区间不重叠、跨实体一致性、状态前置条件、并发安全、迁移安全或性能。

### 6.1 学习问题

提出 4–5 个问题，覆盖：

- 稳定身份与业务唯一键的差异；
- 属性、实体与关联实体的边界；
- 基数与可选性的验证方法；
- ER 图与图外约束的能力边界；
- 当前关系、有效期历史、审计记录和事件日志的区别。

### 6.2 建模目标与输入

输入包括：

- `MOD-02` 的系统边界和权威命名；
- `MOD-05` 的四个逻辑实体；
- 业务词汇、身份规则、唯一性和生命周期；
- 关系两端的最小/最大数量及反例；
- 时间语义、历史查询和修正要求；
- 数据保留、审计、迁移、并发和完整性要求。

未知的生产基数、并发冲突率、查询分布、历史保留期和迁移策略继续标为验证缺口。

### 6.3 参与者与步骤

参与者至少包括业务负责人、领域/数据建模者、应用开发者、数据库工程师和独立评审者。

步骤：

1. 固定业务词义和问题边界。
2. 以稳定身份识别实体，不从表名开始。
3. 用独立生命周期、身份和属性判断实体边界。
4. 为每条关系确认两端的最小/最大数量。
5. 把多对多或带属性的关系提升为关联实体。
6. 把图不能表达的约束移入约束表。
7. 用有效期关联实体保存关系历史。
8. 把数据库执行、并发、迁移和性能留给后续验证。

### 6.4 模型产物

#### Mermaid ER 图

只使用一张 `erDiagram`，展示六个实体、七条关系、稳定身份和少量理解关系所需的属性。

图中不得：

- 展示运行时序；
- 把所有字段扩张成完整 schema；
- 用注释声称时间重叠或状态约束已由图证明；
- 使用物理表名、数据库类型或索引。

图的可访问名称应说明它是费用申报 ER 教学模型，并支持局部横向滚动、键盘聚焦与 ArrowRight 滚动。

#### 身份与边界决策表

比较：

- 实体：有稳定身份和独立生命周期；
- 属性：只描述所属实体，不需单独追踪；
- 值对象：由值定义，可整体替换；
- 关联实体：关系自身有属性、历史或独立约束。

表格必须使用费用申报例子，并说明分类是上下文决定而不是普遍固定答案。

#### 约束覆盖表

至少包含：

- 结构关系与普通基数；
- 业务唯一性；
- 时间区间有效性与不重叠；
- 跨实体一致性；
- 状态前置条件；
- 并发、迁移和性能。

每行标明主要表达位置和仍需验证的证据。

### 6.5 完成判断

完成条件：

- 六个实体均有可解释的稳定身份；
- 七条关系的两端下界和上界明确；
- `EmployeeOrgAssignment` 的存在由关系属性和历史需求证明；
- 有效期采用一致的半开区间语义；
- 图外约束没有伪装成图已证明的事实；
- 当前状态、有效期历史、审计记录和事件日志明确区分；
- 所有本站教学假设和未知项可识别。

### 6.6 常见失败

至少覆盖：

- 把显示名称或可变业务编号当作稳定身份；
- 只写“一对多”，不说明可选性；
- 把带属性和历史的多对多关系藏在普通连线中；
- 根据当前组织归属重算历史申报；
- 把审计字段、事件日志或 Temporal Event History 当作业务关系历史；
- 认为 ER 图已经证明时间重叠、状态条件或并发安全；
- 把逻辑 ER 图直接称为生产 schema。

### 6.7 与其他模型的衔接

- `MOD-01` 负责从评审问题选择模型。
- `MOD-05` 提供四个核心逻辑实体，并在本批次更新为有效链接。
- `PR-13` 帮助区分领域含义与持久化实现。
- Temporal Saga 案例只用于对比控制面 Event History 与业务关系历史。
- `MOD-08` 将讨论状态机，但尚未发布，因此只写无链接后续提示。

### 6.8 完整演练

演练包含：

1. 员工在组织 A 有一条主要归属。
2. 员工提交申报，申报引用当时有效的归属记录。
3. 审批决定和付款意图按各自身份与唯一性建模。
4. 员工随后转入组织 B，旧归属区间关闭，新归属开始。
5. 旧申报仍引用组织 A 的历史归属，不能按当前关系改写。
6. 如果需要纠正历史，必须显式记录修正策略；本文不假定静默覆盖。

演练明确区分业务有效时间、记录修改时间、审计信息和事件记录。

## 8. 来源与版权边界

### 8.1 逻辑/ER 建模资料

产品文档只代表相应工具或方法，正文不得将其表述为行业唯一标准。

### 8.2 Mermaid

Mermaid 官方文档只用于支持 `erDiagram` 的语法、关系标记和渲染行为。Mermaid 是表达工具，不是 ER 理论标准，也不支持本文的费用申报领域规则。

如文档无法固定到不可变版本，应记录精确访问日期和仓库使用的 Mermaid 版本，并避免依赖未经锁定的新语法。

### 8.3 PostgreSQL 18

PostgreSQL 18 官方文档可用于说明：

- `UNIQUE`、`CHECK`、外键等约束机制；
- range 类型的上下界语义；
- exclusion constraints 可用于表达某些不重叠规则。

这些机制不证明本文的费用申报规则正确，也不证明并发、迁移或性能达标。正文不提供完整 DDL。
