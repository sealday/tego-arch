## 1. 目标与非目标

本主题新增一篇可独立阅读的架构风格文章，说明模块化单体如何在一个部署单元内，用业务模块、显式合同和数据所有权控制变化与耦合。文章必须把“模块化”和“单体”分开解释：前者描述源码、语义和数据边界，后者描述构建与部署形态；模块化单体不是任意分包的单体，也不是暂时没有拆开的微服务集合。

统一案例继续使用提交订单。系统包含订单、库存、支付和通知能力；正文以订单模块为编排起点，展示同步模块调用、本地事务、提交后事件与事务性发件箱的边界。文章不把共享进程、共享数据库或框架模块检查误写成自动隔离，也不声称模块化单体天然获得独立扩缩、独立发布或故障隔离。

本轮不实现 STY-05，不完成 CASE-04 或 QST-03，不新增运行时功能，不改变既有路由，不进行无关重构，也不把 Spring Modulith、.NET、Java 包或某一目录模板写成架构风格定义。

## 2. 页面结构与核心判断

新增 `content/styles/sty-04-modular-monolith.mdx`，类型为 `style`，主题 ID 为 `STY-04`，正式页面 slug 为 `/styles/sty-04`。文章沿用现有风格页的十一段契约：

2. 组件、连接器与约束
3. 边界与控制流
4. 数据所有权与一致性
5. 部署单元与故障域
6. 团队拓扑
7. 质量属性收益与成本
8. 迁移路径
9. 禁用条件
10. 对比案例
11. 来源

正文围绕五个不可替代的判断组织：

- **模块合同：** 其他模块只能通过公开应用合同、稳定查询合同或已提交事件协作，不得导入内部类型、调用内部仓储或绕过入口写表。
- **数据所有权：** 共享物理数据库可以存在，但每张权威表、迁移和写入路径必须有唯一模块所有者；共享数据库不等于共享数据模型。
- **一致性：** 同一进程和数据库允许在明确不变量边界内使用本地事务；跨模块原子事务必须被识别为耦合，而不是被“没有网络”掩盖。提交后副作用用事件或 Outbox 表达时，需要定义提交、投递、重复和失败恢复。
- **部署与故障：** 默认仍是一个制品、一个发布节奏和高度共享的进程故障域；模块边界可以降低变化耦合，但不会自动创造运行隔离。
- **拆分条件：** 只有独立发布等待、资源曲线、合规/数据驻留、故障隔离、团队自治或技术边界成为持续可测压力，并且模块合同与数据迁移已经可验证时，才把模块作为服务拆分候选。

## 3. 统一场景与比较框架

提交订单场景采用以下控制流：

1. 外部请求进入订单模块公开入口；
2. 订单模块校验订单不变量，通过库存模块公开合同申请预留；
3. 订单模块和库存模块各自保护拥有的数据，不允许跨模块直接写表；
4. 若二者确属同一数据库事务，正文明确其原子性收益与模块耦合成本；
5. 订单提交后记录领域事件或 Outbox，通知模块异步消费；
6. 重复投递、消费失败和恢复责任由显式合同处理，不把进程内事件等同于可靠消息。

对比表至少覆盖普通分层单体、模块化单体和微服务三个候选，并逐项比较业务边界、调用、数据所有权、一致性、部署、故障域、团队拓扑、运行成本和拆分信号。STY-05 仅作为未发布的下一主题出现，不生成可操作页面链接；正文只能说明待验证的比较方向，不能替代微服务主题。

## 5. 来源与版权治理

来源采用“两类直接证据 + 既有相邻来源”的最小闭环：

1. 模块化单体原始或一手工程论述，用于核对单部署单元、模块边界和服务拆分前提；
2. 官方模块化应用文档或可检查示例，用于核对公开模块、允许依赖、模块验证和事件协作机制；具体框架只作为实现例证；
3. 既有 STY-00、STY-03 与微前端案例来源仅承担尺度比较，不重复注册或越权支持 STY-04 的生产结果。

最终正文至少使用两个独立受治理远程域，并严格控制 `manifest_primary` 数量。每条新增来源必须包含作者/机构、发布日期或版本时间、核查日期、固定版本或可复查边界、来源类型、证据角色、许可证、许可证证据和使用限制；同步 `data/source-ledger.json`、`data/source-link-health.json`、公开来源投影和 `docs/source-license-inventory.md`。

版权策略为原创中文总结、原创订单场景、原创表格与原创图示；不复制外部图、源码结构、长段落、目录或品牌视觉。事实、来源支持的推断、Tego Arch 分析和未知生产结果必须显式分开。

## 6. 图示设计

格式决策为 **Draw.io + SVG**。决定性条件是：图中需要四个业务模块、两个以上模块/部署/数据区域、同步与异步两类连接器、数据所有权和 Outbox/消费失败恢复，主节点超过七个且连接器带语义标签；它也是文章的核心教学资产。Mermaid 会迫使布局依赖隐藏节点或交叉连线，位图又不足以承载精确拓扑。

新增可编辑源文件：

- `diagrams/sty-04-modular-monolith-boundaries.drawio`

新增发布资产：

- `static/img/diagrams/sty-04-modular-monolith-boundaries.svg`

图示只完成一个任务：让读者看清“一个部署单元内仍有多个拥有合同和数据的业务模块”。至少表达：

- 单一部署边界；
- 订单、库存、支付、通知四个模块边界；
- 每个模块的公开合同与内部实现；
- 模块拥有的数据区或表；
- 提交订单同步路径；
- 提交后 Outbox/事件路径；
- 共享进程故障域与异步恢复说明；
- 颜色之外仍可识别的线型、标签和图例。

SVG 必须由 Draw.io 源文件产生并与其保持同步。文章提供目的明确的替代文本和受控横向滚动区域；精确规则同时写入正文与比较表，图示不得成为唯一证据。
