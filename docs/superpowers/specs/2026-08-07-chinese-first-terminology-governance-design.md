# 中文优先术语治理设计

状态：待书面复核

日期：2026-08-07

## 背景

Tego Arch 面向希望从高级工程实践转向架构设计的中文读者。项目已经形成 94 篇正文，但术语表达仍存在三类问题：有些英文概念没有中文主称，有些同一概念在不同文章中使用不同英文拼写，还有些首页、表格和图示把内部约定或英文标签直接暴露给读者。

本次变更不以“删除所有拉丁字符”为目标。产品名、协议、代码、命令、网址和文献原题需要保持准确；真正需要治理的是面向读者的概念表达。项目采用“中文主称优先，必要英文在首次出现时伴随”的规则，并用单一术语注册表、正文术语页和自动检查共同维持。

## 已批准选择

采用注册表驱动方案：

1. 所有面向读者的英文术语首次出现时使用“中文（English）”；带公认缩写时使用“中文（English，ACRONYM）”。
2. 同一页面后续统一使用规范中文名称或已经说明过的公认缩写。
3. 产品、组织、开源项目和标准的官方专名可以保留，但首次出现必须给出中文类别或含义说明。
4. 代码、命令、网址、文件路径、程序标识符、配置键、字段名和文献原题保持原样。
5. 术语注册表是页面、检查器和贡献规范的唯一事实源，不维护平行词表。

## 目标

- 建立可审阅、可版本化的中文术语注册表。
- 新增正文页面“术语规范”，解释规则并展示全部登记术语。
- 更新首页和 README，使读者可见术语遵循同一规则。
- 把首页路线图中的“基础与质量”改为“需求与约束”，同步更新浅色和深色图片。
- 清理正文标题、段落、表格、图片说明和图中文字中的不规范英文。
- 在完整验证链中加入术语门禁，阻止新的未登记英文或禁用写法进入产品。
- 更新贡献说明，让协作者知道何时新增术语、如何写首次出现和如何申请局部例外。

## 非目标

- 不翻译或改写代码、命令、配置、接口字段、文件路径、网址和仓库标识符。
- 不翻译官方产品名、组织名、商标、协议缩写、标准编号和文献原题；只补充必要的中文说明。
- 不修改既有 slug、外链、来源标识、生成数据身份或历史提交。
- 不追溯改写 `docs/` 下的历史计划、评审记录和设计档案。
- 不使用全局搜索替换批量改写技术术语。
- 不引入新的运行时依赖或第三方自然语言处理服务。

## 规范显示规则

### 普通技术术语

首次出现：

> 质量属性（Quality Attribute）

后续出现：

> 质量属性

普通技术术语不得只写英文，也不得在同一页面反复附加英文括注。

### 带缩写的术语

首次出现：

> 架构重要需求（Architecturally Significant Requirement，ASR）

后续出现可以使用：

- 架构重要需求；
- ASR。

不得在首次出现前直接使用未说明的缩写。HTTP、URL、API 等常见工程缩写同样须在各页面首次出现时给出中文、英文全称和缩写；只有代码、命令、路径、网址和程序标识符中的字面量适用结构性例外。

### 产品、项目与组织专名

首次出现必须让中文读者知道专名所指的类别，例如：

> OpenAI 智能体软件开发工具包（OpenAI Agents SDK）

后续可以继续使用官方名称 `OpenAI Agents SDK`，也可以使用“该工具包”。官方名称不做机械翻译，不改变商标大小写和连字符。

案例标题若已经由“官方名称：中文判断句”构成，中文判断句可以承担类别说明；不要求在标题中重复括注。

### 方法、模式与标准名称

已有稳定中文译名时使用中文主称，并在首次出现时保留英文或缩写，例如：

> 架构权衡分析方法（Architecture Tradeoff Analysis Method，ATAM）

没有稳定中文译名时，使用中文解释加官方名称，例如：

> 领域叙事协作建模（Domain Storytelling）

标准编号、协议名和官方章节名保持准确；正文叙述和表格标签必须提供中文。

### 代码与引用例外

以下内容不参与“中文（English）”检查：

- 围栏代码和行内代码；
- 命令、配置键、API、字段名和程序标识符；
- 文件路径、URL、邮箱和仓库坐标；
- 外部链接中的官方文献原题；
- 直接引文中的原文；
- 版本号、标准号和许可证标识。

例外只保护原始字面量。围绕它们的解释仍必须使用中文。

## 单一术语注册表

新增 `data/terminology.json`，采用 `schema_version: 1`。顶层只允许：

```json
{
  "schema_version": 1,
  "terms": []
}
```

每个术语只允许以下字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 唯一、稳定的 kebab-case 标识 |
| `canonical_zh` | 规范中文主称 |
| `english` | 英文全称；无英文时为 `null` |
| `acronym` | 公认缩写；无缩写时为 `null` |
| `kind` | `translated-term`、`proper-noun`、`acronym`、`standard` 或 `code-literal` |
| `first_use` | 首次出现的完整显示形式 |
| `subsequent_use` | 后续允许形式数组 |
| `allowed_aliases` | 合法异形、官方大小写或历史兼容形式 |
| `forbidden_aliases` | 必须被门禁拒绝的裸英文或不规范写法 |
| `note` | 语义边界、翻译理由和例外说明 |
| `order` | 页面中的稳定排序值 |

解析器必须拒绝：未知字段、缺失字段、空白值、重复 `id`、重复 `order`、非法 kind、规范化后冲突的别名、同一别名同时允许和禁用，以及与其他术语主称冲突的禁用别名。

术语注册表不承担百科全书职责。`note` 只解释用词边界，不在没有来源的情况下扩展概念定义。需要完整论证的概念继续由对应正文承担。

## 正文术语页

新增根级正文页面：

- route：`/terminology`
- 标题：`术语规范`
- 侧栏标签：`术语规范`
- 类型：`reference`
- 位置：根侧栏现有参考类内容之后，不进入顶部导航栏。

页面包含：

1. 中文优先原则；
2. 首次出现与后续使用规则；
3. 专名、缩写、代码、引用和图示的例外；
4. 由 `data/terminology.json` 渲染的规范术语表；
5. 新增或修改术语的贡献流程。

术语表通过专用 React 组件读取注册表，不在 MDX 中手写第二份表。桌面端使用结构化表格；移动端允许表格在自身容器内横向滚动，不允许页面整体溢出。

## 自动检查架构

### 共享解析边界

将现有产品文案测试中的可见 MDX 文本提取逻辑抽成共享只读模块。术语门禁和产品文案边界测试必须使用同一套定义，避免两个解析器对“读者可见文本”产生分歧。

检查器读取术语注册表，并扫描：

- `content/**/*.mdx` 的标题、正文、表格、链接标签、图片 alt 和可见图注；
- front matter 中的 `title`、`sidebar_label` 和 `summary`；
- `README.md`；
- `src/pages/**/*.tsx` 与公开组件中的用户可见字符串；
- Mermaid 节点和连线标签；
- Draw.io 与 SVG 中的可见文本。

围栏代码、行内代码、URL、路径、导入语句、JSX 属性名、程序标识符、机器元数据和外部引用原题被排除。

### 检查规则

1. 已登记 `forbidden_aliases` 在可见正文中出现时失败。
2. 需要首次说明的英文或缩写在页面第一次出现时，必须匹配注册表中的 `first_use`。
3. 第一次说明之后，只允许 `subsequent_use` 和 `allowed_aliases`。
4. 未登记且不属于结构性例外的连续拉丁词组被报告为“未知术语”，不得静默进入正文。
5. 大小写、复数、连字符和斜杠按术语记录处理，不做跨术语的猜测性归一化。
6. 检查器一次报告全部问题，禁止只输出首个命中。

错误格式：

```text
<path>:<line> [<term-id-or-unknown>] "<matched>" -> "<expected>"
```

门禁只报告，不自动替换。技术术语可能一词多义，机械修复会改变事实含义。

### 局部例外

优先通过注册表表达合法专名、缩写和代码字面量。确实无法登记的单次用法可以使用结构化局部例外，但必须同时包含：

- 规则编号；
- 非空理由；
- 精确到一次命中的范围。

禁止整文件豁免，禁止无理由 suppression，禁止用 baseline 或 snapshot 接受新增违规。

## 图示术语治理

图中可见文字属于读者文案，适用相同规则。

- Mermaid：检查 MDX fence 中的可见标签，语法标识符不参与检查。
- Draw.io + SVG：同时检查可编辑源和发布 SVG，确保文字一致。
- 位图：生成前使用闭集文字清单；生成后进行人工文字核对，并在视觉验收报告中记录。位图不依赖 OCR 作为唯一门禁。
- 图片 alt 与图注：按普通正文检查。

首页路线图属于概念性位图，继续使用项目既有手绘编辑语言。此次只替换术语，不改变已批准的构图、颜色、节点关系和主题适配。

## 存量正文清理

清理按风险而不是按字符串批量进行：

1. 首页、README、根目录页和标题；
2. 正文小标题、表格标签、图片 alt、图注和 Mermaid 标签；
3. 普通叙述中的裸英文；
4. 同一术语的大小写、连字符和译名不一致；
5. 已登记术语的首次出现与后续使用。

质量属性场景的六个固定标题原子更新为：

- `来源（Source）`
- `刺激（Stimulus）`
- `环境（Environment）`
- `对象（Artifact）`
- `响应（Response）`
- `响应度量（Response Measure）`

对应内容 schema、11 篇质量属性文章和测试必须在同一任务中更新，不能只改正文。

以下属于已知高优先级问题：

- 首页独立英文标签与未来方向副标；
- `Safety`、`Persistence Ignorance`、`Secure by Design` 等裸英文标题；
- `Retry`、`Backoff`、`Handoff`、`Supervisor` 等未按页面首次说明的术语；
- Mermaid 中的 `and`、`Note` 和完整英文句子；
- `human in the loop` 与 `human-in-the-loop` 等拼写漂移；
- arc42 官方章节名只有英文、没有中文表格标签。

历史 `docs/`、测试夹具中的演示英文、代码样例和外部引用原题不纳入存量清理。

## 贡献约束

README 和拉取请求模板必须提醒协作者：

1. 写作前检索 `/terminology` 和 `data/terminology.json`；
2. 已有术语使用规范中文主称；
3. 新术语先登记，并说明翻译依据和使用边界；
4. 首次出现使用批准格式；
5. 图中文字、alt 和图注同样接受术语检查；
6. 运行 `npm run verify`，不得通过放宽规则或整文件豁免绕过失败。

## 测试策略

实施严格遵循测试先行：

1. 先为注册表解析器编写失败测试，覆盖 schema、冲突和确定性排序。
2. 再实现最小解析器，使注册表测试通过。
3. 先为术语页投影编写失败测试，再实现组件和页面。
4. 先为可见文本检查编写正反例，确认当前内容因已知违规失败。
5. 逐组清理存量内容，使同一门禁转绿。
6. 先更新首页合同测试，再改首页文案和图片引用文字。
7. 对路线图图片执行浅色、深色、桌面和移动端视觉核对。
8. 最后运行完整 `npm run verify`，确认生成物、链接、类型检查和生产构建全部通过。

至少覆盖以下合法反例：

- 行内代码与围栏代码；
- 命令和配置键；
- URL、路径和邮箱；
- 产品官方名称；
- 已登记协议缩写；
- 外部链接中的文献原题；
- 直接引文；
- Mermaid 语法标识符。

至少覆盖以下失败样例：

- 裸英文普通术语；
- 首次出现只有缩写；
- 禁用别名；
- 未登记拉丁词组；
- 无理由局部例外；
- Mermaid、SVG 或 Draw.io 中的不规范可见标签。

## 验收标准

- `/terminology` 可访问，并且全部术语由唯一注册表渲染。
- 术语注册表在非法 schema、冲突或重复项时失败。
- 首页和 README 使用相同的规范名称与首次出现格式。
- 首页不再出现“基础与质量”或独立的 `FEATURED NOTE`。
- 两张首页判断路径图片只把“基础与质量”替换为“需求与约束”，浅色和深色版本构图一致。
- 94 篇现有正文中，检查范围内达到零个未说明违规。
- 固定质量属性场景标题、schema 与测试保持一致。
- 新增正文自动进入术语扫描，无需维护静态文件清单。
- 错误信息包含文件、行号、规则和建议主称。
- README 与拉取请求模板明确贡献规则。
- `npm run verify` 全部通过，Docusaurus 生产构建成功。
- 术语页和首页在 `1440×1000` 与 `390×844` 的浅色、深色主题下无页面横向溢出，图片和术语表可读。

## 风险与控制

- **机械翻译改变含义：** 只清理已审定术语；检查器不自动修复。
- **未知英文误报：** 结构性排除代码、引用和字面量；术语通过注册表分类。
- **注册表与页面漂移：** 页面直接消费注册表，生成和检查链验证确定性结果。
- **首次出现难以判断：** 以单个页面为边界；标题算该页面第一次出现。
- **产品专名被错误翻译：** 专名保留官方拼写，首次出现只补充中文类别说明。
- **图片成为检查盲区：** 文本闭集、源文件检查和人工视觉报告共同覆盖，不伪造自动 OCR 保证。
- **局部例外失控：** 只允许单次命中、有理由的结构化例外，禁止文件级 suppression。
- **一次性清理范围过大：** 按用户可见风险分组实施，每组独立测试和评审；最终门禁仍要求零未说明违规。
