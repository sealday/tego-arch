# DDD-01 战略 DDD 总览设计

日期：2026-09-08  
状态：已批准，待实施计划  
范围：E5 首篇 P0；仅交付 DDD-01，不提前创建 DDD-02

## 1. 目标与非目标

本轮发布 `/patterns/ddd-01`，用一个明确标注的说明性订单履约场景，演示如何从语言冲突识别子域、形成候选限界上下文，并用 Context Map 表达上下游方向、契约与翻译责任。主要读者是需要评估现有业务边界的架构师、技术负责人和领域专家。

文章交付的是一组可验证、可被反证的领域边界假设，不是微服务拆分图、组织重组方案或数据库切分清单。它不实现订单系统，不进入聚合、实体和值对象的战术设计，不把示例中的核心子域分类写成行业通用答案，也不虚构企业、事故、指标或生产经验。

## 2. 已批准决策

- 使用“语言冲突 → 业务能力 → 边界 → 关系”的推导主线。
- 固定五个候选边界：销售订单、库存承诺、支付结算、履约配送、客户支持。
- 场景为本站原创说明性场景；来源只支持 DDD 定义、关系模式和分析方法。
- 先呈现不同团队对“订单完成”等词的冲突，再建立各上下文的本地统一语言。
- 每个候选上下文必须给出本地语言、不变量、权威事实和独立变化原因。
- Context Map 必须表达方向、契约、翻译责任和失败边界，不能只画五个方框。
- 子域分类采用条件化判断；核心、支撑、通用取决于具体公司的竞争方式与业务复杂度。
- 使用 Draw.io + SVG 主图与两张高密度表；固定版本和来源适用范围进入证据卡。

## 3. 学习问题与保留判断

正文回答五个问题：

1. 为什么同一个“订单”词汇会在不同业务责任中产生互相矛盾的状态？
2. 子域、限界上下文和统一语言分别解决什么问题，为什么不能相互替代？
3. 如何用规则、数据权威与变化来源提出候选边界？
4. Context Map 如何记录上下游权力、契约和模型翻译，而不退化成系统调用图？
5. 如何用业务流程、失败场景与组织证据验证或否定候选边界？

读者必须保留的判断是：统一语言不是全公司唯一词典；限界上下文不是微服务、团队或数据库的同义词；子域属于问题空间，限界上下文是模型适用边界；Context Map 记录边界之间的关系及其代价。边界是需要持续验证的设计假设，而不是一次研讨会永久产出的事实。

## 4. 说明性订单履约范围

场景固定包含五类业务责任：接受商业订单、承诺库存、处理资金动作、执行配送、处理客户补救。开篇冲突固定使用“订单已完成”：销售订单可能指商业承诺已经成立，履约配送可能指货物已经交付，支付结算可能仍等待结算或退款窗口收敛。

说明性流程为：销售订单接受购买意图；库存承诺独立决定是否预留；支付结算登记并确认必要的资金动作；履约配送在所需前置条件满足后建立任务；客户支持读取组合视图，并把取消、退款、库存释放或补救命令交回相应事实所有者。

该流程只用于检验边界和责任，不能证明实际企业流程、性能、团队结构或服务拓扑。任何未知外部支付结果都必须回到支付事实所有者查询或进入明确的人工终态，不能由销售订单猜测成功。

## 5. 子域分析与条件化分类

文章先按业务目标、规则复杂度、变化来源和差异化价值识别子域，再讨论其类型。分类不由技术难度、代码数量或服务数量决定。

- 若公司的竞争优势来自可售承诺、履约时效或复杂订单承诺，相应子域可以是核心子域。
- 支付通道连接通常更接近通用能力，但公司的授信、费用、退款或风险规则仍可能形成核心或支撑子域。
- 客户支持不能因为使用通用工单产品就被视为没有领域模型；补救政策和跨上下文协调仍需明确责任。

正文必须给出反证：若一个所谓核心子域没有独特规则、没有持续领域投入，也不能解释竞争差异，就应重新分类。分类变化不自动要求立即改变部署边界。

## 6. 五个候选限界上下文

### 销售订单

拥有购买意图、价格承诺、订单接受、取消资格与商业订单状态。它不能直接拥有库存数量、支付机构状态或配送任务状态。

### 库存承诺

拥有可承诺数量、预留、缺货、替代与释放规则。销售订单只能请求承诺并接收结果，不能越过边界写库存事实。

### 支付结算

拥有授权、扣款、退款、结算、对账和外部支付不确定结果。外部支付提供方的模型由该上下文内部的 Anti-Corruption Layer 翻译。

### 履约配送

拥有拣货、打包、交接、运输、交付和履约例外。它接收履约所需的已确认事实，但不重新判定商业订单是否成立。

### 客户支持

拥有诉求、补救方案、退换货协调和人工例外。它可以读取组合视图，却必须通过相应事实所有者执行退款、取消或释放等动作。

两张正文表中的第一张逐行固定记录：上下文、本地术语、主要不变量、权威事实、变化来源、边界反证。正文不能把表中字段简化成数据实体清单。

## 7. Context Map 关系设计

销售订单发布已接受的商业承诺；库存承诺与支付结算分别返回独立业务决定；履约配送消费建立任务所需的已确认事实；客户支持读取面向补救的组合视图并把改变事实的命令交回所有者。

关系模式必须按实际协作含义选择：

- Customer/Supplier 仅用于下游优先级真实进入上游计划的协作关系，不能作为任意调用箭头的标签。
- Open Host Service 与 Published Language 用于上游向多个消费者提供稳定集成入口和公开语言。
- Anti-Corruption Layer 标在承担翻译责任的下游或外部适配边界，不能与 Customer/Supplier 无依据地叠加。
- 组合视图只提供用途受限的读取模型，不表示共享数据库、共享领域对象或写入权转移。

第二张正文表逐行固定记录：上游、下游、交换事实、关系模式、契约所有者、翻译位置、失败影响、反证或重画条件。

## 9. 图示与响应式设计

格式决策为 `Draw.io + SVG`。主图包含五个上下文、一个只读组合视图、一个外部支付方、两个以上系统边界和多条带关系标签的有向连接；它是核心教学资产，位置、线型与标签共同承担语义，满足 Draw.io 路由条件。

建议路径：

- `diagrams/ddd-01-strategic-ddd-context-map.drawio`
- `static/img/diagrams/ddd-01-strategic-ddd-context-map.svg`

图的中心为销售订单；库存承诺与支付结算位于其上游协作侧，履约配送位于承诺消费侧，客户支持及组合视图位于下方，外部支付提供方位于系统边界外。每条线同时标出交换事实、方向和关系模式，不依赖颜色区分。图例明确 U/D、C/S、OHS、PL、ACL，并说明关系模式不是传输协议。

主图和两张表形成三个具名、可聚焦、可横向滚动的语义区域。图示必须在 800px 文章宽度和移动宽度验证文字、箭头、端点、边界、图例、暗色主题、色盲可辨性、局部滚动与页面无横向溢出。

## 10. 证据、来源与版权边界

主要定义来源为 Eric Evans 的 DDD Reference。它用于支持子域、统一语言、限界上下文、Context Map 与关系模式定义，并遵守其 CC BY 4.0 许可边界。Martin Fowler 的 Bounded Context 与 Ubiquitous Language 页面用于辅助解释大型模型的内部一致性和语言演化。

Context Mapper 官方文档只用于核对关系表示、方向和组合语义；工具的 validator 规则不是 DDD 唯一规范。Microsoft 的领域分析材料只辅助说明战略分析先于服务识别、边界需要持续演化；不能用其微服务语境证明限界上下文天然等于微服务。

说明性订单场景、五边界划分和主图均为本站综合设计，必须标记 `说明性场景`、`基于证据的推断` 或 `个人分析`。不使用微信文章作为来源或证据。原创 Draw.io/SVG 按仓库规则登记，禁止复制外部图、Logo、品牌视觉、水印或原始构图。

## 11. 失败、验证与重画条件

文章至少覆盖以下失败信号：

- 同一术语在一个候选上下文内部仍有互斥含义；
- 一个业务不变量必须跨多个边界同步写入才能成立；
- 多个上下文都宣称拥有同一权威事实；
- 下游只能复制上游内部模型，无法表达自己的本地语言；
- 所谓独立边界总是联动变更、联动发布或由同一规则驱动；
- 组合视图逐渐获得写入权，成为隐蔽共享模型；
- ACL 没有明确所有者，翻译失败无人处理；
- Context Map 只剩协议与调用方向，无法解释团队协作和模型代价。

发现这些信号时必须重访语言、不变量和所有权，允许合并、拆分或重画边界。不能通过增加消息、API、共享表或更多服务掩盖模型冲突。

图示测试锁定 Draw.io/SVG 的节点、分组、端口、waypoint、marker、关系标签、图例、层序、有效样式、几何净空和语义同步。来源测试锁定身份、许可、claim role、原始插图登记、可见锚点与远程健康记录。关系测试只接受真实存在的 reciprocal routes，DDD-02 不得被提前创建或变为可操作链接。

## 13. 完成定义

DDD-01 只有在以下条件全部满足时才能完成：

1. 不打开来源也能理解子域、统一语言、限界上下文和 Context Map 的区别与推导顺序。
2. 五个候选上下文都有本地语言、不变量、权威事实、变化来源和反证条件。
3. 子域分类保持条件化，没有把技术复杂度或服务数量当作核心子域判据。
4. Context Map 的每条关系都有方向、交换事实、契约和翻译责任。
5. 说明性流程不绕过事实所有者，不借共享数据库偷换集成。
6. 不把限界上下文等同于微服务、团队、代码仓库或数据库。
7. Draw.io/SVG、两张表、来源、许可、术语和真实 reciprocal 关系全部闭合。
8. 定向与完整验证、代码/安全、内容/版权、架构三类独立评审全部通过。
9. Stage A 与 Stage B 的 exact-head Pages、HTTP 和四态生产功能证据真实可复核。
10. DDD-01 标为 complete 时仍不创建或发布 DDD-02。
