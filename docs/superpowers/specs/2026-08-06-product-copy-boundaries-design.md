# 面向用户文案边界设计

状态：Approved

日期：2026-08-06

## 背景

首页与部分内容页仍暴露了设计和维护阶段的内部思考。例如“首页保留方向，实时进度回到 backlog”描述的是页面如何分工，不是读者能获得什么；主题目录中的“本页从机器可读主题清单生成”暴露实现来源；学习路径中的“后续待补”把内部内容计划直接呈现为产品正文。

这些表达会让最终产品像项目工作台或设计稿，而不是已经发布的架构学习产品。本次变更建立一条可执行边界：面向读者的页面只解释价值、证据、范围和可采取的下一步，不解释团队如何组织页面、生成内容或管理待办。

## 目标

- 移除首页和内容页中的设计过程、实现过程与内部待办语言。
- 保留公开项目进度入口，但使用读者可理解的“查看项目进度”。
- 将学习路径中的内容待办改写为读者导向的延伸问题。
- 为首页与全部 MDX 内容建立自动化文案边界检查，阻止同类表达再次进入产品。
- 让失败信息直接指出文件、行号、规则类别和命中文案。

## 非目标

- 不禁止“本文证据范围”“本站分析”等必要的编辑和证据边界。
- 不禁止架构领域中的正常 `backlog`，例如消息积压、队列 backlog 或方法论讨论。
- 不扫描 `docs/`、测试说明、设计规范、评审记录和内部 backlog；这些文件本来就面向协作者。
- 不借此重写案例论证、来源卡、版本边界或页面信息架构。
- 不引入新的运行时依赖或内容处理框架。

## 文案分类

### 必须移除

1. **页面分工说明**
   - 例：“首页保留方向”
   - 例：“实时进度回到 backlog”
   - 原因：描述设计者如何安排信息，而不是读者获得的价值。

2. **实现来源说明**
   - 例：“本页从机器可读主题清单生成”
   - 例：“计划主题仍由长期 backlog 跟踪”
   - 原因：暴露生成管线和内部事实源。

3. **内部内容待办**
   - 例：标题“后续待补”
   - 例：该标题下以“补充……”开头的项目任务。
   - 原因：把作者的内容计划当成读者正文。

4. **内部工具名称作为行动标签**
   - 例：“查看实时 backlog”
   - 原因：行动标签应说明用户目的，而不是维护工具。

### 必须保留

- 固定版本、来源截断日期和证明边界中的“本文”。
- 标注原创推断时的“本站分析”或等价证据标签。
- 架构机制中的正常 `backlog`、`TODO`、pending state 等领域术语。
- 对上游源码中 TODO、失效页面或未证实能力的事实说明。

## 面向用户的改写

### 首页

- 路线图说明改为直接描述研究路线连接的内容，例如：
  - “初版沿一条可验证的研究路线展开，连接基础、建模、治理与学习闭环”
- 公开进度入口保留原链接，标签改为：
  - “查看项目进度”
- 历史快照、图例语义和发布门槛说明保留，因为它们帮助读者正确解释图片。

### 主题目录

以下目录删除生成来源和内部 backlog 说明：

- `content/concepts/index.mdx`
- `content/methods/index.mdx`
- `content/modeling/index.mdx`
- `content/principles/index.mdx`
- `content/quality-attributes/index.mdx`
- `content/styles/index.mdx`

统一改为读者导向的浏览说明：

> 选择已发布主题进入正文，并沿关联内容继续学习。

### 学习路径

以下页面将“后续待补”改为“延伸问题”：

- `content/paths/07-cloud-native-platform.mdx`
- `content/paths/08-collaborative-state-frontend.mdx`
- `content/paths/09-edge-physical-agents.mdx`
- `content/paths/10-agent-platform-gateway.mdx`

每条“补充……”任务改写成问题句。问题保留原主题和事实边界，但把作者待办转换成读者可用于继续研究或评审系统的检查项。

## 自动检查设计

新增一份独立的产品文案边界测试，扫描：

- `src/pages/index.tsx`
- `content/**/*.mdx`

检查分两层：

1. **首页源码合同**
   - 禁止已确认的页面分工表达和“查看实时 backlog”。
   - 要求存在“查看项目进度”及新的读者价值说明。

2. **MDX 可见文案扫描**
   - 读取每个 MDX 文件。
   - 排除 front matter、围栏代码块、HTML 注释和 Markdown 链接地址。
   - 对剩余可见文本应用窄规则：生成来源说明、内部 backlog 跟踪说明、`## 后续待补`，以及该内部段落中的任务式“补充……”。

规则采用精确语义模式，不做全局关键词禁用。新增规则必须附带一个真实产品文案示例和一个不应命中的合法反例。

每个失败项输出：

```text
<relative-path>:<line> [<rule-id>] <excerpt>
```

一次测试报告全部命中，避免修复一个后才发现下一个。

## 测试策略

1. 先新增文案边界测试并在当前内容上运行，确认它因已知首页、目录和学习路径表达而失败。
2. 改写首页与 MDX 文案，使同一测试转绿。
3. 增加内存样例，证明以下内容不会被误报：
   - Kafka queue backlog；
   - 固定源码中的 TODO；
   - “本文以固定版本为证据范围”；
   - “本站分析”证据标签。
4. 运行现有首页合同、内容验证、链接检查、类型检查和生产构建。

## 错误处理

- 文件读取失败时测试必须失败，不得跳过文件。
- MDX 结构无法安全归一化时报告文件，不得把未解析内容视为合格。
- 检查器不自动改写内容；文案修改必须由作者审阅，避免机械替换改变事实含义。

## 验收标准

- 最终首页不出现“首页保留方向”“实时进度回到 backlog”或“查看实时 backlog”。
- 首页仍能通过“查看项目进度”访问公开进度记录。
- 六个主题目录不暴露生成管线或内部 backlog。
- 四条学习路径不再出现“后续待补”或作者任务式“补充……”。
- 案例中的证据范围和领域 `backlog` 用法不被删除或误报。
- 新测试能报告文件、行号、规则类别和上下文。
- 完整仓库验证通过，且不新增依赖。

## 风险与控制

- **误报正常技术术语：** 使用上下文模式，不禁止单个词。
- **规则只覆盖当前原句：** 规则按语义类别维护，并用真实正反例锁定意图。
- **任务句改写造成事实变化：** 只改变叙述视角，不新增完成状态、来源或保证。
- **未来新增页面漏扫：** 通过递归发现 `content/**/*.mdx`，不维护静态文件清单。
