# Tego Arch 静态本地搜索设计

**日期：** 2026-08-28  
**状态：** 已确认，待实施计划  
**适用范围：** Tego Arch Docusaurus 站点

## 1. 背景

Tego Arch 当前使用 Docusaurus 3.10.2，公开内容位于 `content/`，由 docs 插件挂载到根路由 `/`，并通过 GitHub Pages 发布到 `/tego-arch/`。站点目前约有 108 篇正式 MDX 内容，但没有站内搜索。

首期搜索的目标是提供中文优先的关键词检索，同时保持纯静态部署：不增加搜索服务器、托管账号、运行时密钥或查询遥测。搜索只覆盖面向读者的正式内容，不覆盖内部规格、评审材料或生成的来源台账页面。

## 2. 决策

采用 `@easyops-cn/docusaurus-search-local`，以 Docusaurus 主题插件的方式集成。

选择它的原因如下：

- 支持 Docusaurus 3 和 React 19；
- 构建时生成静态索引，符合 GitHub Pages 部署模型；
- 同时支持英文与中文索引，并为中文提供 Jieba 分词和用户词典；
- 已包含导航栏搜索框、键盘交互、即时结果与完整结果页；
- 当前内容规模不需要独立搜索服务。

未选择的方案：

- **Pagefind：** 中文分词和分片索引能力较好，但需要在 Docusaurus 构建后额外生成索引，并自行集成 React 搜索界面。它是内容规模显著增长后的备选方案。
- **自建 MiniSearch 索引：** 控制力最高，但需要自行维护内容抽取、中文分词、排序、界面、路由跳转和可访问性，首期成本与收益不匹配。
- **Algolia DocSearch、Typesense 等托管方案：** 能提供更强的排序、分析或语义检索，但不符合首期零后端、零账号的约束。

## 3. 架构与数据流

搜索与站点共享同一条构建和发布流水线：

```text
content/*.mdx
      ↓ Docusaurus production build
静态 HTML + 带内容哈希的本地搜索索引
      ↓ GitHub Pages artifact
浏览器按需加载索引 → 本地匹配 → 跳转到文章或章节
```

搜索不是内容数据的第二套事实来源。文章标题、章节和正文仍来自 Docusaurus 生成的页面；插件只在生产构建期间抽取这些页面并生成可查询索引。

运行时查询只在浏览器内执行，不发送查询词，也不依赖站外 API。搜索索引加载失败不得影响正文、侧边栏或普通导航。

## 4. 索引边界与配置

插件配置遵循以下约束：

| 配置 | 设计值 | 原因 |
| --- | --- | --- |
| `indexDocs` | `true` | 索引正式 docs 内容 |
| `indexBlog` | `false` | 站点未启用博客 |
| `indexPages` | `false` | 排除首页和自定义生成页面 |
| `docsRouteBasePath` | `/` | 与当前 docs-only 根路由一致 |
| `docsDir` | `content` | 使索引哈希绑定正式内容目录 |
| `language` | `['en', 'zh']` | 同时处理中文与英文技术术语 |
| `hashed` | `filename` | 内容变化时生成新文件名，避免旧索引缓存 |
| `searchResultLimits` | `8` | 控制即时结果密度 |
| `searchResultContextMaxLength` | `80` | 提供足够但不过长的上下文 |
| `explicitSearchResultPath` | `true` | 显示命中章节路径 |
| `fuzzyMatchingDistance` | `1` | 容忍小范围输入错误 |
| `highlightSearchTermsOnTargetPage` | `false` | 避免跳转后持续高亮干扰正文 |
| `searchBarShortcutKeymap` | `mod+k` | macOS 使用 Command，其他平台使用 Ctrl |
| `askAi` | 不配置 | 避免外部服务和密钥依赖 |

主题保留已有 Mermaid 支持，并增加本地搜索主题。搜索入口位于导航栏右侧、GitHub 链接之前。GitHub Pages 的 `baseUrl: '/tego-arch/'` 必须由生产构建与浏览器验收覆盖，禁止在搜索组件中硬编码根域路径。

`docs/` 下的规格与评审文件不属于 Docusaurus 内容目录，因此不会进入索引。由 `source-ledger-pages` 插件生成的页面也因 `indexPages: false` 被排除。

## 5. 中文词典

新增一个独立、版本化的 UTF-8 Jieba 用户词典。词典路径由 `zhUserDictPath` 指向，不把大段词典内联进 Docusaurus 配置。

首批词典包含约 30–50 个容易被错误切分的稳定架构术语，例如：

- 限界上下文
- 事件风暴
- 模块化单体
- 微前端
- 架构适应度函数
- 智能体循环

词典遵守 Jieba 用户词典格式：一词一行，可选词频和词性，文件编码为 UTF-8。英文缩写和包含空格的英文术语由英文索引管线处理，不为它们伪造中文词条。

词典采用人工维护。只有当正式内容引入稳定领域术语，并且搜索验收表明默认分词不可靠时才新增词条；不从标题或正文自动批量生成词典。自动化检查词典格式、重复项和规定的核心词条。

## 6. 用户交互

- 用户可点击导航栏搜索框，或使用 `⌘K / Ctrl+K` 聚焦搜索。
- 输入后显示最多 8 条即时结果；每条包含文章标题、命中章节路径和上下文片段。
- 结果中的匹配文本高亮，但打开目标文章后不继续高亮正文。
- 用户可用方向键移动选择，用回车打开结果，也可进入完整结果页。
- 桌面端与移动端均使用插件提供的响应式弹窗，不为首期维护第二套搜索界面。
- 空查询不展示推荐内容；无结果和完整结果页使用明确的简体中文文案。
- 首期不提供分类筛选、搜索历史、热门词、查询分析或 AI 问答。

站点 locale 为 `zh-Hans`，固定采用的插件版本 0.55.3 已提供对应翻译。实现时通过浏览器确认这些文案生效；只有发现缺失或错误时，才在站点的 `zh-Hans` 翻译资源中显式覆盖相应键值。

## 7. 匹配与排序验收

搜索沿用插件的 Lunr 排序和中文分词管线。首期不 fork 插件或实现自定义排序器。验收关注用户结果，而不是锁定内部评分数值：标题或章节直接命中的文章应排在只命中正文的文章之前，目标文章应出现在前三条结果中。

首批代表性查询：

| 查询 | 预期结果 |
| --- | --- |
| `微前端` | 前三条包含微前端架构或 single-spa 案例 |
| `限界上下文` | 前三条包含 DDD Context Map |
| `CQRS` | 前三条包含命令查询职责分离文章 |
| `适应度函数` | 能找到架构适应度函数方法文章 |
| `Kubernetes` | 能找到 Kubernetes reconciliation loop 案例 |
| 单字符误输入 | 仍返回与原词相关的合理结果 |
| 不存在的词 | 显示中文无结果状态 |

如果插件默认排序无法满足上述内容级验收，先检查词典、标题和章节抽取，再评估最小配置调整。首期不因单个排序问题直接转向自建搜索引擎。

## 8. 失败处理

- 索引是正式发布产物。插件配置、词典解析或索引生成失败时，生产构建必须失败。
- 不允许发布只有搜索入口但缺少索引文件的构建结果。
- 浏览器端索引请求失败时，站点正文与导航仍可使用。插件未暴露索引加载失败的界面回调；首期不复制或 fork 搜索组件来增加自定义失败文案，搜索在该次网络故障期间可以保持不可用。
- 空查询不加载或执行无意义搜索。
- Ask AI 保持未配置，生产构建和浏览器网络检查中不得出现对应 API 请求。
- 首版记录索引原始体积与传输压缩体积作为基线。后续测试报告显著增长，但在获得基线前不设置任意的绝对失败阈值。

## 9. 测试与发布验收

### 9.1 自动化测试

1. **配置契约**
   - 依赖和主题配置存在；
   - docs、blog、pages、路由、目录、语言和哈希配置符合本设计；
   - Ask AI 未配置。
2. **词典契约**
   - 文件为有效 UTF-8；
   - 每行符合 Jieba 用户词典格式；
   - 没有重复词；
   - 约定的核心术语存在。
3. **构建产物**
   - `npm run build` 成功并生成带哈希的搜索索引；
   - 构建页面通过 `/tego-arch/` 下的正确地址加载索引；
   - 正式内容进入索引，首页、自定义来源台账和内部 `docs/` 文件不进入索引。
4. **缓存行为**
   - 在隔离 fixture 中改变受索引内容后，生成的索引文件名或内容哈希发生变化。
5. **全量回归**
   - `npm run verify` 全部通过。

### 9.2 浏览器验收

在本地生产构建和发布后的 GitHub Pages 各执行一次：

- 运行代表性查询并检查前三条结果；
- 检查鼠标、方向键、回车和 `⌘K / Ctrl+K`；
- 检查桌面端与移动端布局；
- 检查亮色与暗色主题；
- 检查完整结果页、空查询与无结果状态，并确认阻断索引请求不会破坏正文和普通导航；
- 检查结果链接与索引请求均正确保留 `/tego-arch/` 基础路径；
- 检查没有外部搜索或 Ask AI 请求。

## 10. 发布方式与演进边界

实现与当前 GitHub Pages 工作流一起发布，不新增部署 job 或基础设施。发布前必须通过自动化测试、本地生产浏览器验收和完整 `npm run verify`；发布后再对生产地址执行关键查询冒烟测试。

当出现以下任一信号时，重新比较 Pagefind 或托管搜索：

- 索引体积或加载时间开始明显影响首次搜索；
- 内容达到当前规模的数倍，并需要按分类分片或过滤；
- 需要搜索分析、同义词治理、跨站索引或权限控制；
- 需要语义检索或基于内容的问答。

迁移时应保留搜索入口、快捷键和结果展示的用户约定，把索引生成与查询适配封装在搜索实现边界内，避免搜索提供方渗透到内容模型。
