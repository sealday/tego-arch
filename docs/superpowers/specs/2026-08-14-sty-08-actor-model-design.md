## 1. 目标与非目标

本主题新增一篇可独立阅读的架构风格文章，回答 Actor Model 与线程、普通消息消费者、事件驱动架构和微服务的区别。文章以订单履约为统一案例：每个订单由一个具有稳定逻辑身份的 Actor 管理，命令进入邮箱后串行处理，Actor 独占自己的可变状态，并通过消息与库存、支付和通知边界协作。

核心判断是：Actor Model 通过逻辑身份、私有状态、异步消息和逐条行为执行降低共享状态并发复杂度，但它不自动提供持久化、端到端有序、可靠投递、恰好一次、全局事务、网络透明或业务恢复。邮箱串行只是一个 Actor 内部的处理约束；运行时调度、消息传输、监督、重启、重新定位和状态恢复分别属于不同责任层。

文章保持框架中立。Akka、Microsoft Orleans 和 Erlang/OTP 只作为可核查的实现例证或边界证据，不进行产品排名、API 教程或供应商选型，也不把任一框架的默认行为推广为所有 Actor 系统的模型公理。

本轮不实现 STY-09、STY-14 或待办中的完整消息交付语义专题，不新增 Actor 运行时、框架依赖或示例应用，不把每个类、请求、数据库行或微服务都机械映射为 Actor，也不宣称 Actor 是线程、事件消费者、微服务或状态机的同义词。

## 2. 读者问题与核心对照

文章必须让首次接触 Actor Model 的工程师回答以下五个问题：

1. Actor 的身份、状态、邮箱、行为和监督分别解决什么问题？
2. 同一个 Actor 的串行处理与线程互斥、消息队列消费和事件传播有什么不同？
3. Actor 与微服务如何组合，为什么 Actor 不能自动形成独立部署或业务边界？
4. 邮箱、监督、位置透明、持久化、消息顺序和投递各自保证什么，又不保证什么？
5. 哪类业务实体适合 Actor，哪些查询、事务、生命周期或运维条件要求停止采用？

正文使用固定四组对照：

| 对照对象 | Actor Model 的决定性区别 | 不得外推 |
| --- | --- | --- |
| 线程与锁 | Actor 是逻辑并发单元，以私有状态和消息交互；运行时可在不同线程上调度其行为 | Actor 不固定绑定线程，也不意味着无竞争资源或无需容量控制 |
| 普通消息消费者 | Actor 具有稳定逻辑身份与封装状态，消息按目标身份进入其邮箱 | 共享队列消费者实例不一定对应长期业务实体；邮箱也不自动持久化 |
| 事件驱动架构 | Actor 回答谁拥有状态、谁处理消息；事件驱动回答事实如何传播、携带什么以及消费者如何耦合 | 使用事件不等于使用 Actor；Actor 消息也不一定是领域事件 |
| 微服务 | Actor 通常是更细粒度的运行时实体，可按订单、设备或会话建模 | Actor 不天然具有独立制品、部署、数据边界、团队所有权或公开服务合同 |

四组对照是机制分析，不构成成熟度阶梯。线程、队列、事件、Actor 和微服务可以在同一系统中组合；文章只在责任和保证明确时描述组合，不把术语相似当作架构等价。

## 3. Actor 的五个构件

正文固定解释五个构件，并为每个构件写出正向责任和否定边界：

- **逻辑身份：** 发送者面向 Actor 引用或稳定键发送消息，而不是直接取得内部对象并修改状态。身份可跨激活或位置变化保持，但其生命周期和寻址语义由具体运行时定义。
- **私有状态：** Actor 的可变状态只能由自身行为修改。隔离的是直接内存写入，不是共享数据库、外部服务、静态单例、文件或网络资源；这些资源仍可能竞争或产生一致性问题。
- **邮箱：** 邮箱缓冲发往目标 Actor 的消息，并让 Actor 逐条取得待处理项。邮箱是否有界、持久、优先、FIFO 或会丢弃消息是实现和配置问题，不能从“Actor”一词推导。
- **行为：** Actor 处理一条消息时可以改变内部状态、创建其他 Actor、发送后续消息或改变下一条消息的处理方式。一次行为串行不等于整条业务流程原子，也不保证外部副作用只发生一次。
- **监督：** 负责实体观察子 Actor 或被管理 Actor 的执行故障，并按明确策略重启、停止或升级。监督处理执行单元故障，不代替业务拒绝、补偿、对账、持久化恢复或人工终止。

文章必须区分业务错误与执行故障。库存不足、支付拒绝和订单状态非法是领域结果，应通过消息返回并由业务流程处理；空指针、资源损坏或不可恢复的运行时异常才进入监督策略。不得用“let it crash”掩盖可预期业务分支或重复外部副作用。

## 4. 统一订单案例与正常数据流

统一案例固定订单、库存、支付和通知四个业务边界，并增加订单 Actor、其邮箱、监督者和显式持久化边界。`Order-123` 是逻辑身份示例，不宣称生产系统必须按每个数据库行建立 Actor。

正常路径如下：

1. 调用方向 `Order-123` 发送带操作 ID、关联 ID 和期望订单版本的 `SubmitOrder`；
2. 消息进入该订单 Actor 的邮箱，运行时一次执行一个行为；不同订单 Actor 可以并行运行；
3. 订单 Actor 校验当前状态与版本，持久记录本次决定或待执行步骤，再向库存边界发送预留请求；
4. 收到库存结果后，订单 Actor 推进支付授权；支付成功后确认订单并请求通知；
5. 库存、支付和通知分别拥有自己的权威状态，订单 Actor 只拥有订单状态与履约协调状态；
6. 超时、重复或迟到回复按操作 ID、状态版本与当前阶段判断，不能仅凭消息到达顺序覆盖较新的事实；
7. 通知失败不撤销已确认订单；支付、退款、库存释放和外部通知等不可逆或外部副作用具有独立幂等、查询、对账和人工停止路径。

订单 Actor 的单邮箱可避免同一订单内两个行为同时直接修改其私有内存，却不能提供跨库存、支付和通知的分布式原子提交。并发影响多个订单的共享库存时，库存权威边界仍必须执行自己的并发控制和不变量。

## 5. 邮箱、顺序与投递边界

文章把“收到消息”“进入邮箱”“开始处理”“业务提交”“发送回复”和“外部效果完成”作为六个不同观察点。任何一个观察点都不能自动证明后续观察点已经发生。

最低公共设计按可能重复、迟到、丢失和超时处理消息：

- 每次业务操作具有稳定消息或操作 ID，并传播关联 ID 与必要因果信息；
- 接收者以业务键、操作 ID 和状态版本执行幂等判断；
- 超时表示结果未知，不等于目标未执行；重复发送前先查询、对账或使用目标侧幂等合同；
- 同一发送者到同一接收者的顺序保证若由框架提供，必须注明范围、直接路径、失败与重启条件；不得外推为跨发送者、跨中介、跨节点或重试后的全局顺序；
- 邮箱积压、最老消息、处理耗时、丢弃、死信、重试次数与 Actor 激活数量必须可观测；
- 有界邮箱需要背压、拒绝、降级或溢出策略；无限邮箱不是容量方案。

Akka 的至多一次投递与发送者—接收者对内顺序只作为 Akka 官方实现例证；Orleans、Erlang/OTP 或其他运行时具有各自合同。正文不得把某个框架的保证写成 Actor Model 的统一规范。

## 6. 监督、重启与业务恢复

监督设计至少包含重启、停止和向上升级三种动作，并为每种动作说明适用故障、重启强度或预算、停止条件与人工所有者。无限重启、无预算重试或对同一毒消息反复重启都必须列为禁用行为。

重启后可能出现以下状态：

- 内存状态已丢失，但邮箱中仍有待处理消息；
- 失败消息被丢弃、重新投递或转入隔离，具体行为取决于运行时；
- 已发送的外部请求可能成功、失败或结果未知；
- 持久化状态可能落后于外部效果，或恢复后再次看到旧消息。

因此业务恢复必须独立设计：从事件日志、快照或外部权威存储恢复订单状态；以已持久的流程阶段决定下一动作；查询库存和支付的权威结果；修复毒消息后受控重放；预算耗尽、状态冲突或不可逆效果不明时转人工。监督者不能仅凭异常类型推断支付是否发生，也不能通过重启伪装业务回滚。

## 7. 位置透明与分布式边界

位置透明允许发送者通过逻辑引用或身份与 Actor 交互，而不把当前进程、线程或节点地址写入业务调用代码。它降低寻址和重新放置的耦合，但不能消除以下事实：

- 本地与远程消息具有不同延迟、序列化、容量、失败和安全边界；
- 网络分区、节点退出、目录陈旧、重复激活防护和目标不存在仍需处理；
- 远程传输要求稳定消息合同、版本兼容、身份认证、授权、加密和最小披露；
- 调用者不能用本地函数调用的心智模型理解远程 Actor；超时后结果仍可能未知；
- Actor 重定位或重新激活不自动迁移未持久化内存、外部租约、定时器或正在执行的副作用。

文章将“逻辑位置可隐藏”与“物理故障不可隐藏”并列为位置透明的结论。若业务正确性依赖 Actor 永远位于特定节点、与本地资源共同失效或零延迟通信，必须显式建模放置约束，不得以透明性掩盖它。

## 8. 采用、迁移与停止条件

Actor Model 适合具有大量稳定身份、每个实体独立维护有限状态、单实体命令可串行化、实体之间主要通过异步消息协作，并且活跃集合远小于逻辑实体全集的场景。订单、设备数字孪生、会话和房间是说明性候选，不构成性能或规模保证。

采用前必须回答：Actor 身份如何生成和回收；邮箱是否有界与持久；状态权威在哪里；重启从何恢复；重复和迟到消息如何处理；跨 Actor 查询与不变量由谁协调；外部副作用怎样去重与对账；运行时升级、再平衡和节点故障怎样演练。

从现有微服务或事件驱动系统迁移时，只选择一个具有明确身份和局部串行规则的实体作为试点：先固定消息合同、状态机、持久化和外部权威；再把该实体的共享锁或并发写入口收敛为邮箱消息；最后验证积压、激活、恢复、重放和热点实体。不得先把所有服务或表行改写为 Actor 再寻找边界。

以下情况要求保持现状、收紧范围或停止采用：

- 主要工作是跨大量实体的即时联接、扫描或聚合查询；
- 核心不变量必须跨多个 Actor 同步成立，却没有明确协调、预留或补偿机制；
- 实体没有稳定身份或生命周期，Actor 只会增加寻址与状态成本；
- 热点 Actor 无法分解且单邮箱成为吞吐瓶颈；
- 团队无法运营邮箱积压、监督预算、持久化恢复、集群放置和分布式诊断；
- 采用理由只是“避免写锁”“框架能自动扩缩”或“位置透明意味着不用考虑网络”。
