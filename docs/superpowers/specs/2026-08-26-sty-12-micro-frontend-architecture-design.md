日期：2026-08-26

## 1. 目标与非目标

本轮发布 `/styles/sty-12`，以电商前台的商品、购物车、结算和账户切片说明 Micro-Frontend（微前端）何时能降低跨团队发布协调，以及运行时组合如何同时引入共享浏览器资源、制品兼容、状态所有权和故障恢复成本。文章定位是架构决策指南，不是 single-spa、Module Federation 或其他框架的配置教程。

目标是让读者在不打开外链时也能判断：是否存在真实的独立交付压力；业务切片由谁端到端拥有；Shell、公共运行时和业务后端分别负责什么；共享依赖何时值得集中；制品如何原子提升与回滚；同页失败能隔离到什么程度；何时应继续使用模块化前端单体。

本轮不创建真实电商应用、前端编排框架、制品仓库、清单签名服务、灰度平台、授权系统或 npm 依赖；不把微前端等同于组件库、iframe、微服务、微内核或安全沙箱；不重复现有 `/cases/micro-frontends-single-spa` 的源码状态机导读；不实现 STY-13。

## 2. 已批准决策

- 贯穿场景为电商前台，商品、购物车、结算、账户由不同稳定业务团队负责。
- 文章以架构决策链为主，生命周期和团队拓扑只作为机制证据。
- 主组合方式为浏览器运行时组合；服务端组合、构建时组合和 iframe 只进入比较表。
- 购物车、订单和账户真相留在权威后端；切片之间只交换稳定标识和版本化合同。
- Shell 只拥有身份上下文、顶层路由、制品清单、挂载槽位、系统级观测和恢复入口。
- 独立发布使用不可变制品与版本化清单原子切换；禁止运行时解析漂移的 `latest`。
- 公共运行时采用最小共享：只纳入体积收益明确、兼容策略成熟且维护者清晰的依赖。
- 故障目标为切片级降级；同一主线程、DOM、同源存储和网络会话不被误写为隔离。
- Shell 只提供会话身份；后端对每个请求重新认证、授权并执行业务校验。
- 单一小团队、统一发布节奏、边界不稳定或缺少平台治理能力时，优先模块化前端单体。

## 3. 读者问题与保留判断

正文回答五个学习问题：

1. 微前端解决的组织和发布问题是什么，哪些表面拆分没有产生独立交付？
2. Shell、业务切片、公共运行时、发布控制面和后端权威系统各自拥有什么？
3. 购物车到结算的数据如何跨切片流动，又不形成可变全局数据库？
4. 制品、共享依赖和合同如何独立升级，同时保持可审计的组合与回滚？
5. 浏览器运行时能隔离哪些失败，哪些风险仍跨切片传播，何时不应采用？

必须保留的判断是：微前端首先是多个稳定业务团队独立交付同一产品的组织与发布选择，运行时组合只是实现手段。代码库数量、框架混用或页面区域数量都不能单独证明需要微前端。若发布仍依赖中央 Shell 排期、全局状态变更仍要求所有团队同步、共享依赖升级仍形成统一发布列车，系统只是把前端单体改造成分布式前端单体。

## 4. 构件、接口与所有权

### Shell

Shell 读取受控版本化制品清单，解析顶层路由，提供业务槽位，传递最小只读身份上下文，安装系统级错误与观测钩子，并展示降级和恢复入口。Shell 不拥有商品、购物车、结算或账户规则，不直接修改切片私有 DOM，不广播完整业务对象，也不替后端授权。

### 业务切片

商品、购物车、结算和账户切片各自由一个稳定团队端到端拥有，包含界面、内部路由、公开前端入口、后端接口合同、流水线、告警、值班和回滚责任。切片只操作自己的 DOM 根节点；不得读取其他切片的私有状态、DOM 结构或构建产物内部模块。

### 公共运行时

公共运行时只接纳体积显著、单实例收益明确并具有兼容矩阵的依赖。每项共享依赖必须有维护者、支持版本范围、升级窗口、弃用期、健康信号和回退策略。领域模型、可变业务状态、无边界工具集合和跨域写入能力不得进入公共层。小型或高变依赖允许重复打包，以换取独立升级。

### 发布控制面

发布控制面接收不可变制品，验证内容身份、来源、合同兼容性和健康探针，再生成一份完整版本化清单。提升与回滚均以整份清单为原子单位；不得逐项拼接未知组合，也不得让生产 Shell 自动追踪 `latest`。

### 权威业务面

商品、购物车、订单和账户后端保存业务真相。切片凭稳定资源 ID 和预期版本读取或提交请求；后端逐请求校验会话、租户、权限、不变量和幂等键。浏览器显示状态不构成业务提交证据，切片挂载成功也不授予跨域权限。

### 观测与恢复面

一次用户旅程可以共享关联 ID，但指标、错误、制品版本、团队所有者、恢复动作和服务目标按切片区分。Shell 只汇总系统视图，不替业务团队决定订单终态。

## 5. 结算数据流与发布流

用户进入结算路由后，Shell 读取当前已批准清单并解析结算制品。Shell 校验制品加载结果和挂载合同，把最小会话上下文与购物车稳定 ID 交给结算切片。结算切片从购物车后端重新读取带版本的权威状态；后端逐请求鉴权并返回可结算快照。用户提交订单时，切片提交幂等键、购物车 ID 和预期版本；订单后端校验不变量并返回权威订单 ID。随后界面只根据订单 ID 查询或订阅结果，不根据本地成功提示推断业务完成。

发布时，业务团队先构建不可变制品并生成内容身份。控制面验证制品、公开入口、公共运行时兼容范围、最低 Shell 版本和健康探针。候选清单在预发布环境完成合同与关键旅程验证后，作为一个新版本原子提升。异常时回退上一整份已知可用清单；回退前端制品不撤销已经发生的订单、支付或库存效果。

跨切片通信默认使用稳定 ID、后端 API、URL 或版本化事件。任何要求同步传递完整可变购物车对象、共享写入全局 Store、读取对方 DOM 或导入私有模块的方案都必须被标记为边界泄漏。

## 6. 故障、隔离与恢复

### 清单无效

清单真实性、内容身份或结构校验失败时，Shell 保持上一已知可用清单，不猜测制品地址，不拼接部分新版本。控制面阻止候选提升并通知清单所有者。真实性可以由受控发布通道或签名机制建立，本文不预设唯一实现。

### 制品加载失败

加载超时、网络失败或完整性不匹配只降级对应槽位，保留顶层导航、身份和恢复入口。商品推荐可以隐藏或使用明确占位；关键结算切片不可用时必须禁止提交，不能展示缓存成功状态。

### 挂载或运行失败

错误边界记录切片名、制品版本、清单版本、路由和关联 ID，清理该槽位并显示明确降级界面。重复重试必须有上限；持续失败时回退清单或引导用户离开受影响旅程。

### 合同不兼容

控制面在提升前验证 Shell、切片和公共运行时的支持范围。若运行时仍遇到未知导出、版本冲突或公开入口不兼容，系统回退整份清单；不得在生产中自动选择“最接近”的版本。

### 后端结果不确定

网络超时不等于业务失败。切片用幂等键、购物车 ID 或订单 ID 查询权威状态；无法判定时进入明确的待确认或人工终态。浏览器不得通过重放无幂等保护的提交来补偿。

### 隔离边界

运行时组合可以隔离制品版本、发布节奏、路由区域、错误展示、回滚和团队责任；不能自动隔离主线程、内存、DOM、全局 CSS、同源存储、网络会话或供应链权限。确需更强隔离时，应评估跨源 iframe、独立 origin、内容安全策略和更窄后端权限，并接受通信、可访问性、性能和体验成本。

## 7. 架构决策链与停止条件

决策链按以下顺序执行：

1. 是否存在至少两个长期稳定、能端到端负责用户价值且需要独立发布的团队？若否，停止并使用模块化前端单体。
2. 业务边界是否已在单体中形成明确公开接口和局部状态？若否，先完成逻辑模块化。
3. 是否真的需要运行时独立上线？若只需代码隔离，使用构建时包组合。
4. Shell 是否能保持薄，并且权威业务状态留在后端？若否，先修复所有权。
5. 是否具备不可变制品、版本化清单、兼容门禁、观测、回滚和跨团队事故响应？若否，不进入运行时组合。
6. 最小共享依赖是否产生可测量收益，且维护者能承担兼容治理？若否，允许局部重复。
7. 同页隔离是否足够？若安全或资源隔离是硬要求，评估跨源 iframe 或独立应用边界。

退出信号包括：每次切片发布仍修改 Shell；共享 Store 或公共业务模型频繁破坏兼容；公共运行时升级要求全员锁步；端到端故障无法定位所有者；独立流水线数量远超真实团队边界；下载、内存和主线程成本超过自治收益。触发后优先合并切片、收窄公共层或回到模块化单体，而不是继续增加编排层。
