# STY-14 架构风格选择矩阵设计

日期：2026-09-07  
状态：已批准，待实施计划  
范围：G009 收官页，仅交付 STY-14；不创建 STY-15

## 1. 目标与非目标

本轮发布 `/styles/sty-14`，使用同一个订单履约系统，在业务增长、局部故障、团队独立交付三种压力下比较 Modular Monolith、Microservices 与 Event-Driven。文章服务于正在决定现有系统是否应拆分、是否应引入异步交互的团队负责人，而不是制作一个脱离上下文的架构风格排行榜。

核心目标是把选择拆成两条独立轴：部署与数据所有权边界，以及同步与事件驱动交互方式。默认从模块化单体开始；只有可测量的独立部署、所有权或故障隔离要求才触发服务拆分；只有确实需要时间解耦、缓冲或多消费者传播时才引入事件。

本轮不实现订单系统、消息基础设施、性能基准、成本模型或组织重组；不声称模块化单体、微服务或事件驱动天然具有更高性能、可用性或团队效率；不把三者写成成熟度阶梯；不创建或发布 STY-15。

## 2. 已批准决策

- 主要读者是评估现有系统演进路径的团队负责人。
- 三次比较共享一个订单履约业务域和完全相同的能力范围。
- 三种压力固定为业务增长、局部故障、团队独立交付。
- 结论形式是“默认起点 + 证据触发器 + 可逆动作 + 停止条件”，不是加权总分。
- Event-Driven 是可叠加的交互机制；模块化单体和微服务都可以采用同步、事件驱动或混合交互。
- 视觉使用部署边界 × 交互方式双轴矩阵，禁止画成从单体到微服务再到事件驱动的线性升级路线。
- 机制事实复用 STY-04、STY-05、STY-06 已治理的一手来源；新增来源仅用于填补确实存在的机制证据缺口。

## 3. 学习问题与保留判断

正文回答四个问题：

1. 订单履约系统当前真正承受的是业务增长、局部故障，还是团队交付压力？
2. 哪些压力要求改变部署与数据所有权边界？
3. 哪些压力只要求把部分同步交互改为事件驱动？
4. 何时应该停止演进，避免为了“先进”而拆分？

读者必须保留的判断是：服务边界和交互方式是两条不同的决策轴。模块化单体不是尚未成熟的微服务；微服务不会自动产生团队自治；事件不会自动解决一致性，也不要求系统先拆成微服务；同步交互在需要即时拒绝或确认时仍然成立。

## 4. 统一订单履约基线

三个压力场景都固定处理五项能力：提交订单、预留库存、登记支付意图、确认履约、发送通知。每种候选结构必须承担相同的命令、状态、失败和恢复责任，不能通过删减业务能力获得比较优势。

订单接受与权限校验需要即时确定结果。库存预留与支付意图必须有明确权威状态和重复请求边界。履约传播、通知和非关键派生工作可以在确有异步价值时采用事件。外部支付副作用不属于本地数据库事务，任何未知结果都必须查询权威状态或进入补偿与人工终态。

场景是本站原创说明性演练，不代表真实客户、事故、吞吐数字、成本收益或生产经验。

## 5. 双轴决策模型

第一轴是部署与所有权边界：

- 模块化单体保留一个部署边界，通过模块 API、唯一写入责任和本地事务管理内部耦合。
- 微服务要求代码、数据权威、部署、容量、故障处置和值班责任能够真实独立；只有网络调用而没有这些独立性不构成有效服务边界。

第二轴是交互方式：

- 同步交互适合调用方必须立即获得接受、拒绝或权威结果的路径，但要承担超时、不确定结果和调用链故障传播。
- 事件驱动适合时间解耦、缓冲和多消费者传播，但要承担交付重复、顺序、积压、重放、毒消息、事件合同演进和消费方恢复责任。

两轴形成四种可行组合：同步为主的模块化单体、单体内异步化、同步协作的微服务、跨服务事件传播。文章不能把任何一个象限写成最终形态。

## 6. 三类压力演练

### 业务增长

先检查热点位置、数据库容量、锁竞争、队列等待、部署频率和模块依赖。若团队与发布节奏仍可协调，优先保持一个部署边界，通过索引、容量治理、模块隔离、派生读模型或单体内异步化解决压力。只有容量或发布证据持续证明某个能力必须独立扩展或部署时，才拆出服务。

### 局部故障

比较本地事务内失败、同步远程调用的不确定结果，以及事件缓冲后的积压与恢复。事件可以隔离非即时工作的时间窗口，但不会消除数据一致性、幂等、毒消息和人工终止责任。只有故障必须由独立运行边界隔离时，才同时改变部署边界。

### 团队独立交付

只有代码所有权、数据权威、发布节奏、容量预算、告警与值班责任都能独立时，微服务才支持团队自治。若共享数据库、联动发布或跨团队审批仍是主路径，拆分只会把组织耦合变成分布式耦合。是否采用事件驱动由时间解耦需求另行决定。

每个场景必须输出当前最小可行结构、需要观测的证据、升级触发条件、可逆动作、停止条件和责任人。

## 7. 迁移触发器与停止条件

触发器必须能被持续观测，而不是使用“系统变复杂”“规模变大”等不可验收描述。候选证据包括：特定模块独立扩容需求、跨模块锁等待、联动发布失败率、故障影响范围、团队等待时间、同步调用未知结果、事件积压年龄、重复副作用和恢复时长。

每次演进只改变一个主要变量：先强化模块边界，或先把一条非关键路径异步化，或先拆出一个拥有独立数据与运行责任的服务。动作必须保留回滚路径和观察窗口。

停止条件包括：证据未达到预先约定阈值；新边界仍依赖共享同步写；独立部署不能减少协调；事件消费者没有恢复所有者；异步化使业务必须等待的结果更难确认；新增基础设施和运行负担超过可观测收益。

## 10. 证据、来源与版权边界

机制事实优先复用 STY-04、STY-05、STY-06 已治理的一手来源与既有 source identity。实施前逐条确认这些记录仍可支持：模块边界和本地事务；独立部署与数据所有权；同步远程调用失败；事件交付、重复、顺序、积压、重放与合同演进。

双轴矩阵、默认起点、触发器与停止条件属于本站综合推断，必须明确标记，不让任何单一来源承担完整选择结论。说明性场景不使用虚构指标。若需要新增来源，只接受能够补足具体机制缺口的一手资料；博客排行、供应商营销对比和二手“最佳实践”不得成为选择证据。

原创 Draw.io/SVG 作为本站插图登记，禁止复制外部图、品牌视觉、Logo、签名、水印或原始构图。正文只使用原创摘要和窄范围事实，不长篇复刻来源文字。
