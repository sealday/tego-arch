## 1. 目标与非目标

本主题新增一篇可独立阅读的架构风格文章，用同一个“订单已提交”事实区分四种容易混淆的事件模式：事件通知、状态转移、事件携带状态和事件溯源。文章的核心任务不是证明事件驱动优于同步调用，而是让读者能够判断：事件表达了什么、消费者还需读取什么、当前状态由谁权威保存、历史事件能否重建状态，以及相应的耦合与恢复成本落在哪里。

这四类是 Tego Arch 为本主题建立的教学比较框架，不宣称是业界唯一或穷尽式分类。事件通知、事件携带状态和事件溯源采用已有模式含义；“状态转移”则专门描述以合法业务状态迁移为核心语义的事件用法。四类可以在同一系统内针对不同业务事实并存，不构成成熟度阶梯，也不要求系统从第一类逐级升级到第四类。

统一案例延续 STY-05 的订单、库存、支付和通知边界，但本主题不重新讲解微服务拆分或完整 Saga。它固定同一业务动作与参与者，改变事件的语义、载荷和状态责任，以隔离真正需要比较的变量。

本轮不实现 STY-07 或 STY-14，不把四类扩展成完整的风格选择矩阵，不新增产品运行时功能，不引入消息产品或云平台依赖，也不把事件代理、Outbox、CQRS、异步处理或事件日志单独等同于事件驱动架构或事件溯源。

## 2. 核心比较模型

全文使用五个固定问题比较四种模式：

1. 消费者收到的是“发生过某事”、一次合法迁移、所需状态，还是权威事件历史？
2. 消费者是否需要回查订单服务？
3. 当前状态的权威来源在哪里？
4. 事件是否参与当前状态重建？
5. 丢失、重复、乱序和模式版本变化分别由谁处理？

四种模式采用以下精确定义：

- **事件通知：** 生产者通知其他系统某个事实已经发生，载荷通常只含事件标识、聚合标识和必要上下文；消费者需要更多信息时回查生产者。生产者不应把必须执行的命令伪装成通知。
- **状态转移：** 事件表达聚合从一个业务状态迁移到另一个业务状态，例如订单从 `PENDING` 变为 `CONFIRMED`，并携带迁移原因、聚合版本或前后状态等校验信息。重点是迁移是否合法、重复迁移如何幂等、乱序迁移如何拒绝或暂存；它描述状态机语义，不意味着事件携带完整业务快照。
- **事件携带状态：** 事件包含消费者完成本地处理所需的状态或变化集，使消费者可以维护本地副本并避免同步回查。消费者拥有自己的派生副本，不因此取得源业务状态的权威写入权。
- **事件溯源：** 聚合的有序事件流是权威写入记录；命令处理通过追加新事件改变状态，当前聚合状态与读取投影由事件回放派生。消息代理中的保留日志、审计表或“事件很多”都不足以证明事件溯源。

文章必须明确三条防混淆边界：状态转移不等于事件携带状态；消息载荷包含完整数据不等于事件溯源；使用消息代理、Outbox 或可重放流只说明传递与保存机制，不自动决定业务状态模式。

## 3. 统一案例与四轮叙事

四轮都从同一个业务事实“订单已提交”开始，并保持订单、库存、支付和通知四个参与者不变。每轮使用相同观察顺序：订单服务产生什么，三个消费者接收什么，消费者怎样获得所需状态，权威数据与本地副本在哪里，重复/乱序/回放怎样处理，以及这种模式何时适用或不适用。

### 3.1 事件通知

订单服务发布最小 `OrderSubmitted` 通知。库存、支付和通知消费者依据订单 ID 回查订单服务获取各自所需数据。该轮突出小载荷、低模式复制和较强运行时回查依赖，并交代通知丢失后的补偿扫描、生产者不可用时的重试/降级，以及避免把“请预留库存”伪装成既成事实。

### 3.2 状态转移

订单服务发布明确的订单状态迁移，例如 `PENDING → CONFIRMED`，附带原因、聚合版本和关联标识。消费者按状态机校验前置状态与版本；重复的同版本迁移幂等忽略，旧版本拒绝，存在缺口时暂存或触发补取。该轮突出业务迁移语义，而不是携带所有订单字段。

### 3.3 事件携带状态

订单服务发布版本化订单状态或消费者所需字段。库存、支付和通知据此更新各自的本地副本或投影，不在正常路径回查订单服务。该轮突出减少时间耦合、降低回查延迟和生产者读负载的收益，同时说明数据复制、陈旧窗口、字段最小化、隐私边界、模式演进与重建成本。

### 3.4 事件溯源

订单聚合不直接把当前状态作为唯一权威记录，而是向按聚合有序的事件存储追加领域事件；命令处理前从事件流与可选快照恢复状态，通过乐观并发追加新事件，再由投影处理器生成订单读取模型，并发布适合外部消费者的集成事件。该轮必须把事件存储与消息代理分开，把领域事件流与对外集成合同分开，并说明回放不得重放支付扣款等外部副作用。

## 4. 组件与数据流边界

文章统一使用以下概念边界：

- **命令：** 表达期望某个明确接收者执行动作，可以被拒绝；不得用过去式事件名称掩盖命令意图。
- **领域事件：** 表达领域边界内已经发生的事实，可用于聚合内部状态演进；不保证适合作为跨边界稳定合同。
- **集成事件：** 面向外部消费者发布的版本化事实合同，可以由领域事件映射产生，并按最小披露原则设计载荷。
- **事件代理：** 负责事件分发、保留、消费位置和重投等传递能力，不自动成为聚合权威状态源。
- **Outbox：** 在本地事务内记录待发布消息，缩小数据库提交与发布之间的一致性缺口；它不提供端到端恰好一次。
- **事件存储：** 在事件溯源模式中保存聚合的权威、有序、追加式事件流，并提供流版本并发控制；普通审计日志或代理日志不自动满足该责任。
- **本地副本与投影：** 都是派生状态。前者服务于跨边界自治读取，后者通常由事件流构建特定查询视图；二者都必须能说明陈旧性、版本和重建责任。

事件流的最低公共信封包含事件 ID、事件类型、发生时间、生产者/来源、聚合或业务键、模式版本、关联 ID 与因果 ID。载荷随四种模式变化；公共信封的一致性不能掩盖业务语义差异。

## 5. 图示设计

格式决策为 **Draw.io + SVG**。主图采用四列并排的比较板，每列对应一种事件模式，每行回答同一个问题。固定列顺序为事件通知、状态转移、事件携带状态、事件溯源，固定观察行至少包括“生产者写入”“事件载荷”“消费者取数”“权威状态”“恢复/回放”。同一订单案例在四列中使用一致参与者与视觉词汇，避免布局差异被误认为架构差异。

四列的决定性路径分别为：

- 事件通知：最小事件进入代理，消费者再回查订单服务；
- 状态转移：带 `from/to`、原因和版本的迁移事件进入消费者状态机；
- 事件携带状态：版本化状态事件直接更新消费者本地副本；
- 事件溯源：命令处理器向事件存储追加事件，回放恢复聚合并构建读取投影，另行映射集成事件。

图中必须显式区分命令、领域事件、集成事件、同步回查、异步传递、事件存储、权威写模型、本地副本和派生投影。正常消费路径与恢复/回放路径使用不同线型，并通过文字、箭头与图例共同编码，不能只靠颜色。事件溯源列不得画成“消息代理就是事件存储”，回放路径不得连接到外部支付副作用。

## 6. 决策矩阵与选择规则

正文结尾提供一张四模式决策矩阵，至少比较：载荷大小、同步回查依赖、时间耦合、模式耦合、权威状态位置、本地复制成本、乱序处理、重放能力、审计能力、隐私暴露、模式演进、存储/运行成本和适用信号。

选择规则必须体现：

- 只需告知事实、消费者数量少且回查可接受时，优先考虑事件通知；
- 业务动作由显式状态机约束、迁移合法性比完整快照更重要时，考虑状态转移；
- 消费者必须在生产者不可用时自治读取、并能承担复制与演进成本时，考虑事件携带状态；
- 业务确实需要从历史事实重建、时间点查询、强审计或多投影，且团队能承担事件设计与演进复杂度时，才选择性采用事件溯源。

文章同时列出停止条件：简单请求—响应已满足需求；业务要求跨边界即时强一致；团队无法运营代理、积压、死信和回放；事件所有权与模式治理不清；隐私或删除要求与不可变历史冲突且没有设计；事件溯源只是为了“更现代”或“以后可能审计”。

## 7. 可靠性与故障恢复

可靠性不是文章主线，但每种模式必须说明最低责任：

- 事件通知：生产者使用事务性发布边界；丢失通知可由持久记录与补偿扫描发现；回查失败有有界重试、降级或人工处理。
- 状态转移：按聚合键保证可解释的顺序，携带单调版本；非法、重复、旧版和缺口迁移分别拒绝、幂等忽略、丢弃或暂存补取。
- 事件携带状态：消费者按聚合 ID 与版本幂等更新；旧状态不能覆盖新状态；需要全量引导或可控重建路径，并处理模式兼容和敏感字段撤回。
- 事件溯源：追加使用预期流版本做乐观并发；事件模式升级不破坏历史；快照只优化回放而不成为新权威；回放必须确定且隔离外部副作用；毒事件有隔离、修复、受控重放与人工终止路径。
- 通用边界：投递语义按至少一次设计，消费者执行幂等；重试有退避与上限；死信不是终点，必须有所有者、告警和处置时限；关联 ID、因果 ID、积压、处理延迟、失败率和投影水位必须可观测。

Outbox 只解决本地状态提交和“待发布”记录的原子性，不保证消息只发布一次、消费者只处理一次或跨服务状态同时一致。补偿是新的业务事实，不是数据库回滚。事件溯源回放只能重建确定性内部状态，不能再次扣款、发短信或调用不可逆外部系统。

## 9. 来源与版权治理

来源采用少而完整的机制证据集，实施前固定精确 URL、版本、许可证和证据角色。候选闭环包括：

1. Martin Fowler 的 `What do you mean by “Event-Driven”?`，支持事件通知、事件携带状态和事件溯源的区别，并明确这些模式容易被混淆；
2. Microsoft Azure Architecture Center 的 `Event-driven architecture style`，支持生产者—通道—消费者、发布订阅/事件流、载荷选择、顺序、幂等、错误处理和模式演进；
3. Microsoft Azure Architecture Center 的 `Event Sourcing pattern`，支持事件存储、聚合回放、乐观并发、投影、快照和事件演进边界；
4. CNCF CloudEvents 规范及其规范仓库，支持公共事件信封字段与可移植事件描述，但不用于证明业务模式分类；
5. 一项能直接支持业务状态机/状态迁移语义的一手或高质量上游资料；若研究无法找到足够精确的证据，则把“状态转移”明确标为 Tego Arch 教学分析，不伪造外部共识。

最终正文至少使用三个独立受治理远程域，并严格限制 `manifest_primary` 为一个。新增来源必须登记作者/机构、发布日期或固定版本、核查日期、来源类型、证据角色、许可证与证据、引用范围和禁止外推项；同步来源台账、链接健康缓存、公开投影和许可证清单。

版权策略为原创中文事实总结、原创统一案例、原创决策矩阵和原创图示。不复制外部拓扑、图形、长段落、示例代码或品牌视觉。外部事实、由证据推导的判断、Tego Arch 教学分类和未知生产行为必须清楚分开。

## 12. 发布停止条件

只有以下条件全部满足，才可标记 STY-06 完成：

1. 页面不依赖外链也能准确区分四种事件模式及其状态责任；
2. 同一订单案例和固定比较问题贯穿四轮，读者可以横向比较而不是记忆四套无关示例；
3. 状态转移、事件携带状态和事件溯源的边界无互相替代或暗示升级关系；
4. 命令/事件、代理/事件存储、Outbox/恰好一次、CQRS/事件溯源等常见混淆均被显式否定；
5. 来源、许可证、术语、关系、图示和生成投影全部闭合；
6. 定向测试、完整验证与独立代码、内容/版权、架构评审通过；
7. Stage A exact-head Pages 成功，线上四态交互、来源、关系、图示、溢出与诊断检查完成并留下真实证据；
8. Stage B 写回精确 commit、run、job、日期、线上观察和测试计数，再次完整验证并发布；
9. STY-07 成为唯一下一项，保持 `unpublished/pending`、未勾选且不可操作；
10. 本地 `main`、`origin/main` 与最终证据提交一致，临时工作树安全清理，用户未跟踪文件保持不变。
