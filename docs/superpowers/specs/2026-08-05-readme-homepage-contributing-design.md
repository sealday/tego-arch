# Tego Arch README、首页定位与协作贡献设计

日期：2026-08-05  
状态：已完成对话设计，等待书面规格复核

## 1. 背景

Tego Arch 已具备案例、原则、质量属性、方法、建模、学习路径、来源治理与持续发布机制，但仓库根目录尚无 README，首页当前仍把受众描述为“第一次系统学习架构的工程师”，没有准确表达项目面向高级工程师转向架构设计的定位，也没有把长期执行路线和协作贡献方法放到新访问者最容易看到的位置。

本次变更建立仓库 README 和网站首页的一致叙事，并为协同开发者提供可执行的贡献入口。变更同时确定项目自有代码与内容的双许可证边界。

## 2. 目标

1. 用一句清楚、不过度承诺的定位说明项目服务谁、训练什么能力。
2. 在 README 与网站首页展示初版路线图，并把 `docs/content-backlog.md` 保持为精确进度的唯一事实源。
3. 让贡献者知道可以贡献什么、从哪里选题、如何登记来源、需要运行哪些验证。
4. 明确初版追求完整知识体系，后续迭代从完整版衍生三类产物。
5. 采用代码 Apache-2.0、原创文章与原创插图 CC BY 4.0 的双许可证方案，同时保留第三方材料的独立权利边界。

## 3. 非目标

- 不在本次变更中实现便携小抄、精华学习路线或 Tego 实践内容。
- 不创建尚无实际页面的导航链接或空白栏目。
- 不重构现有案例目录、内容生成器或长期 backlog。
- 不把路线图图片当成精确、实时的项目状态源。
- 不把仓库许可证套用到外部链接、短引用、商标或第三方图片。

## 4. 受众与项目定位

主要受众是已有扎实开发经验、正在从高级工程师转向架构设计职责的人。项目不以背诵模式名称为目标，而是训练以下判断：

- 如何从业务目标和质量属性识别架构驱动因素；
- 如何划分边界、控制权、状态与责任；
- 如何比较方案的适用条件、代价、失败模式与演化路径；
- 如何让架构结论回到一手来源、可检查实现和真实案例；
- 如何在发布、恢复、安全、观测、成本和组织约束下做可落地决策。

推荐主定位文案：

> 面向有经验的高级工程师，用证据、权衡与真实案例训练从实现到架构决策的能力。

## 5. 产品方向

### 5.1 初版：完整知识体系

初版沿 20 个持久故事完成架构基础、质量属性、方法、原则、建模、架构风格、领域与分布式模式、生产治理、专题、案例、反模式与设计题。完成标准不只是文章数量，而是来源、版权、关系、验证、发布和线上检查全部闭合。

### 5.2 后续产物一：便携小抄

从完整版提炼第一性原理、关键判断和高代价错误提醒。目标是占据尽可能小的记忆空间，在设计评审、故障处理和关键决策时帮助工程师避免基础性错误。它不是术语表，也不替代完整解释。

### 5.3 后续产物二：精华学习路线

从完整版选择一组连贯主题，按明确线索组织成更短的学习路径。它降低进入门槛，服务更广泛的工程师群体，但保留完整版本中的证据与边界链接，不把精简内容写成无条件结论。

### 5.4 后续产物三：Tego 实践与规划

说明这些架构判断在 Tego 设计中的实际应用位置、当前取舍和未来规划。初版只展示这一方向，不创建没有内容支撑的链接；待形成可审阅材料后再进入导航和来源治理。

## 6. README 信息结构

README 使用“定位优先”结构：

1. 项目名称、定位和一句价值说明；
2. 主要入口：在线站点、学习路径、案例库、贡献说明；
3. 初版发布路线图图片；
4. 路线图说明和指向 `docs/content-backlog.md` 的最新状态链接；
5. 适合人群与不适合人群；
6. 知识体系与阅读方式；
7. 初版目标和三个后续产物；
8. 本地开发：Node.js 版本、安装、启动、验证；
9. 贡献类型、贡献流程、内容与来源门槛；
10. 双许可证、第三方材料和免责声明。

README 使用仓库相对路径引用 `static/img/illustrations/tego-arch-initial-release-roadmap.png`，确保 GitHub 可直接显示。图片下方明确标注它是执行概览，精确进度以 backlog 为准。

## 7. 网站首页信息结构

### 7.1 Hero

- 保留 Tego Arch 和软件架构知识图谱身份。
- 主标题强调从高级工程师到架构设计者的能力转换。
- 正文使用第 4 节的定位，不声称项目能直接授予职位或保证结果。
- 主按钮进入学习路径，次按钮进入 GitHub README 的贡献锚点。
- 现有 `projectStatus` 卡片继续从生成状态文件读取数字，避免手工维护第二份进度。

### 7.2 路线图区

路线图紧接 Hero：

- 标题说明初版追求完整知识体系；
- 展示 `/img/illustrations/tego-arch-initial-release-roadmap.png`；
- 提供目的型 alt 文本；
- 说明图片是阶段概览，最新精确状态由 backlog 维护；
- 提供到 GitHub backlog 的链接，不新增网站路由。

路线图属于 `位图` 概览：其工作是帮助读者记住执行阶段与初版门槛，不承担 20 个故事的完整任务定义。

### 7.3 “初版之后”区

在路线图之后增加三个方向卡片：

1. 便携小抄；
2. 精华学习路线；
3. Tego 实践与规划。

卡片只陈述目标和边界，不包含按钮或伪造链接。未来真实产物发布后再增加入口。

### 7.4 既有内容

保留案例、迁移地图、五步阅读协议、开放入口和贡献区。贡献区文案改为显式列出内容、来源纠错、原创图示和工程改进四类贡献，并链接 README 的贡献章节。

## 8. 贡献模型

### 8.1 可贡献内容

- 内容：概念、原则、质量属性、方法、建模、模式、风格、案例、反模式和设计题；
- 证据：来源补充、版本固定、错误纠正、失效链接和许可证边界；
- 图示：原创位图、Mermaid 或 Draw.io + SVG，遵循项目格式决策与来源登记；
- 工程：内容契约、生成器、验证、可访问性、性能和导航改进。

### 8.2 开始方式

- 小型事实纠错、错别字、失效链接或局部测试修复可以直接提交 PR。
- 新主题、页面结构变化、许可证变化、来源模型变化和跨页面重构先创建 issue，写明读者问题、范围、来源候选和停止条件。
- 选题和状态只从 `docs/content-backlog.md` 读取；历史 spec/plan 不恢复为活任务。

### 8.3 内容贡献门槛

- 优先使用标准、原作者、官方文档、论文、源码与一手工程材料；
- Awesome、路线图和聚合索引仅用于 discovery/learning；
- 明确区分事实、基于证据的推断、厂商自述、本站分析和未知项；
- 原创中文表达，不逐段翻译，不复制第三方图表或目录文案；
- 外部来源登记到 `data/source-ledger.json`，正文 citation 与使用角色闭合；
- 图示遵守 `.codex/skills/illustrating-architecture-articles/` 的格式决策和集成要求；
- 通过定向检查与 `npm run verify`。

### 8.4 本地命令

README 至少给出：

```bash
npm ci
npm run start
npm run verify
```

并声明 Node.js `>=24.0`。需要联网复核来源时单独运行 `npm run check:links:live`，避免把网络状态混入默认离线验证。

## 9. 版权设计

### 9.1 代码

根目录 `LICENSE` 使用 Apache License 2.0，覆盖项目自有源代码、构建脚本、测试、配置和工具代码，除非文件另有说明。

### 9.2 原创内容与插图

新增 `LICENSE-CONTENT.md`，声明项目自有中文文章和原创插图采用 Creative Commons Attribution 4.0 International。再利用者必须适当署名、链接许可证并说明修改，不得暗示 Tego Arch 为其使用背书。

### 9.3 第三方边界

新增 `NOTICE.md`：

- 外部来源、短引用、第三方图片、商标和链接作品继续受各自许可证或权利约束；
- source ledger 中的许可证只覆盖登记的具体作品范围；
- Tego Arch 的双许可证不重新授权第三方材料；
- 事实性总结和链接不等于取得原作品版权。

README 与网站 footer 使用简短双许可证声明，并链接仓库中的三个版权文件。

## 10. 路线图资产与来源边界

发布资产为：

`static/img/illustrations/tego-arch-initial-release-roadmap.png`

该图是项目自有的生成式原创概览，使用 Tego Arch 的暖白手绘视觉语言。它不复刻外部人物、签名、文字或构图，也不作为外部事实证据。

本次用途是 README 与应用首页，而不是受治理的 MDX 证据文章。许可证由 `LICENSE-CONTENT.md` 覆盖；source ledger 保留显式登记缺口，直到图片进入受治理 MDX 文档并能形成真实 document citation，避免伪造文章引用。

## 11. 响应式与可访问性

- 路线图使用语义化 `img`、目的型中文 alt 和稳定的宽高比；
- 图片容器在桌面限制最大宽度，在移动端宽度为 100%，不得产生页面横向溢出；
- 状态说明不能只依赖图中的颜色，附近文本重复“已完成、当前、待执行、发布门槛”的含义；
- 三个未来方向卡片在窄屏堆叠；
- 新链接保留可见焦点与明确文案；
- 深色模式下为暖白图片提供边框或底色，避免边界消失。

## 13. 验证策略

1. 定向测试锁定：
   - README 存在并包含定位、路线图、贡献流程、Node 版本和验证命令；
   - 三个许可证文件的范围声明一致且第三方排除明确；
   - 首页包含路线图、alt、初版之后三个方向和贡献链接；
   - footer 展示双许可证而不是笼统的单一 copyright 文案。
2. 运行：
   - `npm run validate:content`
   - `npm run check:content`
   - `npm run check:reviews`
   - `npm run typecheck`
   - `npm run build`
   - `npm run verify`
3. 在 desktop `1440x1000` 与 mobile `390x844` 检查首页：
   - 路线图清晰、无横向溢出；
   - Hero、方向卡片和贡献区层级正确；
   - 图片路径、许可证链接、GitHub 贡献锚点可用；
   - console 无 warning/error，页面无 error。

## 14. 验收条件

- 新访问者在首页和 README 第一屏能够理解目标受众与项目价值；
- 路线图同时出现在 README 和网站首页，且明确指向 backlog 作为精确状态源；
- README 能让新贡献者从选题、来源登记、本地运行到 PR 验证形成闭环；
- 初版完整性与三个后续产物均有准确、不过度承诺的说明；
- Apache-2.0、CC BY 4.0 与第三方材料边界无冲突；
- 定向测试、全量验证和两种视口检查通过。
