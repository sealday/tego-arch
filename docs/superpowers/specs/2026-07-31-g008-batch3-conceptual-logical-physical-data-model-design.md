# G008 Batch 3：概念、逻辑与物理数据模型设计

## 1. 目标

本批次只发布并关闭 `MOD-05`：用同一个费用申报问题展示数据模型如何从业务语义逐层加入身份、关系、约束和平台实现决定。

页面必须帮助读者区分：

- 概念模型回答“业务中有哪些事物、词义和关系”；
- 逻辑模型回答“实体如何识别、关联和受业务约束”；
- 可移植关系模式回答“逻辑结构如何映射为表、键、类型族和索引候选”；
- 严格意义上的物理模型如何在指定 DBMS 上落实约束、类型、索引和存储决定。

主线示例继续使用 `MOD-02` 的费用申报系统边界与命名。`MOD-02` 中的图是系统边界和外部系统命名的权威；`MOD-05` 只增加数据视角，不重画或改写系统边界。

## 3. 已批准的方法

采用“同一业务问题逐层演进”的方案，而不是三张互不关联的模型或只提供静态对照表。

```text
业务词汇
  → 概念模型
  → 逻辑模型
  → 可移植关系模式
  → PostgreSQL 18 物理实现切片
  → 迁移与验证缺口
```

每一步必须明确：

1. 继承了上一层哪些语义；
2. 新增了哪些决定；
3. 哪些问题仍保持未知；
4. 哪些事实只是本站教学假设。

## 4. 术语边界

官方产品资料对三层术语并非行业唯一标准。本页采用以下受约束的教学组织：

| 层次 | 本页定义 | 明确不证明 |
| --- | --- | --- |
| 概念模型 | 主要业务概念、词义和业务关系 | 实体键、基数、表结构或流程顺序 |
| 逻辑模型 | 与 DBMS 无关的实体、属性、唯一标识、关系、基数和业务约束 | SQL 表已经设计、平台约束可执行或查询性能达标 |
| 可移植关系模式 | 把逻辑实体映射为表、主外键、类型族、唯一性和索引候选 | 这是严格意义上的 DBMS 物理模型或可直接部署 |
| PostgreSQL 18 物理切片 | 在指定平台上选择实际约束与索引类别的最小示例 | 完整生产 DDL、性能结果、容量、迁移安全或运维方案 |

正文不得把数据库中立的关系模型描述为所有官方来源共同认可的严格 PDM。应明确说明：SAP、IBM 和 Oracle 的官方资料通常把 physical model 解释为面向具体 DBMS 的实现。

## 5. 内容结构

页面沿用 modeling 类型的固定结构：

1. 学习问题
2. 建模目标与输入
3. 参与者与步骤
4. 模型产物
5. 完成判断
6. 常见失败
7. 与其他模型的衔接

9. 来源

### 5.1 学习问题

提出 3–5 个问题，至少覆盖：

- 三层模型各自增加什么决定；
- 身份、关系和约束在哪一层变得明确；
- 可移植关系模式为什么还不是完整物理模型；
- 哪些平台决定必须通过迁移和运行证据验证。

### 5.2 建模目标与输入

输入包括：

- `MOD-02` 的费用申报系统边界与权威命名；
- 业务词汇、规则、样例和冲突；
- 身份、生命周期、时间和金额语义；
- 数据保留、审计、权限和迁移约束；
- 目标 DBMS 及版本；
- 可验证的查询、写入和完整性要求。

页面必须区分来源事实与本站教学假设。费用申报的逻辑实体、字段、键、类型和索引不是 `MOD-02` 或真实生产系统公开事实。

### 5.3 参与者与步骤

参与者至少包括业务负责人、数据/领域建模者、应用开发者、数据库负责人和独立评审者。

步骤：

1. 固定业务词汇和问题边界。
2. 建立概念模型，不加入表或数据库术语。
3. 在逻辑模型中加入身份、关系、基数和业务约束。
4. 映射为可移植关系模式，记录表、键、类型族和索引候选。
5. 选择 PostgreSQL 18 作为一个受限物理切片，说明平台决定。
6. 把未知项、迁移风险和验证条件交给实现与运行证据。

### 5.4 模型产物

#### 三层决策表

必须只有一张主映射表，并放入可聚焦的局部横向滚动 wrapper。表格至少包含：

- 层次；
- 关键问题；
- 费用申报示例；
- 新增决定；
- 明确不证明。

#### 原创 Mermaid

必须只有一张 Mermaid。它表达以下映射，而不是业务流程：

- 业务概念：员工、费用申报、审批、付款；
- 逻辑实体：Employee、ExpenseClaim、Approval、PaymentInstruction；
- 可移植关系表：employee、expense_claim、approval、payment_instruction；
- PostgreSQL 物理切片：PK/FK/UNIQUE/CHECK/NOT NULL、索引候选和类型选择；
- 迁移与验证缺口。

图中必须明确显示“映射”或“加入决定”，不得用时间顺序箭头暗示运行流程。

### 5.5 完成判断

完成条件包括：

- 同一个业务词汇能跨层追踪；
- 每个逻辑实体都有稳定身份和约束说明；
- 关系模式能回指逻辑语义；
- PostgreSQL 切片明确平台版本和决定；
- 所有教学假设、未知项和验证缺口可见；
- 没有把表数量、外键、索引或规范化程度写成正确性或性能证明。

### 5.6 常见失败

至少覆盖：

- 只换名，不逐层增加决定；
- 在概念模型中过早加入表和键；
- 把逻辑模型写成流程图；
- 把可移植关系模式误称为已验证物理模型；
- 从 C4 或 arc42 图推断生产 schema；
- 用索引候选承诺性能；
- 忽略金额、时间、身份、历史和迁移语义。

### 5.7 与其他模型的衔接

- `MOD-01` 负责从评审问题选择数据模型。
- `MOD-02` 提供费用申报系统边界和权威命名。
- `MOD-04` 说明数据证据如何进入架构文档。
- `PR-13` 说明领域模型与持久化现实之间的边界。
- `MOD-06` 将继续展开 ER 身份、关系、基数、约束和历史变化；它尚未发布，因此正文只写交接方向，不创建链接或 adjacency。
- 流程顺序、状态变化和部署实例不由本页证明。

### 5.8 完整演练

演练语句为“员工提交费用申报，经审批后形成付款指令”。

演练必须逐层说明：

- 概念层：词义和业务关系；
- 逻辑层：实体身份、金额和币种语义、审批关系、付款唯一性；
- 可移植关系层：表、主外键、唯一性、类型族和索引候选；
- PostgreSQL 18 切片：约束与索引类别的示例选择；
- 未知项：实际查询分布、写入竞争、历史保留、分区需求、迁移窗口和性能。

不展示完整 DDL。代码式字段名只用于说明映射，不构成可部署 schema。

## 7. 来源与版权边界

### 7.1 SAP PowerDesigner 16.7 SP10

用于支持：

- 数据模型描述系统产生或消费的信息；
- CDM、LDM、PDM 表达不同抽象层；
- PDM 面向实际数据库实现和物理约束。

边界：

- 这是 SAP 产品方法，不是通用标准；
- 只做原创意译和链接；
- 不复制段落、表格、图、截图、符号或页面布局。

### 7.2 IBM InfoSphere Data Architect 9.1.1 / 9.1.2

用于支持：

- LDM 不特定于数据库；
- 逻辑实体可包含属性、关系、唯一标识和约束；
- 逻辑对象可映射为数据库特定的物理对象。

边界：

- 版本较旧，只用于稳定概念和映射证据；
- 不用于推断当前 DBMS 功能；
- 只做原创意译和链接。

### 7.3 PostgreSQL 18

用于支持：

- CHECK、NOT NULL、UNIQUE、PK、FK 等平台约束；
- 索引带来查询收益，也有写入和维护成本。

边界：

- PostgreSQL 文档不定义三层数据模型；
- PostgreSQL 行为不得泛化为所有关系数据库；
- 不复制完整文档或示例 DDL；
- 若直接改编文档内容，必须遵循 PostgreSQL License；本页优先采用原创说明。

### 7.4 原创性

三层决策表、Mermaid、费用申报实体与字段、关系模式和物理切片均为本站原创教学材料。不得复用厂商商标、logo、产品截图或官方图。
