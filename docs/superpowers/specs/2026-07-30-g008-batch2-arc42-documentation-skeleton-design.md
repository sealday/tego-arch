# G008 Batch 2：arc42 文档骨架设计

## 背景

G008 Batch 1 已完成 MOD-01..03，建立了模型选择入口与 C4 多视图学习路径。下一项 MOD-04 要回答的不是“再画一张图”，而是如何把分散在约束、结构、运行、部署、决策与风险中的架构知识组织成一份可评审、可维护、允许保留未知项的文档。

arc42 官方英文模板当前版本为 v9.0（2025 年 7 月），以十二个问题域组织架构文档，并明确允许按项目需要裁剪。本批次不复制或换皮官方十二章模板，而是设计本站原创的六单元教学骨架，再把六个单元映射到 arc42 v9 的十二个问题域。这样既保留官方方法的可追溯性，也避免让读者为了填满模板而制造没有证据的内容。

MOD-04 只关闭一个主题。MOD-05 及后续数据建模、协作建模和模型治理主题不进入本批次。

## 目标

本批次完成后，读者能够：

1. 解释 arc42 用问题域组织架构知识，而不是替代模型、决策记录或运行证据；
2. 用六个教学单元把一个已有案例映射到目标与边界、约束与权衡、静态结构、动态行为、条件性部署、质量与风险；
3. 区分案例中的已验证事实、基于证据的推断、本地项目决策和未知项；
4. 在 Building Block View 中建立静态分解主线，并用运行、部署和决策证据补充而不混淆证明范围；
5. 对缺少证据的内容明确标为未知、不适用或待验证，不为模板完整度虚构生产事实；
6. 写出至少一个可度量的质量场景，并把它与风险、决策和验证证据连接起来。

## 方案比较与决定

### 方案 A：六单元原创教学骨架映射 arc42 v9

正文以六个学习单元组织内容，每个单元标明对应的 arc42 问题域、所需证据、输出和停止条件。官方十二个问题域提供追溯，本站结构提供教学顺序。

优点是适合一次端到端演练，能够强调证据边界，也符合 arc42 可裁剪原则。代价是必须清楚标出六单元与官方问题域不是一一同名，避免读者误以为这是官方模板。

### 方案 B：逐章讲解官方十二个问题域

按官方章节顺序逐一解释。优点是对照直接，缺点是容易演变为模板复述，篇幅大，并鼓励按章节填空而不是围绕评审问题组织证据。

### 方案 C：只给出一页最小检查清单

以简短清单覆盖边界、结构、运行和风险。优点是轻量，缺点是不能展示内容之间的证据链，也无法证明读者能够把真实案例映射到 arc42。

### 决定

采用方案 A。正文必须显式声明：

- arc42 官方版本仍以十二个问题域组织内容；
- 六单元是本站原创教学投影，不是官方替代模板；
- 所有单元都可以按实际需要裁剪；
- 缺失证据不会因为章节存在而自动成为事实。

## 内容架构

MOD-04 使用 modeling 内容类型的九个标准二级标题：

1. 学习问题
2. 建模目标与输入
3. 参与者与步骤
4. 模型产物
5. 完成判断
6. 常见失败
7. 与其他模型的衔接
8. 完整演练
9. 来源

frontmatter 依赖为 MOD-01 与 MOD-03。MOD-01 提供模型选择与证据边界，MOD-03 提供结构、运行与部署视图的区分。相邻主题连接 MTH-03、MTH-06 和 MOD-13；MOD-13 尚未完成，但其主题路由可以作为后续持续建模入口。Microsoft multi-agent reference architecture 是正文唯一端到端案例。

### 六个教学单元

| 本站原创单元 | 对应 arc42 v9 问题域 | 核心问题 | 最小证据与产物 |
| --- | --- | --- | --- |
| 目标与边界 | 1 Introduction and Goals、3 Context and Scope | 为什么建、为谁建、边界在哪里 | 业务目标、关键干系人、质量目标、业务/技术上下文 |
| 约束与权衡 | 2 Architecture Constraints、4 Solution Strategy、9 Architecture Decisions | 哪些条件不可改变，采用什么总策略，为什么这样取舍 | 约束清单、方案策略、ADR 或可追溯决策 |
| 静态组成 | 5 Building Block View、8 Cross-cutting Concepts 的结构性部分 | 系统由哪些责任单元组成，边界和依赖如何分层 | 分层 Building Block 视图、职责、接口、所有权 |
| 动态行为 | 6 Runtime View、8 Cross-cutting Concepts 的运行性部分 | 关键场景如何跨责任边界执行 | 选定场景、顺序/状态、失败与恢复路径 |
| 条件性部署 | 7 Deployment View | 软件实例在什么已知环境中运行 | 经验证的环境、节点、实例映射；无证据时保留未知 |
| 质量、风险与词汇 | 10 Quality Requirements、11 Risks and Technical Debt、12 Glossary | 如何度量成败，最大风险是什么，术语是否一致 | 可度量质量场景、风险/债务、统一词汇 |

第 8 节 Cross-cutting Concepts 会按证据作用分布到静态组成和动态行为，而不是复制成孤立清单。第 9 节的决策进入“约束与权衡”，但 ADR 仍是独立可追踪产物。第 10 节既包含质量概览，也包含详细质量场景；正文至少给出一个带刺激、环境、响应与度量的场景。

### Building Block 主线

Building Block View 是本文的核心，因为它把系统边界继续分解为可命名、可分配责任、可讨论接口的静态单元。正文使用 Microsoft 案例公开材料中能验证的系统、服务和运行单元，不把技术栈名直接当成责任边界，也不根据图形位置推断所有权。

静态分解必须满足：

- 每个 Building Block 有明确责任；
- 层级只在能回答评审问题时继续展开；
- 依赖方向能回到公开来源或被标为推断；
- 组织所有权没有证据时保持未知；
- 运行步骤和部署节点不混入静态组成定义；
- C4 Component 视图可作为结构输入，但不是 arc42 Building Block View 的唯一表达形式。

### 案例证据分类

Microsoft 案例中的陈述必须落入以下四类之一：

1. **已验证事实**：官方文本、图或仓库直接说明的角色、组件、关系和场景；
2. **基于证据的推断**：由公开材料合理推出，但来源没有直接陈述的结构或后果；
3. **本地项目决策**：为本站教学演练选择的裁剪、命名、映射和评审重点；
4. **未知项**：生产部署、容量、恢复目标、真实组织所有权等没有足够证据的内容。

正文不能把推断降格成无标注事实，也不能用本地项目决定改写 Microsoft 参考架构。部署单元如果缺少公开生产证据，应展示“证据缺口如何记录”，而不是画一个看似完整的拓扑。

### 可度量质量场景

完整演练至少包含一个教学用质量场景，例如：

- 来源：架构评审者；
- 刺激：请求追踪一次跨多个 Agent 的业务流程；
- 环境：参考实现的正常运行演练；
- 制品：编排、Agent 间消息和遥测链路；
- 响应：能够把关键步骤关联到同一业务请求并定位失败责任边界；
- 度量：演练选定的全部关键步骤都有一致关联标识，且故障步骤能在约定检查时间内定位。

具体度量值必须标为本站演练的验收标准，不声称是 Microsoft 生产承诺。质量场景产生的设计选择记录在 ADR，验证结果来自测试或观测，风险项记录仍未满足的差距。

### Mermaid 证据链

Mermaid 图表达最小证据流：

`目标/边界 → 约束/权衡 → 静态组成 → 动态行为 → 条件性部署 → 质量/风险`

决策、验证证据和未知项作为贯穿节点连接相关单元。图的目的不是重画 Microsoft 架构，而是说明文档内容如何相互校验。正文必须解释：

- 静态结构没有自动证明运行顺序；
- 运行场景没有自动证明部署事实；
- 决策没有自动证明实现符合预期；
- 质量与风险需要回链到结构、运行、部署和验证证据。

## 失败处理与停止条件

以下任一情况阻止 Stage A：

- 正文缺少 modeling 类型要求的九个标准二级标题；
- 六单元被表述为 arc42 官方模板或十二个问题域映射不完整；
- Microsoft 案例事实、推断、本地决定和未知项没有清晰区分；
- Building Block View 没有成为静态结构主线；
- 部署内容虚构公开材料没有证明的生产拓扑；
- 缺少可度量质量场景，或把教学度量写成外部生产承诺；
- Mermaid 无法渲染，表格导致页面级溢出，或移动端不可操作；
- 来源身份、许可证或可见引用不完整；
- 站内路由、关系、生成产物、目标测试或完整验证失败。

以下任一情况阻止 Stage B：

- Pages run 的 `headSha` 不等于 Stage A 提交；
- Pages run 未达到 `completed/success`；
- MOD-04 或其关键来源链接不是 HTTP 200；
- 桌面或移动视口发生 document overflow、表格不可横向操作或 Mermaid 标签不可读；
- 浏览器控制台出现 warning/error；
- 来源标签或要求的 parent、adjacent、case、question 链接不能真实点击；
- 部署证据尚未写入 backlog、项目状态和 G008 审查记录；
- 状态更新误关闭 MOD-05..13 或 G008。

验证失败时 MOD-04 保持未完成。修复后重新生成、测试并部署，不使用推测性证据关闭主题。
