## 1. 目标与非目标

本主题新增一篇可独立阅读的架构风格文章，以同一个企业级订单履约案例解释经典面向服务架构（Service-Oriented Architecture，SOA）与微服务的共同基础、不同优化尺度和责任约束。订单、库存、支付和通知由不同业务系统负责，通过稳定服务合同协作；允许集中编排和共享集成能力，但业务决定与权威数据始终归业务系统所有。

文章必须把 SOA 与具体实现产品分开：Web Service、企业服务总线（Enterprise Service Bus，ESB）、消息中间件、服务注册表或共享数据库都不足以定义 SOA。ESB 可以承担路由、协议转换、策略执行和技术观测，却不能因此拥有业务流程状态、业务规则或权威数据。集中编排器可以持有跨系统流程状态并作出恢复决策，但参与系统仍负责自己的本地事务、幂等、业务拒绝和权威结果。

SOA 与微服务存在重叠，不是互斥集合，也不是成熟度阶梯。本文把主要差异定位为优化尺度和约束组合：经典 SOA 偏向企业能力复用、异构系统互操作和统一治理；微服务偏向团队自治、私有权威数据和独立部署。微服务不是 SOA 的自动升级，SOA 也不是微服务的低成熟度前身。

本轮不实现 STY-08 或 STY-14，不扩展为完整企业集成模式目录，不新增产品运行时功能，不引入 ESB、编排器或协议依赖，不推荐特定供应商，也不把组织规模、Web Services 或中央平台写成 SOA 的必要条件。

正文围绕七个不可替代的判断组织：

- **能力与合同：** 服务提供对业务能力的受治理访问，合同明确语义、消息、策略、版本和可见责任；远程接口数量不能证明服务边界。
- **业务与集成责任：** 业务系统拥有业务决定和权威数据；编排器拥有跨系统流程进度与恢复决策；集成基础设施只拥有技术传输、路由、转换、策略执行和技术观测。
- **可选集中编排：** SOA 可以集中编排，也可以使用协同消息。集中编排是可选协作形态，不是定义；编排器持久化流程状态，却不得直接共享写入参与系统的数据。
- **ESB 非定义：** ESB 是可选基础设施。只要中央层积累领域规则、权威状态或绕过合同的共享写入，就形成需要收紧或停止的集成中心风险。
- **数据权威不转移：** 企业合同与共享治理不授权共享数据库写入。订单、库存、支付和通知的权威状态分别留在对应业务系统。
- **部署约束不同：** SOA 参与系统可以独立部署，但企业合同治理可能形成协调窗口；微服务把独立部署与回滚作为核心约束。两者都不能把锁步发布包装成自治。
- **按证据选择：** 异构互操作、企业能力复用和统一政策支持 SOA；持续独立发布、不同资源曲线和团队端到端责任支持微服务；边界、合同或恢复责任不清时，两者都不应继续拆分。

## 3. 统一场景与控制流

同一订单履约案例固定六类责任主体：

- 订单系统接收订单并拥有订单状态；
- 库存系统拥有库存、预留和释放结果；
- 支付系统拥有支付意图、授权结果和对账状态；
- 通知系统拥有投递状态；
- 企业流程编排器持久化跨系统流程状态，通过稳定合同推进、暂停、恢复或终止流程；
- 集成基础设施负责路由、协议与格式转换、技术重试、策略执行和技术观测，不拥有业务状态。

经典 SOA 路径采用明确但非唯一的集中编排方案：

1. 客户端通过企业订单合同提交带稳定请求标识的履约请求；
2. 编排器持久化流程实例与当前步骤，再经集成基础设施调用订单系统；
3. 订单系统在本地事务中写入待处理订单并返回业务结果；
4. 编排器依次请求库存预留和支付授权，各参与系统只提交自己的权威状态；
5. 支付确认后，编排器确认订单并请求通知；支付拒绝、库存拒绝或终止时，编排器发出释放库存、撤销、冲正或退款等新业务动作；
6. 通知失败不反向撤销已确认订单，而是保留通知系统的恢复状态；
7. 编排器重启后从持久流程状态恢复，集成基础设施重启后恢复技术传输，不允许任一层凭技术投递状态推断业务结果。

每次业务调用都具有稳定请求标识。超时必须区分“未执行”“已失败”和“结果未知”；结果未知时先查询或对账，不盲目重复支付、预留或补偿。补偿是新的业务动作，不是假装回滚外部世界。合同版本、兼容窗口、消费者迁移、超时预算、重试、死信、审计和人工终止均有明确所有者。

## 4. 固定机制对照

SOA 与微服务必须使用相同参与者和相同订单步骤，只改变优化尺度与约束组合。正文和测试固定以下八维对照：

| 问题 | 经典 SOA | 微服务 |
| --- | --- | --- |
| 优化尺度 | 企业能力复用与异构系统互操作 | 单个团队的快速自治交付 |
| 合同 | 企业级、稳定、显式治理的服务合同 | 团队拥有、兼容演进的业务合同 |
| 协作 | 可集中编排，也可使用消息 | 倾向分散协作，但不禁止编排 |
| 数据权威 | 留在各业务系统，不因集成而共享写入 | 服务私有权威数据 |
| 部署 | 参与系统可独立部署，企业治理可能形成协调窗口 | 独立部署和独立回滚是核心约束 |
| 平台 | 可共享注册、策略、转换、编排和观测能力 | 平台提供护栏，不拥有业务决定 |
| 故障责任 | 编排器负责流程推进，参与系统负责本地结果与恢复 | 服务团队端到端负责合同、数据、部署和运行 |
| 主要风险 | 中央集成层膨胀成业务逻辑与共享状态中心 | 服务碎片化和分布式运行成本 |

该表是机制对照，不宣称所有 SOA 或微服务实现都采用同一种拓扑。结论必须同时陈述共同点、差异和选择条件，不得把任何一列写成另一列的前后阶段。

## 5. 数据、一致性与失败责任

订单、库存、支付和通知的权威状态分别归对应业务系统。企业数据模型可以为交换定义受治理语义，但不能成为允许所有系统共享写入的单一数据库模型。集成转换把一种合同表示映射为另一种表示，不得悄悄改变业务含义、发明权威值或绕过源系统验证。

编排器只在自己的存储中原子提交流程状态和待执行步骤；参与系统只在自己的本地事务中提交业务结果。跨系统流程不被描述为数据库式原子事务。至少覆盖以下失败分类和责任：

| 失败类别 | 检测 | 自动动作 | 停止条件 | 人工所有者 |
| --- | --- | --- | --- | --- |
| 路由或协议转换失败 | 集成错误与目标不可达 | 有界技术重试、隔离或切换 | 重试预算耗尽或映射不可信 | 集成平台所有者 |
| 业务拒绝 | 合同返回明确拒绝 | 编排器选择业务分支 | 无安全自动分支 | 对应业务系统所有者 |
| 结果未知 | 超时且无权威结果 | 按稳定标识查询或对账 | 截止期到达仍未知 | 编排器与业务系统共同升级 |
| 重复调用或消息 | 请求标识与去重记录命中 | 返回既有结果或幂等忽略 | 标识冲突或结果不一致 | 接收业务系统所有者 |
| 合同不兼容 | 合同测试或运行拒绝 | 使用兼容版本或停止切换 | 无受支持兼容路径 | 合同生产者与消费者 |
| 补偿失败 | 补偿结果拒绝、未知或超时 | 查询、对账或受控重试 | 动作不可逆或预算耗尽 | 业务流程所有者 |
| 死信或积压 | 队列深度、最老消息与失败率 | 隔离、修复后受控重放 | 重放会重复不可逆副作用 | 集成与业务所有者分别承担技术和业务判断 |

共享观测必须包含调用结果、转换失败、端到端流程状态、积压、最老消息、失败率和对账状态。技术平台可以提供信号与护栏，但不能替业务所有者决定库存是否预留、支付是否成功或订单是否终止。

## 8. 来源与版权治理

来源采用五项远程证据与一项原创插图的最小闭环：

1. [OASIS Reference Model for Service Oriented Architecture 1.0](https://docs.oasis-open.org/soa-rm/v1.0/soa-rm.html)，用于服务、能力访问、可见性、交互、真实世界效果、合同与策略等基础概念；它不证明 ESB、Web Services 或集中编排是必要组件。
2. [OASIS Reference Architecture Foundation for Service Oriented Architecture 1.0](https://docs.oasis-open.org/soa-rm/soa-ra/v1.0/soa-ra.html)，用于参与者、治理、策略、服务描述、交互和跨所有权边界责任；它不证明本文订单拓扑是唯一参考架构。
3. [W3C Web Services Architecture](https://www.w3.org/TR/ws-arch/)，用于消息、服务描述、策略和参与者关系；Web Services 只是实现族，不等于 SOA 本身。
4. [James Lewis 与 Martin Fowler 的 Microservices](https://martinfowler.com/articles/microservices.html)，用于围绕业务能力、独立部署、去中心化数据和端到端责任等微服务特征；它用于比较，不支持成熟度阶梯或生产效果保证。
5. [Microsoft Azure Architecture Center 的 Microservices architecture style](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/microservices)，用于独立部署、私有数据、自动化交付、可观测性和分布式成本的第二来源；它不证明云平台或微服务适用于所有企业集成问题。
6. 原创图“经典 SOA 与微服务的订单履约机制对照板”，由 Tego Arch 架构知识项目维护者绘制，支持本文教学比较，不证明生产结果。

## 9. 迁移、采用与停止条件

迁移不从采购 ESB 或拆分服务开始，而从盘点企业能力、系统所有者、权威数据和真实消费者开始：

1. 列出订单履约中每个业务能力、权威状态和当前系统所有者；
2. 把点对点集成中的隐式语义提炼成面向业务结果的服务合同；
3. 为合同建立版本、兼容、身份、策略、超时、幂等、审计和消费者迁移规则；
4. 只把重复且稳定的技术路由、转换和策略移入共享集成能力；
5. 为长流程引入持久编排状态、结果未知对账、补偿和人工终止；
6. 观察企业复用、变更等待、故障恢复和治理成本，再决定继续 SOA、提取微服务或保持现状。

以下情况支持采用或收紧 SOA：异构系统长期存在；多个业务流程需要稳定企业能力；身份、审计或政策需要一致执行；点对点转换重复且无所有者；跨系统流程需要持久恢复。以下情况要求停止扩张：中央集成层开始拥有领域规则或权威状态；所有调用被强制穿过单点却无可测价值；共享规范拖慢局部变化；共享数据库写入继续存在；合同治理没有消费者迁移机制；锁步发布、事故影响或恢复时间没有改善。

若主要压力是单个团队的独立发布、独立回滚、不同资源曲线和端到端值守，且企业级复用与集中治理不是主问题，应优先评估微服务约束。若边界和权威数据尚未理解，应先收紧模块化单体，而不是同时建设 SOA 平台和微服务拓扑。
