## 1. 目标与非目标

本主题新增一篇可独立阅读的架构风格文章，用订单结算与异步履约解释 Serverless Architecture。同步入口只完成认证、校验、幂等受理并返回订单操作标识；持久工作流与权威状态记录保存流程进度；支付、库存、通知等函数只执行有界步骤。文章必须把执行模型、状态、并发、冷启动、成本和供应商边界放在同一业务路径中，而不是把 Serverless 缩写成“把代码部署为函数”。

本文采用 **持久控制面 + 有界函数执行面**。平台接管执行环境供应、部分扩缩、调度和按量计费，业务团队仍拥有订单状态、幂等语义、下游容量、恢复规则、人工终态和退出成本。函数内存、调用栈与临时文件只可作为可丢失缓存，不能承担恢复所需的业务事实。

本轮不做云厂商产品排行，不实现跨云平台、真实订单应用、性能基准、成本计算器或自动迁移工具，不承诺零运维、无限扩缩、端到端 exactly-once 或无成本可移植性。文章不把 Serverless 等同于 Functions as a Service（FaaS）、容器自动扩缩或边缘计算，也不把订单、流量、延迟、价格或故障数据伪装为生产事实。

## 2. 已批准决策

设计对话已确认以下决策：

1. 使用订单结算与异步履约作为统一教学案例；
2. 以函数执行为主线，但把事件源、队列、状态存储和工作流纳入完整系统边界；
3. 同步入口只受理请求，持久工作流拥有订单进度，队列承接异步履约，短生命周期函数执行单步任务；
4. 并发采用入口准入与配额、队列/函数并发上限、下游容量预算三层控制；
5. 每个订单使用幂等键和条件状态转移防重，支付与库存仍由各自权威系统保证业务原子性；
6. 冷启动和成本进入同一容量账本，只有尾延迟预算无法满足时才使用预置容量或常驻服务；
7. 接受合理的供应商能力绑定，但保持业务状态、幂等语义、事件合同、外部回执和恢复规则可导出；
8. 每项专有能力记录替代成本、迁移数据、重放风险和退出触发条件。

另两种方案不采用。同步函数编排器容易让调用栈承担长流程状态；完全事件编舞会模糊订单终态与恢复责任，并与 STY-06 重叠。推荐方案把“谁推进流程”和“谁执行一步”分开，同时保留对冷启动、队列和供应商能力的现实分析。

## 3. 读者问题与保留判断

文章必须让首次接触本模式的工程师回答以下五个问题：

1. 平台接管了哪些运行责任，业务团队仍拥有哪些责任？
2. 短生命周期函数、事件源、队列、持久工作流和状态存储如何分工？
3. 自动扩缩时，重复投递、并发竞争和下游过载如何受控？
4. 冷启动、预置容量和按调用计费如何进入同一容量决策？
5. 哪些供应商能力可以合理绑定，哪些状态和恢复语义必须可导出？

读者应保留六个判断：

- Serverless 转移容量配置和部分运行责任，不消除服务器、状态或运维；
- 函数适合有界计算步骤，不应默认拥有长流程状态；
- 自动扩缩必须服从入口、函数和下游三层并发预算；
- 至少一次投递要求幂等、条件状态转移和权威结果查询，不等于端到端 exactly-once；
- 冷启动是尾延迟与容量问题，预置容量是有成本的工具，不是默认答案；
- 可移植性不等于零绑定，真正需要保护的是业务状态、事件合同、恢复规则和可评估的退出成本。

## 4. 构件与所有权

系统固定包含以下七个构件：

- **同步入口函数：** 认证、校验请求、建立或读取幂等受理记录并返回操作标识；不等待整条履约链完成；
- **持久工作流：** 拥有步骤顺序、状态版本、期限、重试预算、补偿入口和人工终态；不取代支付或库存账本；
- **队列与任务分发：** 吸收突发、重投递任务并限制工作函数并发；积压是待处理事实，不是成功状态；
- **支付、库存与通知函数：** 每次只执行一个有界步骤，携带幂等键并返回标准结果；不把本地内存当作恢复事实；
- **订单状态记录：** 保存订单进度、操作标识、尝试次数、状态版本和外部回执引用；
- **权威下游系统：** 分别拥有支付结果、库存数量和通知投递事实；
- **容量与成本观测：** 关联入口速率、队列年龄、并发、节流、冷启动、执行时长、内存和单订单成本。

正文使用固定“执行与状态责任矩阵”：

| 构件 | 正向责任 | 持久事实 | 明确不拥有 |
| --- | --- | --- | --- |
| 同步入口函数 | 认证、校验、幂等受理 | 受理记录与操作标识 | 整条履约进度 |
| 持久工作流 | 步骤、期限、重试、补偿、终态 | 状态版本与步骤回执 | 支付或库存账本 |
| 队列与任务分发 | 缓冲、重投递、消费限速 | 消息与投递状态 | 业务成功结论 |
| 步骤函数 | 执行一个支付、库存或通知任务 | 只写回标准结果或回执 | 长流程状态与无限重试 |
| 订单状态记录 | 保存订单权威进度 | 订单版本、阶段与关联回执 | 下游业务事实 |
| 权威下游系统 | 原子判定支付、库存或投递结果 | 各自账本与结果查询 | 订单流程编排 |
| 容量与成本观测 | 关联延迟、并发、节流与费用 | 可审计的观测与归因记录 | 自动改变业务终态 |

控制权必须可追溯到最终负责人。订单团队拥有受理、状态转移、提交与补偿；支付和库存团队拥有各自权威操作与查询；平台团队拥有触发器、队列、函数配额、工作流运行时和观测接缝；FinOps 与平台共同提供成本归因，但订单域负责人决定何时因业务预算停止流程。

## 5. 一次订单调用的数据流

一次订单按固定九步推进：

1. 入口认证请求，以调用方幂等键检查或创建受理记录；
2. 入口返回订单操作标识，重复请求返回同一受理结果；
3. 持久工作流读取订单版本，生成支付任务和步骤幂等键；
4. 队列根据并发上限向支付函数交付任务，重复交付不生成新的业务操作；
5. 支付函数调用支付系统，明确成功或失败时记录回执；超时且结果未知时停止盲目重试，改为权威结果查询；
6. 工作流用条件状态转移接受与当前订单版本匹配的回执，再以同样方式推进库存；
7. 库存冲突由库存权威系统原子判定，函数扩容不能突破库存一致性边界；
8. 订单提交后，通知进入可降级的异步步骤；失败可有界重试或转人工，但不回滚已确认订单；
9. 每一步记录排队、执行、冷启动、下游等待、重试和费用归因，形成端到端容量账本。

入口幂等键、订单操作标识、步骤操作标识和事件标识不得混成一个字段。入口幂等键收敛重复受理；步骤操作标识帮助支付或库存查询真实结果；事件标识只标识一次投递。任何去重记录都必须有保留期和业务边界，不能在保留期结束后继续承诺永久 exactly-once。

至少一次投递不等于业务 exactly-once；函数超时不等于下游没有执行；工作流持久化也不把支付与库存纳入同一事务。所有改变订单结论的限制必须留在可见叙事中，不得只藏入证据卡。

## 6. 并发、故障与人工终态

并发按三层预算传播：

1. **入口层：** 按租户和操作类型设置速率、突发量与在途上限；超过预算时明确拒绝或延后受理；
2. **执行层：** 队列消费速率、函数保留并发和批大小受控；平台可用并发不是应用必须使用的并发；
3. **下游层：** 支付、库存等系统给出容量预算，执行层上限不得高于它；预算降低时优先减慢消费，不扩大重试。

正文使用固定七类故障合同：

| 故障 | 检测 | 自动响应 | 停止条件 | 最终责任人 |
| --- | --- | --- | --- | --- |
| 重复或乱序交付 | 相同幂等键、陈旧状态版本或乱序步骤 | 幂等查重、条件状态转移、丢弃陈旧版本 | 事件无法关联订单或状态版本 | 订单域负责人 |
| 队列积压与函数节流 | 队列深度、最老任务年龄、节流和业务期限 | 降低入口、限制消费、保护下游并告警 | 业务期限已无法满足 | 平台运行负责人 |
| 冷启动导致同步超时 | 初始化时长、尾延迟、客户端断开 | 预算内重试或使用预置容量；异步步骤继续查状态 | 客户端期限耗尽或结果未知 | 接口与容量负责人 |
| 支付或库存结果未知 | 调用超时、连接中断、缺少确定回执 | 用业务操作标识查询权威系统并对账 | 无法证明是否已产生外部效果 | 支付或库存域负责人 |
| 毒任务或确定性业务错误 | 同一输入与版本重复确定失败 | 隔离任务并保留输入、版本和尝试证据 | 重试不会改变结果 | 对应业务能力负责人 |
| 重试风暴或成本异常 | 调用放大、并发、错误率和费用预算 | 熔断、降低并发、暂停非关键步骤和新流量 | 单订单或时间窗预算耗尽 | FinOps 与平台负责人 |
| 托管工作流或区域故障 | 工作流不可用、检查点中断或区域信号 | 停止新推进，依据持久检查点恢复或切换 | 状态副本、事件顺序或外部回执不可信 | 业务连续性负责人 |

所有自动重试同时受次数、总时长、业务期限和成本预算约束。通知允许降级；支付和库存不能因队列可重试就默认跳过。任何无法判定真实外部效果的步骤最终进入查询、对账或人工终态。

## 7. 冷启动与成本账本

冷启动不能作为孤立指标。同步路径必须拆成入口排队、运行时初始化、依赖初始化、业务执行和下游等待。只有初始化对尾延迟预算构成实质影响时，才依次考虑减小部署包、延迟初始化、调整运行时、预置容量，最后评估迁移到常驻服务。异步步骤优先检查业务期限和队列年龄，不因单次冷启动直接扩容。

正文使用固定“冷启动与成本决策表”：

| 观察 | 先验证 | 首选动作 | 升级条件 |
| --- | --- | --- | --- |
| 少量同步请求尾延迟升高 | 初始化与下游等待各占多少 | 缩小依赖、延迟非必要初始化 | 初始化持续击穿业务期限 |
| 突发流量产生冷启动 | 入口速率、并发和下游预算 | 缓冲、限流、调整并发 | 同步请求不可缓冲且期限严格 |
| 预置容量利用率低 | 时段分布和空闲费用 | 调低或按时段调度 | 业务要求全时段稳定低延迟 |
| 异步任务处理变慢 | 队列年龄、消费速率和业务期限 | 调整消费与批量，保护下游 | 最老任务接近不可逆期限 |
| 持续高负载且波动小 | 单位成本、利用率和运维成本 | 比较按量函数与常驻服务 | 常驻服务在约束内更可预测 |

一次订单的容量账本至少归因：请求与事件调用次数；函数内存、执行时长与并发占用；工作流状态转移、队列请求与重投递；日志、指标、追踪和数据传输；预置容量或最低实例；支付、库存等下游调用成本；扇出、重复投递、无界重试和高基数观测等异常放大项。

文章不使用易失的绝对价格比较作为结论。来源中的价格和产品参数只说明计费维度与机制；实现阶段固定核查日期，计算示例使用明确标注的说明性输入，并强调区域、架构、折扣、免费额度、币种和产品版本都会改变结果。

## 8. 供应商边界、迁移与停止条件

供应商边界分成三层：

1. **必须保持可导出：** 订单状态、幂等语义、事件合同、外部回执、恢复规则、审计记录和成本归因；
2. **可以合理适配：** 触发器、队列接口、工作流操作、密钥和观测接缝；允许薄适配层，不追求跨云逐行兼容；
3. **可以明确绑定：** 专有并发控制、冷启动优化、状态机语法或事件路由能力，但每项记录替代方案、迁移数据、重放风险和退出触发条件。

迁移不是把所有函数原样搬到另一朵云。退出演练固定为：导出当前订单状态与未完成操作；冻结新流程版本；暂停或排空旧消费者；迁移事件合同、幂等身份和外部回执；在新执行面恢复未完成步骤；验证旧事件或迟到结果不会覆盖新状态；最后撤销旧触发器、凭证和写权限。

采用 Serverless 的信号包括事件驱动负载、明显峰谷、有界任务、可拆分状态和能够接受托管服务约束。采用路径从一个非关键、有界、可重放步骤开始，先建立幂等、状态、观测和停止条件，再引入持久工作流与队列，最后才扩大到支付或库存等高风险步骤。

以下情况要求保持现有服务、转向常驻运行时或停止采用：持续稳定高负载；极严格且无法吸收的尾延迟；长时间计算；需要本地专用资源；跨步骤共享内存或事务；执行模型与运行时限制不兼容；团队无法运营队列、幂等、成本和人工恢复；迁移所需状态和外部回执不能导出；供应商专有语义已经无法被业务合同解释或验证。

## 11. 来源与版权治理

来源采用定义、运行时、交付、扩缩、冷启动、并发、工作流与可移植事件八层最小闭环：

1. CNCF `Serverless Whitepaper v1.0` 与 Serverless Glossary：支持 Serverless 与 FaaS/BaaS 的范围，以及平台按需求执行、扩缩和计费的定义；不证明具体供应商行为；
2. AWS Lambda `Understanding the Lambda execution environment lifecycle`：支持标准函数执行环境的初始化、调用、复用、重置和冷启动机制；新增产品模式必须按页面小节分别限定，不能被外推为所有 Lambda 或所有 Serverless 运行时；
3. AWS Lambda `Understanding retry behavior in Lambda` 与异步错误处理文档：支持调用类型影响重试、重复事件和积压行为；固定参数只属于核查时的对应调用模式；
4. AWS Lambda 并发、预置容量与价格官方文档：支持保留/预置并发、冷启动缓解和额外费用维度；不构成跨区域或长期成本比较；
5. Azure Functions `Scale and Hosting`：支持托管计划、扩缩粒度、scale-to-zero、always-ready 与冷启动差异；不把实例上限或计划名称外推到其他供应商；
6. Google Cloud Run `Maximum concurrent requests for services`：支持部分 Serverless 运行时允许单实例并发请求，以及代码必须并发安全；不把 Cloud Run 容器服务等同于所有 FaaS；
7. CloudEvents `v1.0.2`：只支持跨服务、平台与系统描述事件数据的共同信封，不证明传输、顺序、去重、持久化或业务 exactly-once；
8. Open Workflow Specification `1.0.3`：只支持供应商中立工作流描述、事件、任务、超时、错误和重试等可表达机制；不证明任意运行时实现相同的持久化、故障恢复或迁移语义；
9. 原创图“订单结算与异步履约 Serverless 边界”，用于本站教学，不证明生产效果。
