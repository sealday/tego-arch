- **前置主题：** STY-00、STY-04、STY-05
- **相邻主题：** STY-04、STY-05、PR-09、PR-12

## 1. 目标与非目标

本主题新增一篇可独立阅读的架构风格文章，解释 Microkernel / Plug-in Architecture 如何把稳定业务核心与可替换扩展能力分开，同时把兼容、权限、资源和故障风险限制在明确边界内。统一案例是订单平台：宿主拥有订单流程、权威状态、提交与补偿，税费、支付、库存和通知能力通过插件扩展点接入。

设计采用 **控制面 + 执行面** 双平面。控制面负责插件身份、来源、签名、清单、能力、兼容范围、权限、租户绑定、健康和生命周期；执行面由订单宿主经受控调用网关调用独立插件进程。第三方插件默认不进入宿主地址空间，也不能直连订单数据库、互相调用或自行扩大权限。

文章聚焦应用级微内核和插件架构，不讨论操作系统微内核的调度、内存管理或硬件隔离，不把插件系统等同于微服务、事件总线、依赖注入容器、脚本钩子或任意动态代码加载。进程外执行只提供进程故障边界，不自动形成安全沙箱；操作系统身份、文件系统、网络、凭证和资源配额仍需单独限制。

本轮不实现真实插件运行时、市场、签名服务、容器平台或订单示例应用，不新增 npm 依赖，不修改全站发布流程，也不实现 STY-11。所有订单、插件清单、能力协商、灰度和故障数据均为原创教学场景，不宣称来自生产事故或基准测试。

## 2. 已批准决策

设计对话已确认以下四项决策：

1. 使用订单平台宿主，插件覆盖税费、支付、库存和通知；
2. 第三方插件默认在独立进程运行，通过受控 RPC 边界交互；
3. 兼容策略采用 API 版本与能力协商，宿主按支持范围启用、降级或拒绝；
4. 失败按职责分级：税费、支付、库存失败关闭，通知失败降级并进入异步补偿；
5. 生命周期采用受控动态激活：验证、预热、灰度、排空、卸载，失败恢复旧绑定。

推荐架构是双平面微内核。单宿主直接加载插件虽然简单，却会把版本、权限、发布和观测逻辑堆入订单代码；全事件总线会模糊同步关键决策的成败边界。双平面把“能否运行”和“如何运行”分开，同时保留宿主对业务流程的最终控制权。

## 3. 读者问题与保留判断

文章必须让首次接触本模式的工程师回答以下五个问题：

1. 稳定核心、扩展点、插件、注册表和调用网关分别拥有哪项责任？
2. 插件版本、能力和权限如何协商，何时允许降级，何时必须拒绝激活？
3. 进程隔离解决什么问题，为什么它不等于安全沙箱或租户隔离？
4. 同步关键插件和可降级通知插件失败时，宿主应如何停止、回退、补偿或转人工？
5. 何时值得建立插件平台，哪些假想变化、共享事务或运维能力缺口要求停止采用？

读者应保留六个判断：

- 可扩展性来自稳定扩展合同和可承担的治理成本，不来自“能动态加载代码”本身；
- 宿主拥有订单状态机、提交和补偿，插件只拥有获准能力的实现；
- 兼容声明是门禁输入，不是正确性证明，消费者合同和真实回归仍不可省略；
- 进程外插件可防止插件崩溃直接击穿宿主进程，但必须另行约束凭证、数据、网络、文件和资源；
- 动态激活是新旧实例并行、流量切换与旧版排空，不是在原地覆盖在途调用；
- 当变化不存在、接口无法稳定或团队不能运营兼容与隔离时，保持普通模块边界优于预建插件平台。

## 4. 双平面构件与所有权

控制面固定包含四个构件：

- **插件注册表：** 保存插件标识、制品摘要、发布者、接口版本、能力、依赖、运行约束、所有者和状态；注册表不执行订单业务；
- **供应链验证器：** 检查来源、签名、摘要、撤销和批准记录；通过验证不证明插件业务逻辑正确；
- **策略与权限引擎：** 按租户、环境和能力授予最小数据、网络、凭证和资源范围；插件声明需求，不决定授权；
- **发布控制器：** 执行验证、预热、灰度、停止推进、恢复旧绑定、排空和卸载；它不替订单域决定业务补偿。

执行面固定包含三个宿主构件和四类插件：

- **订单微内核宿主：** 拥有订单流程、权威状态、扩展点顺序、结果验证、提交、补偿和人工终态；
- **受控调用网关：** 执行能力解析、协议协商、最小数据投影、期限、幂等键、短期凭证、配额、熔断、结果结构校验和审计；
- **补偿队列：** 只承载允许异步恢复的通知类工作，不接受税费、支付或库存正确性结果的默认跳过；
- **税费、支付、库存、通知插件进程：** 每个插件只实现一个被批准的扩展能力，不共享宿主内存，不直连订单数据库，不互相组成隐藏业务流程。

业务团队拥有订单流程、外部效果、失败分类和人工决定；插件作者拥有插件实现、清单、兼容声明和运行手册；插件平台团队拥有注册、验证、调度、网关、隔离、配额和发布控制；安全团队拥有签名根、撤销、权限策略和安全事件处置。共同责任必须拆成明确的批准和操作步骤，不能用“平台与业务共同负责”代替最终负责人。

## 5. 能力合同与兼容门禁

每个插件清单至少包含以下固定字段：插件 ID、发布者、制品摘要、插件版本、协议/API 版本范围、能力及版本、必需和可选依赖、所需权限、资源预算、数据字段清单、幂等与重试声明、健康探针、所有者和撤销状态。

宿主解析扩展点时按固定顺序决策：

1. 验证插件身份、来源、签名、摘要和撤销状态；
2. 检查宿主协议/API 版本与插件支持范围是否相交；
3. 检查扩展点所需能力、能力版本和必需依赖；
4. 将插件声明的权限与租户/环境策略求交，不允许声明自动扩大授权；
5. 检查健康、资源、灰度和回滚状态；
6. 产生一个版本化、可审计、带期限的激活绑定。

正文包含固定八维兼容与治理矩阵：

| 维度 | 插件声明 | 宿主/平台门禁 | 不满足时 |
| --- | --- | --- | --- |
| 身份与来源 | 插件 ID、发布者、摘要、签名 | 信任根、来源和撤销检查 | 隔离制品并拒绝激活 |
| 协议/API | 支持的版本范围 | 与宿主版本求交并运行合同测试 | 使用已批准兼容版或拒绝 |
| 能力 | 能力 ID、版本、必需/可选标记 | 扩展点需求与能力集合匹配 | 可选能力降级，必需能力拒绝 |
| 依赖 | 插件/平台依赖及范围 | 检查存在、兼容和循环 | 拒绝或保持旧绑定 |
| 权限 | 数据、网络、凭证、文件需求 | 与租户和环境策略求交 | 缩小授权；无法运行则拒绝 |
| 资源 | CPU、内存、并发、响应大小 | 配额、准入、超时与熔断 | 限流、隔离或停止新流量 |
| 数据与结果 | 输入字段、输出结构、错误分类 | 最小数据投影与结果校验 | 拒绝请求或隔离响应 |
| 生命周期 | 健康、灰度、排空和回滚能力 | 发布闸门与当前绑定状态 | 停止推进并恢复旧绑定 |

语义版本和范围只表达兼容承诺。破坏性业务含义、权限扩大、外部效果或错误语义变化必须提升能力/API 版本并重新批准；未知字段是否可忽略、默认值是否安全、旧插件是否可读新输入都必须由合同测试证明。没有安全相交范围时，正确行为是拒绝激活，不是强制适配或静默删字段。

## 6. 一次订单调用的数据流

一次税费调用按以下顺序发生：

1. 订单宿主到达 `tax.quote` 扩展点并请求所需能力版本；
2. 调用网关向控制面解析该租户当前批准、健康且兼容的插件绑定；
3. 宿主生成最小数据投影，只包含订单 ID、地区、应税项目和合同版本；
4. 网关加入操作 ID、幂等键、期限、调用预算和短期凭证，调用独立插件进程；
5. 插件返回版本化结果或标准错误，不回调订单数据库，也不自行推进订单状态；
6. 网关校验响应结构、大小、耗时和权限使用，记录可观测信号；
7. 宿主根据业务失败策略接受结果、有限重试、失败关闭、降级、补偿或转人工；
8. 控制面只接收健康与策略信号，不取得订单业务决策权。

最小数据投影必须按扩展点定义并可审计。插件不得接收整张订单对象作为未来兼容的“方便接口”，不得持有长期宿主凭证，也不得用日志、错误正文或回调 URL 绕过数据边界。宿主只接受声明过的结果字段；插件新增字段不能自动改变订单语义。

调用网关必须区分调用未开始、明确失败、成功、超时后结果未知、结果不兼容和被策略拒绝。超时不等于插件没有执行外部效果；支付类插件恢复前必须查询权威结果、使用目标侧幂等合同或转入对账，不能盲目重放。

## 7. 故障、隔离与人工终态

正文包含固定五类故障责任表：

| 故障类别 | 检测 | 自动响应 | 停止条件 | 人工所有者 |
| --- | --- | --- | --- | --- |
| 版本/能力不兼容 | 解析无交集、合同测试或结果结构失败 | 保持旧绑定、拒绝候选或使用明确可选降级 | 无批准兼容版本 | 插件平台负责人 |
| 税费/支付/库存超时或失败 | deadline、标准错误、熔断与结果查询 | 有限重试；结果未知先查询/对账；关键步骤失败关闭 | 预算耗尽或无法判定真实结果 | 订单域负责人 |
| 通知插件失败 | 超时、明确失败或不可用 | 降级并写入补偿队列，按幂等键有界重试 | 次数/时限耗尽或重复失败 | 通知能力负责人 |
| 权限、签名或来源异常 | 签名/摘要/撤销/策略拒绝和异常访问 | 隔离实例、撤销短期凭证、停止新流量并保留证据 | 证据保存后禁止自动重放 | 平台安全负责人 |
| 资源耗尽或崩溃风暴 | CPU/内存/并发/响应大小、退出率和重启率 | 限流、熔断、停止新激活、隔离版本 | 健康窗口内未恢复 | 插件运营负责人 |

重试必须同时受次数、总时长和业务期限约束。熔断保护宿主和下游，不把失败变成成功。隔离插件版本后，已开始的调用按调用身份和状态处理，不能把所有未知结果重新排队。通知补偿队列必须有所有者、告警、最老任务年龄、重试上限和人工终止路径。

插件崩溃不应直接结束宿主进程，但共享操作系统用户、无限网络权限、宿主挂载目录或长期凭证仍可扩大影响半径。生产化分析必须分别验证进程、身份、网络、文件、密钥、资源、租户数据和日志边界，不得用一个“sandboxed”标签代替逐项证据。

## 8. 受控动态激活与回滚

生命周期固定为五个阶段：

1. **验证：** 检查制品身份、签名、摘要、清单、漏洞/撤销状态、兼容范围和合同测试；
2. **预热：** 启动候选进程，完成握手、健康、权限、资源和合成调用检查；
3. **灰度：** 按租户、订单分片或小比例新请求绑定候选版本，比较成功率、延迟、错误类别、资源和业务结果；
4. **排空：** 旧实例停止接收新请求，但继续处理已绑定调用，直到归零或到达明确终止条件；
5. **卸载：** 撤销旧绑定和凭证，保存审计记录后释放实例。

任何阶段失败都停止推进、恢复上一批准绑定、保留候选证据并由负责人决定修复或终止。回滚只改变新请求的版本绑定；它不会撤销插件已经产生的外部效果，也不能使不兼容状态自动恢复。若候选写入了旧版不能读取的状态或产生不可逆效果，应停止发布并前向修复、迁移或对账，而不是强制回滚。

插件版本与订单调用必须可关联。每次调用记录插件 ID、制品摘要、能力版本、激活绑定、租户、操作 ID、deadline、结果分类和审计身份。旧实例排空依据的是可验证的在途计数和期限，不是固定等待数秒。

## 9. 适用、迁移与停止条件

适用信号包括：同一稳定核心面对多个真实实现；第三方或独立团队需要独立交付；租户/区域/供应商差异可映射到明确扩展点；扩展合同比持续修改核心更稳定；平台团队能够承担兼容、供应链、隔离、发布、观测和支持成本。

采用路径从普通模块边界开始：

1. 收集真实变化和实现差异，不为假想需求预建扩展点；
2. 在宿主内提取一个业务含义明确、输入/输出有限的策略接口；
3. 固定业务所有权、错误语义、权限和消费者合同测试；
4. 引入清单、注册表和版本/能力解析，但仍保持同一制品；
5. 当独立交付或第三方风险成立时，再迁移为进程外 RPC 插件；
6. 建立签名、最小权限、配额、灰度、排空、回滚和人工处置后，才开放动态激活。

以下情况要求保持模块、收紧范围或停止采用：只有一个稳定实现且没有独立交付需求；插件需要共享宿主事务或任意内部对象；扩展点业务含义频繁变化；低延迟预算不能承担 RPC 和隔离成本；平台无法验证制品来源或限制权限；团队不能维护兼容矩阵、消费者测试、灰度和恢复；每次上线仍需所有插件锁步升级；插件之间形成隐藏依赖图或共享数据库；为追求“开放”而把所有内部接口暴露成插件面。

## 14. 发布、兼容性与完成定义

发布沿用 Stage A / Stage B：

- **Stage A：** 生成新文章和来源投影，STY-10 为 published/pending，STY-11 为 unpublished/pending/non-actionable；完成独立 code、content/rights、architecture 三审；发布 exact READY head并收集生产 HTTP、SVG 和四态 IAB 证据；
- **Stage B：** 只有 Stage A 生产证据闭合后，才勾选 STY-10、将其设为 published/complete，并把 STY-11 设为唯一下一项；再次三审、发布 exact READY head并收集全新生产证据；
- 每次证据提交必须是 evidence-only，固定 raw bytes/SHA、实现 head、run/job、路由、SVG、四态语义、诊断和截图尝试；最终 `HEAD = origin/main = merge-base` 且 ahead/behind `0/0`。

截图若不能形成可信全页证据，必须保存精确尝试并标记 `CAPTURED_REJECTED` 与 `BLOCKED / NOT_ACCEPTED`；功能、HTTP 和确定性图示证据可独立通过，但不得把拒绝截图写成视觉 PASS，不得复用旧截图或切换未授权浏览器。

兼容要求：复用现有 Docusaurus、MDX、生成器、来源治理、术语、横向滚动、Draw.io/SVG 校验和 GitHub Pages 流程；不新增 npm 依赖，不改变全站视觉 token、URL 或发布路径；`src/generated/` 只由现有生成命令更新；不重写 STY-04/STY-05/PR-09/PR-12 的核心定义，只增加准确互惠入口；不修改历史评审、Pages 证据或用户文件来迎合当前投影。

设计起点是 62 个已完成主题、105 篇内容文档和 544 个受治理来源。新增文章后文档数应为 106；来源增量在 Task 3 完成去重、版本和权利审计后由生成器给出，计划与测试固定实际值，不在设计中猜测。Stage B 仅在真实生产证据齐全后把完成主题推进为 63，并保持 STY-11 unpublished/pending/non-actionable。
